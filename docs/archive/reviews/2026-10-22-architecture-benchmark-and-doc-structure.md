# 目标架构对标与文档结构优化

> **评审对象**：`prd.md` · `architect.md` · `data-model.md` · `api.md` · `implementation-status.md` · `ops-target.md` · `setup.md` · `README.md`（合计约 190KB / 8 份）
> **评审视角**：架构层面（风格、边界、质量属性、治理），不进入代码细节
> **对标框架**：arc42 · C4 · ADR(Nygard) · ATAM 质量属性场景 · Diátaxis · Fitness Function
> **日期**：2026-10-22

---

## 0. 一句话结论

**技术选型已经站在 2026 年的主流位置，差距不在"用什么"，而在"怎么治理"和"文档怎么组织"。**

| 层面 | 评级 | 判断 |
|---|---|---|
| 技术选型 | **A−** | Next.js 16 App Router + RSC + Server Action + Drizzle + Neon + RLS，这套组合就是当下 1–3 人 SaaS 的最优解，没有明显选错的地方 |
| 工程质量体系 | **C+** | 测试很强（强于同规模团队），但**可观测性、环境隔离、隐私合规**三块是空的 |
| 文档结构 | **B−** | 内容质量高于绝大多数项目（有 ADR、有质量指标、有风险登记），但**组织形式停留在"一份大文档"范式**：190KB 平铺、无索引、无阅读路径、状态靠 5 份文档互相引用维持 |

三个最值得投入的缺口，按 ROI 排序：

1. **没有 staging / preview 环境**（Neon 分支几乎免费，却解决了"生产形态一次没跑过"这个最大未知）
2. **声称 99.5% 可用但无法测量**（无错误聚合、无 trace、无 SLO 看板 → 这个指标目前不存在）
3. **软删永存 vs 个人信息删除权**（家谱含在世人口信息，PIPL 适用；ADR-15「零后台任务」与删除权直接冲突）

## 1. 对标框架：用哪几把尺子，用到什么程度

现代架构文档实践的骨架由 6 个来源构成。**全盘照搬会压垮 1–3 人团队，所以下表的核心是"用多少"。**

| 框架 | 解决什么问题 | 本项目建议用到什么程度 |
|---|---|---|
| **arc42** | 架构文档的章节骨架（12 章） | **取其骨架，不取全部**。用它的 1/3/5/6/7/8/9/10/11 章，砍掉 2/4/12 的独立成章 |
| **C4** | 分层视图（Context / Container / Component / Code） | **只做 L1 + L2 + L3**。L4（类图）对 TS + Drizzle 项目零收益，代码即文档 |
| **ADR (Nygard)** | 记录"为什么这样选、放弃了什么" | **只给 5–7 个不可逆决策写正式 ADR**，其余留在索引表。全部 21 条都写 = 21 份没人读的文档 |
| **ATAM 质量属性场景** | 把 NFR 从形容词变成可验证的六元组 | **必做**。这是当前文档最大的结构性缺陷：有指标，没有场景 |
| **Diátaxis** | 按"教程/操作/参考/解释"四类组织文档 | **必做**。现有 8 份文档已经隐约分了类，但没有显式命名，导致新人不知道从哪读 |
| **Fitness Function** | 把架构约束变成 CI 里会失败的检查 | **选 5 条**。现在所有约束（"service 不得 import next/*"、"单文件 ≤ 400 行"）都只是文字 |

### 明确不建议采用的

| 实践 | 为什么不适用 |
|---|---|
| 完整 arc42 12 章 | 第 2 章（约束）与第 4 章（解决策略）在本项目各只有半页内容，独立成章是形式主义 |
| C4 L4 代码图 | TS 类型 + Drizzle schema 本身就是最精确的代码视图，画图必然过期 |
| 正式 ATAM 评审会（多角色、2 天） | 团队 1–3 人，没有独立评审方。用它的**场景格式**即可，不必用它的流程 |
| RFC 流程（提案 → 评审 → 批准） | 决策人就是实现人，RFC 会退化成自我审批。ADR 足够 |
| 架构看板 / 架构度量平台 | 6 个模块的体量，仪表盘的成本高于收益 |

## 2. 架构对标：12 个维度的成熟度

「现代基线」一列写的是**2026 年主流团队的实际做法**，不是理想状态。

| # | 维度 | 现代基线 | 现状 | 评级 |
|---|---|---|---|:--:|
| 1 | 架构风格 | 模块化单体 + **垂直切片**：按业务能力切分，模块内不再强制水平三层 | 模块化单体 ✓；但模块内强制"适配/服务/仓储"三层，而代码实际已漂向按域聚合（`lib/db/services.ts`） | **B** |
| 2 | 前端渲染 | RSC 首屏直出 + 客户端缓存层 + 选择性预渲染 | RSC + TanStack Query + `dehydrate` ✓，这一块**领先**同规模项目；未评估 Next 16 的 `use cache` / PPR | **A−** |
| 3 | 前后端契约 | 单一类型源 + 运行时校验 + **中间件化的 Action 包装** | Zod ✓；但 30 个 Action 各自手抄同一套 5 步骨架（校验→上下文→权限→事务→失效） | **B** |
| 4 | 数据访问 | SQL-first 类型安全 ORM + expand/contract 迁移 | Drizzle + 三段式迁移 + 迁移漂移检查 ✓ **教科书级** | **A** |
| 5 | 多租户隔离 | 数据库强制隔离（RLS）+ 应用层过滤 + schema 约束 | 三层齐全，且用 `SECURITY DEFINER` 解掉了 RLS 自引用递归 ✓ **教科书级** | **A** |
| 6 | 认证会话 | Argon2id；会话可即时撤销 | bcrypt（OWASP 现推荐 Argon2id 优先）+ HS256 单密钥 + `token_version`；无轮换路径 | **B** |
| 7 | 可观测性 | OTel trace + 错误聚合 + SLO / 错误预算 | 仅结构化日志。无 trace、无聚合、无看板 → **99.5% 这个指标无法测量** | **C** |
| 8 | 环境与发布 | 每 PR preview 环境 + 临时数据库分支 + 可回滚 | 无 staging、无 preview；迁移与发布同一条流水线；生产形态**一次没跑过** | **D** |
| 9 | 测试 | 金字塔 + 真实依赖集成 + 关键路径 E2E | 73 单测 + 134 真实 PG 集成 + E2E + 覆盖率门槛 ✓ **强于绝大多数同规模团队** | **A−** |
| 10 | 隐私与数据生命周期 | 数据分级 + 保留期 + 删除权 + 可携带权 | 软删永存；无分级、无 TTL、无自助导出 | **D** |
| 11 | 无障碍 | WCAG 2.2 AA + 键盘可达 + 复杂交互的替代视图 | 仅约定对比度；世系表可作画布的替代视图，但未在文档中声明为无障碍路径 | **C** |
| 12 | 文档治理 | 索引 + 分视图 + 真 ADR + 可执行约束 | 见 §3 | **B−** |

**读法**：4 个 A 全在"数据与隔离"上，3 个 C/D 全在"运行与治理"上。这个分布很典型——**这是把最难的技术做对了、把最不性感的治理留空了的项目**。

## 3. 架构层面值得改的 5 件事

只列"改的是架构决策，不是代码实现"的。

### A. 分层 → 垂直切片：文档要追上代码

`architect.md` §4.4 规定模块内固定三层（`app/**` 适配 → `*.service.ts` 业务 → `*.repo.ts` SQL），并配了"service 不得 import `next/*`"这类规则。

但这套规则在这个项目上的**收益接近于零**：

- 6 个模块、30 个 Action，绝大多数业务规则是"校验 + 权限 + 一次写入 + 失效缓存"，service 层没有独立的业务逻辑可放；
- 真正有规则的地方（`moveNode` 的子树重算、`deleteNode` 的级联软删）自然长成了 871 行的 `node-services.ts`——因为规则本来就是聚在一处的；
- 结果是代码自发漂移成**按域聚合**（`lib/db/services.ts` 按 organization/member/project/account 分组），与文档的三层正交。

**现代做法（垂直切片）**：一个能力一个目录，里面放它的 schema、query、action、组件；只有当"同一条规则被两个入口调用"时才抽 service。判断标准不是"架构纯洁"，是**"抽出来之后有没有第二个调用方"**。

**建议**：`architect.md` §4.4 改为"默认垂直切片，满足以下任一条件才抽服务层：① 同一规则 ≥2 个入口 ② 需要跨模块事务 ③ 需要被定时任务复用"。同时删掉"service 不得 import next/*"这条——它防的是不存在的病。

> 这不是"降低标准"，而是承认：**分层架构的收益来自"同一规则有多处调用"，这个项目没有这个前提。**

### B. 补一个 preview 环境（ROI 最高的一件事）

现状：`ops-target.md` 定义了生产拓扑，`verify:deploy` 能在本地生产模式跑通，但**真实 Vercel + Neon 一次没部署过**（`implementation-status.md` 风险 #2、#10 自认）。

这意味着三个高风险假设从未被验证：

1. `pg.Pool` + `attachDatabasePool` 在 Fluid compute 下的连接生命周期；
2. 生产 `POSTGRES_URL` 使用非属主 `app` 角色时，`FORCE RLS` 的兜底是否真的生效；
3. pooled / direct 双 URL 分离下，迁移能否在部署前独立执行成功。

**现代做法**：Vercel Preview Deployment + Neon 分支（`neonctl branches create --parent main`），每个 PR 一套独立数据库。Neon 按分支计费，空闲分支几乎免费。

**为什么这是架构级而不是运维级**：它同时解决了"地基未验证"和"没有 staging"两个问题，而且让 §8 的隔离测试第一次能在**真实生产角色配置**下跑。`architect.md` §11 的"隔离：跨组织查询 0 行"现在只在超级用户迁移 + `SET LOCAL ROLE` 的组合下验证过——那和生产不是同一件事。

### C. 可观测性：从"有日志"到"有 SLO"

现状：结构化 JSON 日志 + `request_id` + `duration_ms`。这是 2020 年的水准，且**有一个内在矛盾**：

- `architect.md` §7 承诺「月度可用率 ≥ 99.5%」；
- `architect.md` §9.5 说「无外部服务；未预期异常写 error 级日志，由 Vercel 日志收集」；
- Vercel 日志有保留期、不可聚合查询、不能告警。

**结论：99.5%（每月 3.6 小时停机预算）这个指标目前无法测量，因此不构成承诺。**

**现代最小集（1–2 天可落地）**：

| 层 | 做什么 | 成本 |
|---|---|---|
| 错误聚合 | Sentry（或等价），Server Action 的 `{ok:false}` 与未捕获异常都上报 | 半天 |
| Trace | `request_id` 贯穿 + 关键查询耗时打点（已有 `duration_ms`，补 DB 段） | 半天 |
| SLO | 3 条：可用性 99.5% / 保存 p95 < 800ms / 错误率 < 0.1% | 半天 |
| 告警 | 错误率突增 → 邮件；`/api/health` 5 分钟探针 → 连续 3 次失败告警 | 半天 |

**特别提醒**：`api.md` §4 的设计让所有写错误返回 HTTP 200 + `{ok:false}`。这个设计本身是对的（UI 要区分错误类型），但它有一个副作用——**服务端错误率恒为 0%**。所以 `prd.md` §8 的「保存失败率 < 0.1%」只能靠客户端埋点或服务端显式上报 `error.code` 才能测。这一点必须在文档里写明，否则这个成功指标永远是空的。

### D. 隐私与数据生命周期：一个被整体遗漏的架构关注点

这是本次对标中**唯一属于"缺一整块"而非"做得不够好"**的维度。

事实基础：

- 家谱数据包含**在世人口**的姓名、性别、生卒、葬地、行传（`node` 表字段），属于《个人信息保护法》定义的个人信息；
- 产品形态是公有云 SaaS，用户是组织（家族），数据主体是族人——**用户与数据主体不是同一人**；
- 现状：`deleted_at` 软删，**永不物理删除**（ADR-09），且 `app_rw` 无 `DELETE` 权限，物理删除在数据库层被挡住；
- ADR-15：「后台任务零个」，理由「无清理需求」。

**冲突点**：PIPL 第 47 条赋予个人删除权。一个族人要求删除自己的信息时，当前架构的答案是"数据永久保留，只是界面不可见"。这不是技术问题，是合规问题，而且**ADR-15 的"无清理需求"这个前提是错的**。

**建议在架构里补三件事**：

| 补什么 | 内容 |
|---|---|
| 数据分级 | L1 账号凭据（邮箱/哈希）· L2 在世人口 PII · L3 已故人口信息 · L4 谱文内容。分级决定加密、保留期、导出粒度 |
| 保留期与硬删路径 | 账号删除 → 30 天冷静期 → **物理删除**（需要 `app_admin` 角色或运维脚本，打破"永不 DELETE"） |
| 可携带权 | 组织级自助导出（`prd.md` Q6 一直悬着，但它其实是法律要求，不是产品偏好） |

**这会让 ADR-15 从"零后台任务"变成"一个清理任务"**——这是本项目第一个真正的后台任务，值得单独立一条 ADR，说明触发条件与实现方式（Vercel Cron 或 Neon 定时函数）。

### E. ADR 表格 → 真 ADR：只写 5 篇

`architect.md` §13 的 21 行表格是一个**决策索引**，不是 ADR。它记了"结论"和"理由"，但丢了 ADR 最值钱的部分：**当时的约束是什么、放弃了哪些方案、代价是什么、什么条件下应该推翻它**。

**建议**：保留表格作为索引（`decisions/README.md`），只给以下 5 个**不可逆或高代价**的决策写正式 ADR：

| ADR | 主题 | 为什么值得写 |
|---|---|---|
| ADR-0002 | 不做编辑锁（last-write-wins） | 直接导致用户数据丢失，是最可能被推翻的决策；必须写清"什么信号出现时提前做" |
| ADR-0003 | 树存储用邻接表 + ltree，且严格父系 | 决定了过继/兼祧/入赘不可表达；M3 排版会固化它，改动是跨全表迁移 |
| ADR-0004 | 软删永存，无回收站 | 与隐私删除权冲突；需要写清边界与补救路径 |
| ADR-0005 | 无后台任务 | 会被隐私清理任务打破；需要写清"第一个任务为什么可以破例" |
| ADR-0006 | RLS + 三层隔离，组织不入 JWT | 全系统最重要的安全假设；需要写清"迁移角色必须 BYPASSRLS"这个隐含前提 |

其余 16 条留在索引表里就够——它们要么是低争议的技术选型（UUIDv7、Drizzle、Biome），要么是标准做法（软删、部分唯一索引）。

**一个现代补充：给决策标注可逆性。** Bezos 的 one-way / two-way door 框架在这里特别有用：

- **单向门**（不可逆）：RLS 隔离模型、树存储形态、主键类型、公开 ID 格式 → 值得花时间、值得写 ADR；
- **双向门**（可逆）：缓存层、限流实现、日志格式、ORM 选型 → 快速决定，错了再改，不必留档。

现有 21 条没有这个区分，导致"UUIDv7 vs serial"和"是否做编辑锁"看起来同等重要——实际差两个数量级。

## 4. 明确不建议做的（避免过度工程）

对标的价值一半在"该做什么"，一半在"不必做什么"。以下 5 项在"现代化"的名义下很容易被引入，但对这个项目是负收益：

| 不做什么 | 理由 |
|---|---|
| 拆微服务 / 引入消息队列 / 事件驱动 | 6 个模块、峰值 QPS < 50、1–3 人团队。拆分的唯一收益是"独立部署"，而独立部署的前提是"有独立团队" |
| 上 tRPC / OpenAPI / GraphQL | 没有外部消费者。`api.md` 已经论证过"多维护一份契约，收益为零"，这个判断是对的 |
| 把 RLS 换成应用层租户过滤（或反之） | 三层防护是当前设计的核心优势，动任何一层都会削弱另两层 |
| 完整 arc42 + 正式 ATAM + C4 L4 | 文档成本 > 收益。§1 已给出裁剪方案 |
| 引入 CQRS / 事件溯源 / 领域事件总线 | 领域模型简单（10 张表、无复杂聚合），引入后所有读都要经过投影，复杂度翻倍而收益为零 |

## 5. 文档结构：现状诊断

### 5.1 现状盘点

| 文档 | 体量 | 实际服务的读者 | 类型（Diátaxis） |
|---|---:|---|---|
| `prd.md` | 17KB | 产品 / 未来自己 | Explanation |
| `architect.md` | 37KB | **开发者 + 运维 + 产品 + 未来自己（4 类混在一起）** | Explanation + Reference 混杂 |
| `data-model.md` | 39KB | 开发者 / DBA | Reference + Explanation 混杂 |
| `api.md` | 20KB | 开发者 | Reference |
| `implementation-status.md` | 20KB | 开发者 / 产品 | Reference（状态） |
| `ops-target.md` | 30KB | 运维 | How-to + Reference |
| `setup.md` | 28KB | 新加入者 | Tutorial |
| `README.md` | 8KB | 所有人 | 索引（弱） |

### 5.2 六个结构性问题

**① `architect.md` 一份文档服务 4 类读者，没有阅读路径。**

37KB 里，新人需要的是 §4（组件）、§6（前端）、§7（后端）；运维需要的是 §3、§10、§9.3；产品需要的是 §1、§12；未来的自己需要的是 §13、§14。**没有任何一处告诉读者"你该读哪几节"。** 结果是要么全读（37KB，约 1.5 小时），要么全不读。

**② "目标 vs 现状"靠 5 份文档互相引用维持。**

现状是：4 份目标文档各带一个状态横幅（"M1 目标设计，业务层未实现"），第 5 份 `implementation-status.md` 记录差异。任何一次实现推进，要更新 **5 个地方**才能保持一致。这不是文档问题，是**状态没有单一来源**。

现代做法：**目标文档不写状态，状态只在一个地方，且机器可校验。**

**③ ADR 是索引不是决策记录。** 见 §3-E。

**④ 质量属性只有指标，没有场景。**

`architect.md` §11 是一张"属性 / 目标 / 验证方式"的表。它有度量（45fps、400ms、99.5%），但**缺 ATAM 场景六元组里的三个关键要素**：谁触发、在什么条件下、期望什么响应。

对比：

| 现在的写法 | 场景写法 |
|---|---|
| 「性能（画布）：1000 节点 ≥ 45fps」 | 「修谱主事人（**来源**）在 5000 人丁的谱系上（**环境**）拖拽画布（**刺激**）时，画布（**制品**）保持流畅（**响应**），帧率 ≥ 45fps 且首帧 < 100ms（**度量**）」 |

差别不是形式：**场景能直接推出设计决策**（"5000 人丁" → 需要按代加载，而不是全量加载），指标不能。这也是为什么文档里"1000 节点 45fps"和"单组织 50 万人丁"能同时存在而不矛盾——因为没人把它们放进同一个场景里。

**⑤ 缺 3 类"最高频被查阅"的文档。**

按查阅频率排序，这个项目最常被问的问题不是"架构为什么这样"，而是：

| 缺什么 | 被问的频率 | 现在怎么办 |
|---|---|---|
| **如何新增一个实体**（schema → 迁移 → query → action → 页面 → 测试 的完整清单） | **最高** | 照着现有代码抄 |
| **运维 runbook**（误删恢复、密钥轮换、连接池耗尽、迁移失败回滚） | 故障时最高 | 散落在 `data-model` §11.3 与 `architect` §14 |
| **测试怎么写**（分层原则、什么时候写集成测试、如何造数据） | 新人最高 | 读现有测试 |

**⑥ 缺隐私/数据生命周期一整块。** 见 §3-D。

### 5.3 章节重叠清单

同一内容出现在多处，改一处漏三处：

| 内容 | 出现在 |
|---|---|
| 软删除机制 | `data-model` §11 · `architect` §8.4 · `prd` §5.4 |
| 权限矩阵 | `prd` §3.2 · `architect` §5.2 · `data-model` §12.5 · `api` §2.2 |
| 错误模型 | `architect` §9.2 · `api` §4 |
| NFR / 质量属性 | `prd` §7 · `architect` §11 |
| 角色定义 | `prd` §3.1 · `data-model` §14 |
| 组织解析 | `architect` §5.3 · `api` §2.2 |
| 无编辑锁的取舍 | `prd` §6.3 · `architect` §5.5 · `api` §3.3 |

七处重叠。现代做法：**每个事实只有一个权威位置，其他地方只链接。**

## 6. 建议的目标文档结构

### 6.1 设计原则（三条）

1. **一份文档只服务一类读者 + 一个更新触发条件。** 违反这条就拆。
2. **每个事实只有一个权威位置。** 其他地方用链接，不用复制。
3. **状态只有一个来源，且可机器校验。** 目标文档不写"已实现/未实现"。

## 7. 三个必须补写的内容大纲

### 7.1 质量属性场景（`08-quality.md` 核心）

七条，每条都对应一个真实的设计决策或验证手段。格式固定：**来源 · 刺激 · 制品 · 环境 · 响应 · 度量**。

| ID | 场景 | 推出的设计 |
|---|---|---|
| QA-PERF-1 | 修谱主事人在 5000 人丁的谱系上拖拽画布时，画布保持 ≥45fps，首帧 <100ms | 按代加载窗口 + 纯函数布局 + `onlyRenderVisibleElements` |
| QA-PERF-2 | 编辑者保存一个人丁时，p95 < 800ms，且不因谱系规模退化 | 单事务写入 + 子树重算上限 + `statement_timeout` |
| QA-PERF-3 | 打开谱系详情页时，TTFB < 400ms（含上下文解析与首屏数据） | 请求级单事务 + 合并上下文 RPC + RSC 直出 |
| QA-AVAIL-1 | 单个 Vercel 实例故障时，请求路由到健康实例，错误率 < 0.5%，恢复 < 30s | 无状态 + 健康探针 + 错误预算 |
| QA-SEC-1 | 攻击者持有组织 A 的会话，请求组织 B 的谱系 ID 时，返回 404 且不泄露存在性 | RLS + 应用层成员过滤 + 复合外键 |
| QA-DATA-1 | 用户误删一棵 200 人的子树后，运维能在 15 分钟内整组恢复，零数据丢失 | 软删 + 同事务时间戳 + runbook |
| QA-PRIV-1 | 数据主体行使删除权时，30 天内完成物理删除并出具确认 | 数据分级 + 保留期 + 硬删路径（**当前不成立**） |
| QA-MAINT-1 | 开发者新增一个实体时，改动 ≤5 个文件，CI 全绿，无需修改架构文档 | 垂直切片 + `add-a-feature` 清单 + fitness function |

**关键**：QA-PRIV-1 和 QA-MAINT-1 现在是**红色的**。场景化写法的价值就在于让红色的东西显形——指标表里看不出来。

### 7.2 威胁模型（`10-threat-model.md`）

信任边界 5 条：浏览器 ↔ Vercel 边缘 ↔ Next.js 运行时 ↔ `app_rw` ↔ `auth` schema。

STRIDE 逐边界，只列**当前有真实缺口**的：

| 类别 | 威胁 | 现有控制 | 缺口 |
|---|---|---|---|
| Spoofing | 会话 Cookie 伪造 | HS256 签名 + HttpOnly + `token_version` | 密钥无轮换路径（泄露即全量伪造） |
| Tampering | 跨组织 IDOR | RLS + 应用层过滤 + 复合外键 | 无 |
| Tampering | 邀请 token 枚举 | 高熵 + 只存哈希 + 7 天过期 | 无 |
| Repudiation | 无法回答"谁改了什么" | 结构化日志 + 软删 | 日志有保留期，超出即无法追溯（已登记为缺口 6） |
| Info disclosure | 密码哈希外泄 | `app_rw` 无 `auth.users` 权限 | `getSessionUser()` 返回整行，靠出口自觉收窄 |
| Info disclosure | 内部人员整库导出 | 无导出功能 | `pg_dump` 权限无约束、无审计 |
| DoS | 登录爆破 | 进程内限流（IP + 邮箱） | 多实例不共享；依赖 `x-forwarded-for` 可信性 |
| DoS | 大树移动拖垮连接池 | 无 | **无 `statement_timeout`** |
| Elevation | viewer 写入 | RLS 策略排除 viewer | 无 |
| Elevation | admin 降级/移除 owner | 服务层校验 | 数据库层无约束（已登记为风险 #1） |

**这张表的用法**：每次新增外部接口或权限路径时重跑一遍，缺口行的增减就是安全工作的进度。

### 7.3 新增一个实体的清单（`guides/add-a-feature.md`）

`architect.md` G3 写「新增一个业务实体 ≤ 3 个文件 + 1 个迁移」，但没有清单。现代做法是把它变成可执行的 10 步：

| # | 步骤 | 产物 | 验证 |
|---|---|---|---|
| 1 | 定义领域词汇与不变量 | `glossary.md` 一行 + 3 条不变量 | 能回答"什么状态非法" |
| 2 | 建表（Drizzle schema） | `schema.ts` | 含 `organization_id`、`deleted_at`、`UNIQUE (organization_id, id)` |
| 3 | 生成迁移 + 手写 RLS/授权 | `NNNN_*.sql` | 照抄 `0001_auth_rls.sql:490-515` 的 DO 块，**不手写** |
| 4 | 加索引 | 迁移内 | 唯一约束必须是**部分索引**（`WHERE deleted_at IS NULL`） |
| 5 | 写 query（读） | `lib/<domain>/queries.ts` | 必带 `organization_id` 条件 |
| 6 | 写 action（写） | `lib/<domain>/actions.ts` | Zod + `requireOrgContext` + `assertPermission` + `withOrg` |
| 7 | 写页面 | `app/**/page.tsx` | RSC 直读，无客户端首屏请求 |
| 8 | 写集成测试 | `tests/*.test.ts` | 至少 3 条：正常、跨组织 0 行、viewer 写入被拒 |
| 9 | 更新 `status/implementation-status.md` | 一行状态 | 唯一状态更新点 |
| 10 | 跑 `pnpm check && pnpm test:coverage` | CI 绿 | fitness function 全过 |

**这份清单是本套文档里 ROI 最高的新增内容**：它把 G3 从"愿望"变成"流程"，而且是唯一一份"新人第一天就需要"的文档。

## 8. 迁移方案：两个选项

### 选项 A：最小可行重构（推荐，约 3 天）

只做 5 件事，不动 `data-model.md` 和 `api.md`：

| # | 动作 | 工时 | 收益 |
|---|---|---|---|
| 1 | 写 `README.md` 索引 + 4 条阅读路径 | 半天 | 190KB 从"平铺"变成"可导航" |
| 2 | `architect.md` 拆成 `architecture/` 下 6 个文件（按现有章节切，不改内容） | 1 天 | 单份从 37KB 降到 ~8KB，读者按需取 |
| 3 | 写 5 篇 ADR（§3-E 列出的） | 半天 | 保住"为什么没选 X"这类最贵的知识 |
| 4 | 新增 3 份 guide（`add-a-feature` / `runbooks` / `testing`） | 1 天 | 覆盖最高频的 3 类查询 |
| 5 | 删除 4 份文档的状态横幅，状态只留 `implementation-status.md` | 半小时 | 5 路同步 → 1 路 |

**不做**：目录大改、arc42 全章、C4 图重绘、隐私章节（后者建议单独立项，因为它要先做产品决策）。

### 选项 B：完整重构（约 2 周）

按 §6.2 的目录树全量迁移，含质量属性场景重写、威胁模型、隐私章节、fitness function 落地。

**建议**：**先做 A，把 B 拆成随功能推进的增量**。理由：文档重构的最大风险不是"做得不好"，是"做完就过期"。A 的 5 项都是**低过期率**的内容（索引、阅读路径、ADR、how-to 清单），B 里的场景与威胁模型应该跟着功能一起长，而不是一次写完然后烂掉。

## 9. 验收标准：怎么知道文档结构变好了

不谈"更清晰""更易读"这类不可测的形容词，只看 5 个可观察的事实：

| # | 验收标准 | 现在 | 目标 |
|---|---|---|---|
| 1 | 新人从零到改完一个字段并上线，需要问人几次 | 未知（无路径） | **0 次**（`add-a-feature.md` 覆盖） |
| 2 | 回答"为什么这么做"平均需要跳几次 | 2–3 次（ADR 表 → 正文 → 风险表） | **≤2 次**（ADR 直达） |
| 3 | 架构约束中，有多少条有 CI 在执行 | **0 条**（全部靠评审） | ≥5 条 |
| 4 | 同一个事实的权威位置数量 | 1–4 处（见 §5.3） | **恒为 1** |
| 5 | 一次实现推进需要更新几份文档的状态 | 5 份 | **1 份** |

第 3 条最关键：**没有被执行的架构约束，本质上只是建议。** 这个项目目前的所有边界规则（分层、模块依赖、文件长度、禁止 `process.env`）都处于"建议"状态——而 `architect.md` 里写着它们"由 Biome 拦截"。
