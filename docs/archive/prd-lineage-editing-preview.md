## 1. 文档概述

### 1.1 背景与要解决的问题

M1 把「录入」做完了：左侧谱系管理、欧式书本画布、世系表、检查器、四种录入方式、增删改移、字辈、搜索定位都已可用（`FR-LIN-1`~`FR-LIN-13` 基本 ✅）。

但 M1 的已知缺口 1 仍然成立：**用户录完不知道成品长什么样**。人丁信息被填进表单，家族却看不到「这个人会在谱书里排成什么样」；编谱人心里没有底，就不敢继续录。谱系录入是几十到几千人的重复劳动，用户每录十个人就会问一次「我录的对不对」，而 M1 的回答是「等谱书模块做完再说」。

同时，M1 缺三件家谱业务的刚需能力：**结构性编辑**（拆支 / 挂接 / 分房）、**录入效率**（快捷键、右键菜单、撤销、生僻字）、**数据带走**（导出）。

> **已落地 vs 本文件新增**：谱系创建、始祖录入、四种亲属添加、删除（软删）在 M1 已有实现（[实现状态](./implementation-status.md) §3.4），本文件对它们的要求是「入口一致、行为可测、补上撤销」，不是从零重写；实时预览、撤销、`node.birth_place` 一列是 M1 的新增，三档详略、快捷键体系、以及 §3.9 之后的全部 M2 块也是新增。

### 1.2 目标

| # | 目标 | 判定方式 | 里程碑 |
|---|---|---|---|
| G1 | 用户能独立完成一条完整闭环：**建谱系 → 录首节点 → 加亲属 → 边录边看成品 → 删除** | 3 名内测用户各独立录完 1 支 20 人以上世系，全程无需口头指导 | M1 |
| G2 | 录入时**同时看到成品**，预览随编辑实时更新（无手动刷新） | 输入任一字段后 ≤ 100ms 预览更新 | M1 |
| G3 | 世系结构可在画布上直接改（拆支 / 挂接 / 分房），不用删了重录 | 三类操作全程不丢失已录入的人丁信息 | M2 |
| G4 | 承嗣关系（过继 / 嗣子 / 兼祧）能被**记录**而非被压平成「亲生」 | 界面可录入 6 类承嗣，与 `family_child.parentage_type` 的 6 个取值一一对应；「传统承嗣」下的嗣子 / 兼祧 / 入赘由人丁备注保留原词（§5.2） | M2 |
| G5 | 用户能把录入的数据**带走**，不被锁定 | 单支世系导出为 GEDCOM 7 文件，至少 2 个第三方工具可导入（[ADR 0017](./decisions/0017-single-branch-export-gedcom7.md)） | M2 |

### 1.3 范围与里程碑

**M1 只保留必须的闭环**，其余全部后置。这条边界是硬约束：M1 的目标是「让用户能把一支世系录完并看到成品」，不是「把参考产品的功能补齐」。

| 阶段 | 范围 | 为什么在这个阶段 |
|---|---|---|
| **M1（必须闭环）** | 建谱系（三入口）→ 录首节点 → 加亲属（父母 / 子女 / 配偶 / 兄弟姐妹）→ 边录边看成品（实时预览，固定一套字段）→ 删除（含撤销）<br>外加闭环必需的支撑：信息面板核心字段、自动保存、检查器三页签、撤销 | 缺任何一环，闭环就断：没有首节点录不进人，没有加亲属录不完一支，没有预览就是缺口 1，没有删除就录错了改不了 |
| M2 结构编辑 | 拆支、挂接与承嗣（含双父）、分房与房支管理 | 这些是「改结构」的能力；M1 阶段用户可以先删了重录，代价可接受 |
| M2 数据带走 | 单支世系导出（GEDCOM 7） | 已由 owner 批准从 M3 提前（[ADR 0017](./decisions/0017-single-branch-export-gedcom7.md)） |
| M2 录入效率 | 快捷键体系、右键菜单、三档详略模式（含偏好表）、排序上移下移、统计口径统一 | 都是加速器与观感，不是闭环必需；M1 用现有入口也能把一支录完 |
| M2 录入增强 | 收藏、别名多值、6 个扩展字段、头像、造字工具、整页预览、谱系数显示 | 提升体验，不阻塞闭环 |
| 范围外 | 见 §1.3.1 | — |

#### 1.3.1 明确不做

- **不做**成书排版、PDF 导出、分享链接——M2 其余部分与 M3（[产品需求](./prd.md) §6.4）。
- **不做**实时协同、编辑锁（M2 后续块）。
- **不做** GEDCOM **导入**（解析问题比导出难一个数量级，用户量不足，[产品需求](./prd.md) §6.2）。
- **不做**全库数据导出（合同 + 手工 `pg_dump` 兜底，与单支导出不是一回事）。
- **不做**多谱系联宗、谱系合并、跨谱系引用（[产品需求](./prd.md) §9 Q5 未决）。
- **不做**谱系配额上限（视频的「谱系数 3/99」是参考产品的商业配额）。
- **不做**智能家谱 / 电子家谱 / 家族微站（视频里是同一控制台的另外三个产品，与本产品无关）。

### 1.4 术语

沿用 [产品需求](./prd.md) §2，本文件新增或收窄以下词：

| 词 | 定义 | 备注 |
|---|---|---|
| 首节点 / 始祖 | 一个谱系的第 1 代血亲，`generation = 1`、`path` 深度 0 | 与 `FR-LIN-2` 同义，界面文案统一用「始祖」 |
| 世系起点 | 因拆支产生的新根：无父节点、`generation` 重算为 1，但**不是**谱系第一个节点 | 一个谱系只有一个始祖，可以有多个世系起点；见 `FR-LEP-42` |
| 行传 | 谱书中一个人丁的条目正文（生平记述） | 对应 `node.biography`；界面页签与字段名统一用「行传」，「生平描述」「传记」不再单列（§3.3） |
| 房支 | 以某个人丁为起点的一支后裔，有房支名称 | 本文件新增概念，见 §5.1 |
| 分房 | 把某个人丁标记为房支起点 | 一个谱系可有多支，可嵌套（§3.11） |
| 拆支 | 断开人丁与其父节点的关系，该子树脱离原世系 | 与 `FR-LIN-8`（改挂）不同：拆支后**没有父节点** |
| 挂接 | 给（无父或需换父的）人丁指定父节点，可带承嗣类型 | 与 `FR-LIN-8` 的区别见 §3.10 |
| 承嗣类型 | 该人丁与父节点的父子关系性质，共 6 类：亲生 / 过继 / 收养 / 继子 / 传统承嗣（嗣子·兼祧·入赘）/ 不详 | 与 `family_child.parentage_type` 的 6 个取值一一对应；原词（「嗣子」「兼祧」「入赘」）进人丁备注 |
| 实时预览 | 编辑区右侧随录入即时渲染的成品条目视图 | 不是谱书排版，是「条目样式」 |
| 信息详略模式 | 实时预览中条目显示多少字段：完整 / 简化 / 至简 | 每用户每谱系记住选择；M1 固定一套，切换是 M2 |
| 造字工具 | 输入常用字库外的生僻字的取字面板 | 家谱人名的高频痛点；视频只可辨按钮名，检索方式为本产品设计（§3.13） |

### 1.5 需求来源与证据分级

本文件的输入是**一段参考产品演示视频**，不是客户访谈。视频只能看到「界面长什么样、操作怎么走」，看不到「为什么这么设计」。因此每条需求都标注来源，分三级：

| 级别 | 含义 | 标注写法 |
|---|---|---|
| A | 视频画面或旁白**可辨**（界面文案、键位、流程顺序） | 「视频」 |
| B | 视频露出**动作或命令名**，但键位、字段、交互细节是本产品决定的 | 「动作=视频，键位/细节=设计」 |
| C | 视频里**没有**，本产品为闭环或工程质量补的 | 「设计」 |

评审发现「把设计写成观察」是本文件最容易犯的错（v0.2 曾有 3 处），因此凡标「视频」的都要能在帧或旁白里指出来。

## 2. 用户与场景

沿用 [产品需求](./prd.md) §1.2 的三类用户：**修谱主事人**（对应 `owner` / `admin`）、**族内协作者**（对应 `editor`）、**修谱工作室**（两类角色都用）。本文件主要服务前两类在录入场景下的行为；`viewer`（审核者 / 顾问）只涉及只读的实时预览（§6）。

| # | 场景 | 触发 | 期望结果 | 里程碑 |
|---|---|---|---|---|
| S1 | 新建谱系，开始录入 | 决定给某支家族建谱 | 三种入口任选其一，30 秒内进入空画布并开始录始祖 | M1 |
| S2 | 连续录入一支世系 | 手上有老谱或族人口述 | 连续加子女、加配偶、改信息，预览同步更新（M2 起可全程键盘操作） | M1 |
| S3 | 录错了要回退 | 发现加错人或整支不该存在 | 30 秒内一键撤销；超时则删除并重新录入 | M1 |
| S4 | 校对成品观感 | 录了几十人之后 | 打开预览，确认谱书里的条目样式能接受（三档详略切换在 M2） | M1 |
| S5 | 老谱上写着「出继某某为嗣」 | 录入到过继条目 | 能挂到嗣父名下，同时保留生父信息与承嗣类型 | M2 |
| S6 | 一支人丁要拆出去单独成谱 | 家族分支独立修谱 | 拆支后该子树自成一系，世次重算，历史信息不丢 | M2 |
| S7 | 族人要一份能带走的数据 | 交给别的软件或存档 | 导出单支世系 GEDCOM 7 文件，第三方工具可导入 | M2 |

## 3. 功能需求

`FR-LEP-01`~`FR-LEP-66` 在本节定义；`FR-LEP-67`/`68` 在 §4.3、`FR-LEP-69`/`70` 在 §6。编号按文档顺序递增、无缺口。每条都标了里程碑（M1 / M2），M1 集合即 §1.3 的闭环。

### 3.1 建谱系（M1）

视频演示了三种入口；设计上**三者复用同一个创建对话框与同一个 Server Action**，只是入口位置不同。

| # | 入口 | 位置 | 上下文默认值 |
|---|---|---|---|
| E1 | 控制台「我的云谱空间」 | `/dashboard/org/{orgSlug}` 的云谱空间列表区（`/dashboard` 的「最近访问」提供同一入口） | 最近访问的云谱空间；分类默认「默认分类」 |
| E2 | 云谱空间概览 | `/dashboard/project/{ref}` 快捷操作区 | 当前云谱空间；分类默认「默认分类」 |
| E3 | 谱系编辑器列表页 | `/dashboard/project/{ref}/lineages` 顶部按钮 | 当前云谱空间；分类取左侧树当前选中节点 |

> 导航层级以 [产品需求](./prd.md) §4.2 为准：`/dashboard` 是「我所属的组织列表 + 最近访问」，云谱空间列表在组织页，谱系编辑器在 `/dashboard/project/{ref}/lineages`。E1 不落在 `/dashboard` 本身。

- `FR-LEP-01`（M1）三个入口都能打开创建对话框；对话框字段、校验、错误提示完全一致。来源：视频（三个入口逐个演示）。
- `FR-LEP-02`（M1）对话框含「新建到分类文件夹」选择器；云谱空间下无任何分类时，系统自动建「默认分类」并在同一事务内挂载，**不出现「先建谱系再补分类」的两步操作**（`FR-LIN-1` 已实现此语义，此处只要求入口一致）。来源：视频（旁白「若没有分类文件夹，系统会自动选择默认分类」）。
- `FR-LEP-03`（M1）创建成功后直接进入该谱系的画布，并自动弹出「录入始祖」（`FR-LIN-2` 行为保持）。来源：视频。
- `FR-LEP-04`（M1）列表页在创建后回到列表时，新谱系出现在所选分类下，`node_count = 0`。来源：视频（谱系列表页表头含「总人数(个)」）。

### 3.2 录首节点（M1）

- `FR-LEP-05`（M1）空谱系进入画布时自动弹出始祖录入；表单必填 **姓氏**（默认继承谱系姓氏，可改）、**谱名**、**世次**（默认 1，可改）；其余字段可空。来源：字段=视频（旁白「首节点需要填写姓氏、谱名、世次，其他可选择性填写」），默认值（姓氏继承谱系、世次 1）=设计。
- `FR-LEP-06`（M1）提交后节点落位第 1 代列，画布显示「始祖」徽标；`node_count` 变 1；右侧检查器自动展开「信息」页签并聚焦下一个空字段。来源：选中态徽标=视频（「首节点: 龙文强(第1代)」），自动展开与聚焦=设计。
- `FR-LEP-07`（M1）始祖不可删除（`FR-LIN-7` 已有保护，此处要求提示文案统一）。**拆支保护属 M2**：拆支上线后始祖同样不可拆支，提示「始祖是谱系的根，不能拆支；如需改结构请用「挂接」调整其子代」——M1 没有拆支入口，这条规则在 M2 生效，不要写进 M1 验收。来源：设计（视频未演示删除始祖）。
- `FR-LEP-08`（M1）一个谱系**允许**存在多个无父节点的血亲（见 §3.9 拆支 `FR-LEP-42`）；只有 `generation = 1` 的第一个节点显示「始祖」徽标，其余显示「世系起点」。来源：设计（视频未展示多根场景）。

### 3.3 人丁信息（M1 核心字段，M2 扩展）

视频的信息面板可见 20 个字段，但**分组标题在视频中不可见**（全片没有「卒」「葬」「文化程度」「职业」等分组字样），分组是设计。M1 只上「让预览能渲染出成品」所需的字段，其余后置。

- `FR-LEP-09`（M1）M1 字段集与分组顺序（**分组为设计**）：**基本信息**（姓氏、谱名、性别、健在/已故）→ **出生**（出生日期、出生地）→ **卒葬**（卒日期、葬地）。这 8 个字段是 §3.5 预览模板能渲染出条目的最小集合。**「出生地」在 `node` 上没有现成列**（只有 `burial_place`），M1 为此加一列 `birth_place text`（可空，加法迁移，§5.6）。**行传不放进信息页签**：它在独立的「行传」页签里编辑（`FR-LEP-11`、`FR-LEP-31`），同一列 `node.biography` 不能有两个编辑器——v0.2 把「生平描述」「传记」「行传」当三个名字塞进一个面板，是上一版的缺陷。**生平**分组在 M1 为空，M2 由扩展字段（`FR-LEP-62`）填充。来源：字段=视频，分组与 M1 取舍=设计。
- `FR-LEP-10`（M1）日期字段支持「选择」与「直接输入」两种方式，直接输入接受 `1978`、`1978-02`、`1978-02-08`、`约 1978`、`民国二十七年` 等写法；原文存 `node.birth_text` / `node.death_text`，能解析出的年份写 `node.birth_year` / `node.death_year`；无法解析时保留原文并标黄提示，**不阻塞保存**。不引入 `event` 表的 `date_qualifier` / `calendar`（那要等事实层读写切换，§5.2）。来源：视频（字段标注「选择或者输入日期」），解析规则=设计。
- `FR-LEP-11`（M1）「行传」页签是 `node.biography` 的唯一编辑器：多行文本，显示字数计数（「N 个字」），上限 2000，达上限时计数变红并禁止继续输入。信息页签只读展示行传前 60 字的摘要并给「去编辑」跳转，不提供第二个编辑框。来源：页签与字数计数=视频（「5个字」「22个字」可辨），上限值与唯一编辑器=设计。
- `FR-LEP-12`（M1）保存为自动保存（停止输入 1.5 秒），页签右上显示「已保存 / 保存中 / 保存失败（重试）」；保存失败不丢失本地内容，重试成功后提示消失。来源：设计。
- `FR-LEP-13`（M1）并发语义沿用既有决策：last-write-wins，**不做版本检测**——`node` 没有 `version` 列，M1 不为此加列。能检测的只有「人丁已被删除」：写入影响 0 行时提示「该人丁已被删除，内容未保存」。两人同时编辑同一人丁时后保存者静默覆盖，这是 [产品需求](./prd.md) §6.3 缺口 3 的已知代价，由 M2 的编辑锁块解决；未保存的输入只留在页面内存，刷新即丢失（**不做**草稿持久化）。来源：设计（沿用既有决策）。
- `FR-LEP-14`（M1）未选中人丁时检查器显示空态：「从画布上选择一位人丁开始录入」，不显示空表单。来源：设计。

### 3.4 加亲属（M1）

- `FR-LEP-15`（M1）在选中节点上可添加：**父母**、**子女**、**配偶**、**兄弟姐妹**。M1 的入口是画布选中态的操作区与检查器按钮（沿用现有交互）；右键菜单与快捷键是同一批操作的加速入口，随 M2 的录入效率块上线（§4.2、§4.3），届时三条路径行为必须一致。来源：命令与键位=视频（右键菜单与底栏逐帧可辨），M1 入口=设计。
- `FR-LEP-16`（M1）添加对话框只要求**姓名**一项必填，其余字段可后补；确定后新节点立即出现在画布正确位置并成为选中态，检查器切到「信息」页签。来源：视频（旁白「填写好配偶的姓名即可添加」），落位行为=设计。
- `FR-LEP-17`（M1）添加**父母**为 M1 缺失能力：给一个已有父节点的血亲添加父母时，父节点为**占位新建**——`name` / `full_name` 取对话框输入的姓名（`full_name` 必填），`sex` 默认 `0`（男）并在信息面板顶部标注「性别待确认」，`generation = 子节点 generation − 1`，`path` 由祖先链推导。原父节点关系默认**替换**（不做承嗣式保留，那是 M2 的 `FR-LEP-46`）；替换前的 `parent_id` 由撤销凭据保留，30 秒内可回退（`FR-LEP-19`）。来源：动作=视频（右键「添加父母 Alt+H」），占位取值与替换规则=设计。
- `FR-LEP-18`（M1）兄弟姐妹继承同一父节点、同世次；无父节点时提示先添加父母（默认自动创建占位父节点）。来源：设计。
- `FR-LEP-19`（M1）**撤销人员添加**：添加成功后出现撤销提示「已添加 XXX · 撤销」，点击回滚**本次操作新增的行**（人丁 + 关联的配偶/家庭边）；`Ctrl/Cmd+Z` 同效。撤销窗口 **30 秒**（与删除共用同一窗口，§7 B6）。**范围限定**：只回滚本次新增的行 + 本次被替换的 `parent_id`（凭据里携带 `previousParentId`），不回滚其它并发修改；单次操作新增/删除超过 **200** 行时不提供撤销（凭据过大），提示「本次操作人数过多，不支持撤销」。提示的位置与样式（右下角 toast、倒计时环）是设计，视频只露出命令名「撤销人员添加」。来源：命令=视频，交互与范围=设计。撤销的存储见 §5.4。
- `FR-LEP-20`（M2）**排序上移 / 下移**（`Alt+<` / `Alt+>`）：调整同父兄弟的显示顺序，落 `node.sort`；配偶在同一血亲下独立排序。来源：视频（键位可辨）。

### 3.5 边录边看成品：实时预览（M1，核心）

这是本文件的重点，也是 M1 缺口 1 的直接解法。

- `FR-LEP-21`（M1）右侧「预览」页签实时渲染**当前选中人丁**在谱书中的条目样式。渲染使用与未来谱书**同一套字段顺序与文案模板**，模板在本文件冻结如下（这就是「成品的样子」的判定基线，不依赖尚未开工的谱书渲染块）。来源：动作=视频（右侧预览页签），模板=设计。

  | # | 模板行 | 完整模式 | 简化模式 | 至简模式 |
  |---|---|---|---|---|
  | 1 | 世次 + 谱名 | `第N世 龙文强` | ✅ | ✅ |
  | 2 | 别名 | `字子美，号云溪` | — | — |
  | 3 | 生卒 | `生于 1978 年，卒于 2050 年` | ✅ | ✅ |
  | 4 | 出生地 / 葬地 | ✅ | — | — |
  | 5 | 配偶 | `配 王氏` | ✅（仅姓名） | — |
  | 6 | 子女 | `子三：文明、文星、文组` | ✅（仅姓名） | — |
  | 7 | 行传 | 全文 | — | — |
  | 8 | 文化程度 / 职业 | ✅ | — | — |

  > M1 只落第 1、3、4、5、6、7 行，且**固定按一套模式渲染**（不做三档切换，三档与偏好表是 M2，见 `FR-LEP-23`）；第 2 行依赖 M2 的别名多值，第 8 行依赖 M2 的扩展字段。表格整体冻结，M2 补齐后不改变行序与文案。

- `FR-LEP-22`（M1）预览随编辑**即时**更新：任一字段输入后 ≤ 100ms 反映到预览，不发起网络请求（纯客户端渲染，数据来自当前表单状态）。来源：视频（旁白「同时可进行实时连线预览」）。
- `FR-LEP-23`（M2）「偏好设置」页签提供**信息详略模式**三档（视频可辨「完整模式 / 简化模式 / 至简模式」），作用于预览，字段取舍见上表。M1 不切换模式，固定渲染上表 M1 行集合。来源：视频。
- `FR-LEP-24`（M2）详略模式的选择按「用户 × 谱系」记忆（服务端存偏好，跨设备一致），默认「简化」，存储见 §5.3。来源：动作=视频（偏好设置页签），粒度=设计（粒度本身仍待确认，§10 Q-LEP-5）。
- `FR-LEP-25`（M1）预览对空字段的处理：不渲染空字段行，不留占位符；行传为空时显示「暂无行传」灰字（M2 起仅完整模式显示该行）。来源：设计。
- `FR-LEP-26`（M1）预览为只读，点击预览中的字段不进入编辑；需要编辑时回到「信息」页签。来源：设计。
- `FR-LEP-27`（M1）预览、世系表、云谱空间概览三处的姓名与世次必须一致，取同一份数据（不在页面内各拼一遍）。来源：设计。

> **为什么预览不等同于谱书渲染**：谱书排版依赖版式与字体（M3），本文件的预览只保证「条目内容与顺序」正确，不保证分栏、字号、页眉页脚。冻结上表的意义是：预览的正确性可以被测试断言，而不是「等谱书做出来再对齐」。

### 3.6 删除（M1）

- `FR-LEP-28`（M1）选中人丁 → 右侧工具条「删除」（M2 起增加右键菜单 / `Delete` 入口，§4.2、§4.3）→ 确认对话框列出影响：「将删除 X 及其 N 位后代、M 位配偶，共 K 人」。视频的提示语只有「注意 删除的人物节点如有后代节点，会连同其后代节点一起删除」，**人数统计是本产品设计**（更好，且可测）。来源：动作=视频，人数统计=设计。
- `FR-LEP-29`（M1）删除为一次事务内的**整组软删**（子树 + 配偶），`node_count` 同步；无回收站界面（M2 回收站为后续块），但删除后 30 秒内可撤销（与 `FR-LEP-19` 同一套撤销机制、同一窗口，存储见 §5.4）。来源：视频（旁白说明连带删除），撤销=设计。
- `FR-LEP-30`（M1）始祖删除仍被拒绝（`FR-LIN-7` 保持）；被谱文引用的人丁删除时提示「有 N 处引用，删除后引用失效」（[产品需求](./prd.md) `FR-BOOK-4` 的编目只引用谱系与谱文，不引用单个人丁，所以引用检查只查谱文）。来源：设计。

### 3.7 编辑器布局与交互基础设施

本节的 `FR-LEP-31`、`32` 是 M1（页签与工具条是闭环的容器）；`FR-LEP-33`~`36` 是 M2 的录入效率块（快捷键与右键菜单），列在此处是为了让交互规格集中在一节。

- `FR-LEP-31`（M1）右侧检查器为**三页签**：**信息 / 行传 / 预览**；M2 增加第四个「偏好设置」（`FR-LEP-23`）。页签切换不丢失未提交的表单内容。视频该位置有四个页签，首个页签在多数帧 OCR 读作「别名」、「信息」只出现在字幕里；本产品定为「信息」（内容含别名，§3.3），命名待确认（§10 Q-LEP-7）。来源：页签=视频，M1 只上三个与命名=设计。
- `FR-LEP-32`（M1）右侧竖向工具条按里程碑逐项上线：M1 只有**删除**；M2 补**挂接 / 拆支 / 分房**。未选中节点时按钮禁用并给出 tooltip 说明原因；`viewer` 隐藏整条工具条（§6）。来源：视频（四个按钮），上线节奏=设计。
- `FR-LEP-33`（M2）底部快捷键栏常驻，展示当前节点的亲缘导航入口与对应键位；窄屏（< 1280px）折叠为「快捷键」按钮弹出面板。来源：视频（底栏「当前节点·配偶·兄弟·子女·父母」）。
- `FR-LEP-34`（M2）左侧栏在 1024px 以下可折叠，折叠状态记入 `localStorage`，不影响画布交互。来源：设计。
- `FR-LEP-35`（M2）快捷键在输入框聚焦时不生效（除 `Esc` 与 `Ctrl/Cmd+Z`）；`?` 打开快捷键总览面板。来源：设计。
- `FR-LEP-36`（M2）快捷键总览面板（`?` 打开）只列**本文件已定义行为**的命令：添加父母（`FR-LEP-17`）、添加子女 / 配偶 / 兄弟姐妹（`FR-LEP-16`）、撤销（`FR-LEP-19`）、删除（`FR-LEP-28`）、收起/展开节点（§4.2）、健在/已故与男/女切换（§3.3 字段）、搜索定位（§3.7 搜索）、上下左右切换节点（§4.2）、排序上移/下移（`FR-LEP-20`）。视频面板里还出现「生成世序」「称谓」「切换定位」「编辑节点」「新增首节点」等条目，这些命令在本产品没有独立语义（世次是存储列、不「生成」；「称谓」无字段落点），**不进入本文件**，待产品确认后再补（§10 Q-LEP-12）。所有快捷键都要有非键盘入口（底部栏、右键菜单、`?` 面板），不做「只有老手知道」的隐藏操作。来源：条目=视频，取舍=设计。

### 3.8 统计口径（M2）

视频的云谱空间概览有「谱系(个) / 总人数 / 男性人数 / 女性人数 / 健在人数 / 已故人数」。本产品概览已有对应区域，本节只约束**口径**。

- `FR-LEP-37`（M2）统计只计未软删的人丁；配偶计入总人数与性别计数；`健在 + 已故 = 总人数`，在世状态取 `node.is_alive`（**布尔，没有第三态**）。不要用 `person.living_status`——事实层那张表目前没有任何读写路径（[实现状态](./implementation-status.md) §2），拿它算统计会得到空值。来源：字段=视频，口径=设计。
- `FR-LEP-38`（M2）口径与实时预览、世系表完全一致，同一份聚合函数，不在页面内各算一遍。来源：设计。

### 3.9 拆支（M2）

- `FR-LEP-39`（M2）选中人丁 → 右侧工具条「拆支」→ 二次确认对话框（说明「将断开与父节点 X 的关系，该人丁及其后代成为独立世系起点，世次从 1 重新计算」）→ 确定完成。来源：视频（旁白完整描述流程）。
- `FR-LEP-40`（M2）拆支后：该节点 `parent_id = NULL`，子树全部人丁的 `path` / `generation` 按新根重算，`node_count` 不变；原父节点失去该子树。来源：设计。
- `FR-LEP-41`（M2）拆支不删除任何数据：人丁信息、配偶、承嗣记录、房支归属全部保留；操作可撤销（`Ctrl/Cmd+Z`，30 秒内）。撤销**不依赖快照表**：拆支只改了 `parent_id` 与派生列，客户端持有原父节点 id，撤销时写回 `parent_id` 并按祖先链重算 `path` / `generation`（§5.4 的同一套「先写后补偿」，不新建表）。来源：设计。
- `FR-LEP-42`（M2）拆支后若该子树带有房支标记，房支**仍属同一谱系**（拆支只断开 `parent_id`，不迁移 `lineage_id`），房支名称不变、起点人丁不变；房支管理列表里该房支的「分房节点」仍指向原起点人丁，但该人丁已不再是原世系的一部分——这是 M2 需要产品裁决的边界（§10 Q-LEP-13）。来源：设计。
- `FR-LEP-43`（M2）撤销拆支时，`path` / `generation` / 房支归属一并恢复到操作前的值；撤销窗口关闭后，界面上不再提供「合支」入口（见 §10 Q-LEP-2）。来源：设计。

### 3.10 挂接与承嗣（M2）

- `FR-LEP-44`（M2）选中人丁 → 右侧工具条「挂接」（或右键「挂接到父级其他节点」）→ 对话框含：**父级节点选择器**（搜索 + 最近节点）、**备注** → 保存。**承嗣类型字段是本产品设计**：视频的对话框只有父级选择器与备注，承嗣类型只出现在旁白里（「挂接的功能还可用于嗣子、过继、兼祧的父子关系的处理」）。来源：对话框=视频，承嗣字段=设计。
- `FR-LEP-45`（M2）承嗣类型枚举 **6 类**，与 `family_child.parentage_type` 一一对应：`亲生`→`birth`、`过继`→`adoptive`、`收养`→`foster`、`继子`→`step`、`传统承嗣`→`traditional`、`不详`→`unknown`。**不做** 1 对多的枚举：`traditional` 一个值不硬拆成「嗣子 / 兼祧 / 入赘」三个界面值，这三者的原词写进人丁备注（`node.remark`），因为 `family_child` 没有备注列、`parentage_type` 也不该被界面枚举牵着扩（§5.2）。来源：6 类映射=数据模型既有 CHECK，界面取值=设计。
- `FR-LEP-46`（M2）承嗣关系**保留生父**：过继 / 嗣子 / 兼祧的人丁同时拥有「生父」与「嗣父」两条父子边，它们属于**两个不同的家庭**（`family` 行不同），不是同一家庭里的两条边——后者被 `uk_family_child_family_person` 禁止。`node.parent_id` 指向**主父**（决定谱系路径与世次）。界面在信息面板显示「生父：X · 嗣父：Y」。来源：设计（视频未展示双父录入）。
- `FR-LEP-47`（M2）挂接对话框的父级选择器排除：自身、自身的后代（防成环）、已删除节点；选中非法目标时按钮禁用并说明原因。来源：设计。
- `FR-LEP-48`（M2）挂接成功后 toast「挂接成功」，画布重新布局，该子树世次重算；若承嗣类型非亲生，节点卡片显示承嗣徽标（如「嗣」）。来源：toast=视频（旁白与画面「挂接成功!」），徽标=设计。
- `FR-LEP-49`（M2）挂接与 `FR-LIN-8`（拖拽改父）是同一底层能力：拖拽改父等价于承嗣类型 = 亲生的挂接；两者共用同一个事务服务，不各写一套。来源：设计。

### 3.11 分房与房支管理（M2）

- `FR-LEP-50`（M2）选中人丁 → 右侧工具条「分房」→ 对话框含**分房节点**（默认当前选中人丁，可改选）、**房支名称**（必填，≤24 字，同谱系内唯一）、**备注**（≤200 字）→ 确定完成。视频的对话框除房支名称与备注外，确实还有一个分房节点选择器；另有一处「世系 / 谱书」下拉在 OCR 里只能部分辨认，存疑（§10 Q-LEP-8）。来源：视频（对话框字段可辨），必填与长度=设计。
- `FR-LEP-51`（M2）一个谱系可有多个房支，**允许嵌套**（大房下再分小房）：房支成员 = `root_node_id` 的子树，一个节点的房支归属取**最近祖先房支**；服务端拒绝成环（新起点的房支不得是自身的祖先房支）。视频没有展示嵌套场景，这是设计。来源：设计。
- `FR-LEP-52`（M2）顶部工具栏「房支管理」打开对话框：表格列出房支名称 | 分房节点（世次 + 姓名）| 人丁数 | 操作；操作为「直达」（定位到该房支起点并高亮整支）与「删除房支」。「人丁数」列是设计（视频未可辨），但它与 §3.8 的统计口径必须一致。来源：对话框=视频，列与操作=设计。
- `FR-LEP-53`（M2）删除房支只删标记，不删人丁；删除后该支人丁仍在原世系中，只是不再属于任何房支（若父房支存在则回落到父房支归属）。来源：设计。
- `FR-LEP-54`（M2）画布上房支起点节点显示房支徽标；左侧栏可选「按房支分组」视图（可后置）。来源：设计。

### 3.12 世系导出（M2，已批准）

- `FR-LEP-55`（M2）右键菜单与顶部「导出」提供：导出该人丁的**溯源及后代世系**文件、**包含兄弟**的版本、以及「复制到剪贴板」。视频的菜单项可辨「导出…世系 GEN 文件」「复制溯源及后代世系」「（包含兄弟）」三种变体。来源：视频。
- `FR-LEP-56`（M2）导出格式为 **GEDCOM 7.0**（FamilySearch 标准，UTF-8 编码，文件扩展名 `.ged`）。**不是 5.5.1**：5.5.1 是 1999 年 ANSEL 字符集时代的产物，对中文姓名与生僻字需要大量私有扩展标签；GEDCOM 7 用 UTF-8 + 显式 payload 类型表达同样语义。视频界面 OCR 显示为「GEN 文件」，疑为 GEDCOM 的显示差异（§10 Q-LEP-3）。
  **可判定的 7.0 特征（验收就查这几条）**：① 扩展名 `.ged`、UTF-8 无 BOM；② `HEAD.GEDC.VERS` 为 `7.0`；③ 行语法 `<level> <TAG> [<xref>] <payload>`，行首 `@` 转义为 `@@`；④ **不出现 `CHAR`、`CONC`**（7.0 已取消，超长行传用 `CONT` 续行）；⑤ 承嗣等扩展信息走 `TYPE` / `NOTE` 的标准 payload，不发明私有标签。来源：格式=owner 决策 + [ADR 0017](./decisions/0017-single-branch-export-gedcom7.md)，范围与判定项=设计。
- `FR-LEP-57`（M2）导出为只读操作，不影响数据；导出走 `content.read`，`viewer` 可用（§6）。来源：设计。
- `FR-LEP-58`（M2）导出前校验并给出报告：无法表达的字段（承嗣原词、自定义类型）按 GEDCOM 7 的 `TYPE` payload 或 `NOTE` 承载；仍无法承载的，在导出结果里列出「N 处已降级」，不静默丢弃。来源：设计。
- `FR-LEP-59`（M2）导出只做**单支世系**（选中人丁的溯源 + 后代子树），不做全库导出、不做导入。整库导出仍走合同 + 手工 `pg_dump`（[产品需求](./prd.md) §6.2）。来源：设计（[ADR 0017](./decisions/0017-single-branch-export-gedcom7.md) 的范围收窄）。

### 3.13 录入增强（M2）

- `FR-LEP-63`（M2）头像：允许上传（单张 ≤ 2MB，jpg/png/webp），未上传时显示姓氏首字占位块。**媒体上传依赖 M2 的媒体块**，落 `node.avatar_media_id`（[数据模型](./data-model.md) §13.2 已预告该列），本节只要求信息面板留出位置与占位态。来源：视频（「添加头像」），能力=设计。

- `FR-LEP-65`（M2）**整页预览**：预览页签顶部提供入口，切到只读的全屏成品视图：范围为**该谱系全部未软删血亲人丁**，按世次升序、同世次按 `node.sort` 排列，配偶紧随其血亲；`Esc` 退出并回到画布选中态。来源：设计。

## 5. 数据需求

> 表结构以 [数据模型](./data-model.md) 为唯一来源。本节只声明**需要新增/变更什么**与**为什么**，列清单是「待写入 [数据模型](./data-model.md) §6.x 并在 §13.2 登记的候选」，不构成表结构事实来源；实施前必须先落文档、再出迁移。
> 小节按「对象」分组，里程碑写在每个小节标题里。**M1 只需要 §5.4（撤销存储，不建表）+ §5.6 里的一列 `node.birth_place`**；§5.1、§5.2、§5.3、§5.5 都是 M2。

### 5.1 新增：`branch`（房支，M2）

房支是「以某个人丁为起点的一支后裔」的**标记**，不是独立存储的树。成员通过 `root_node_id` 的子树推导，避免与人丁表双写导致不一致。

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | uuid | 主键 `uuidv7()`，与全库一致 |
| `organization_id` / `project_id` | uuid | 租户列与租户内唯一键 |
| `lineage_id` | uuid | 所属谱系 |
| `root_node_id` | uuid | 分房节点；同谱系内唯一（部分唯一索引，`deleted_at IS NULL`） |
| `name` | text | 房支名称，≤24 字；同谱系内唯一 |
| `notes` | text | 备注，≤200 字 |
| `created_at` / `created_by` / `updated_at` / `deleted_at` | | 公共列 |

- 需要 RLS + 复合外键到 `lineage (organization_id, id)` 与 `node (organization_id, id)`。
- 房支**不**在 `node` 上加冗余列：一支的成员是推导出来的，加了列就要维护一致性（`node_count` 的教训）。
- 嵌套由 `FR-LEP-51` 的「最近祖先」规则表达，**不需要** `parent_branch_id` 列，也就不会出现环——环只可能在「起点的房支是其祖先房支」时出现，服务端按祖先链校验即可。

### 5.2 承嗣类型落点（M2）

现有 `family_child.parentage_type` 已支持 `birth / adoptive / foster / step / traditional / unknown`，**不需要新表、不需要新列**。需要的是三件事：

1. 界面 6 类 → 列的 1:1 映射（§3.10 `FR-LEP-45`），不做 1 对多。
2. **双父靠两个家庭表达**：`uk_family_child_family_person (organization_id, family_id, person_id) WHERE deleted_at IS NULL` 只禁止「同一家庭里同一人丁出现两次」。生父家庭与嗣父家庭是两个 `family` 行，两条边各自合法。`family_child.is_primary` 的含义是**主父母家庭**（再婚场景下选哪一家作展示口径），**不是**生父/嗣父标记；`node.parent_id` 与 `is_primary = true` 的家庭对齐，决定谱系路径与世次。
3. 「传统承嗣」内部的嗣子 / 兼祧 / 入赘原词写进 `node.remark`（§5.6 新增列），不扩 `parentage_type`。

> 与 [数据模型](./data-model.md) §6.7 的「回填只写 `birth`」一致：回填的旧数据全部是亲生，新录入才带承嗣类型。**前置依赖**：承嗣类型的录入与展示要走 `family_child`，而事实层当前读写全部走 `node`（[实现状态](./implementation-status.md) §2 的读写切换计划尚未写）。因此本块必须先补 `family_child` 的查询函数与写 Action，否则 `FR-LEP-46` 的双父展示没有数据来源——这一条必须写进实施计划的前置任务清单，不能默认它已就绪（本文件是需求文档，不承担排期）。

### 5.3 新增：预览偏好（M2）

「用户 × 谱系」的详略模式需要存储位置（`FR-LEP-24`）。**M1 不做三档切换，因此 M1 不需要这张表**；它与 `FR-LEP-23` 一起在 M2 落地。

**设计决定**：新建轻量表 `lineage_view_preference`，列为 `id uuid PK DEFAULT uuidv7()`、`organization_id`、`lineage_id`、`user_id`、`preview_detail text CHECK IN ('full','simplified','minimal')`、公共列；`UNIQUE (organization_id, lineage_id, user_id) WHERE deleted_at IS NULL`。理由：偏好会随 UI 继续增加（房支分组、世系表列显隐），塞进 JSON 会变成第二套 schema；而 `organization_member` 属于 `auth_service`、由 Better Auth 管理，业务代码不得写入，也不存在 `metadata` 列。

### 5.4 撤销的存储（M1）

30 秒撤销（`FR-LEP-19`、`FR-LEP-29`）**不新增表**，复用既有软删：

- **添加的撤销 = 反向删除 + 回写父关系**：客户端持有本次操作新增的节点 id 列表（`createdIds`）与被替换的原父节点 id（`previousParentId`，可能为空），撤销时在同一事务里软删 `createdIds` 并把 `previousParentId` 写回 `parent_id`，再重算 `path` / `generation` / `node_count`。不产生任何「快照」数据；占位父也在 `createdIds` 里，因此不会残留。
- **删除的撤销 = 恢复软删行**：删除 Action 在成功响应里返回 `{ deletedIds, deletedAt }`（本次被软删的人丁 id 列表与时间戳），客户端把这份凭据留在内存；撤销时回传 `deletedIds`，服务端在同一事务内恢复这些行并重算 `path` / `generation` / `node_count`。
- **上限 200 行**：`deletedIds` 随响应回传客户端，超过 200 人时凭据过大（§7 B7 允许单谱系 500+ 人丁，删一棵大树会传几千个 id），此时**不提供撤销**并提示「本次操作人数过多，不支持撤销」——这是有意的取舍，不做服务端快照表。
- **服务端只做两个校验**：① 这些行的 `deleted_at` 距当前 ≤ 30 秒；② 行的 `organization_id` 属于当前会话所在组织。`node` **没有** `deleted_by` 列（`lib/db/schema/lineage.ts` 只有 `deleted_at`），所以「谁删的」无法从数据判断——30 秒窗口 + 组织范围是唯一护栏，实现时必须写明这一点，不能假设存在操作者校验。超出窗口或跨组织的恢复请求一律拒绝，提示「撤销窗口已过，请联系管理员用数据库恢复」。
- **为什么不做「延迟提交」**：把写操作挂在服务端内存里等 30 秒再落库需要后台任务，而本产品明确零常驻进程（[ADR 0005](./decisions/0005-zero-background-jobs.md)）。因此撤销是「先写、后补偿」，不是「暂不写」。
- **刷新页面即失效**：凭据只存在客户端内存，刷新后撤销不可用。这是可接受的行为，30 秒窗口本来就限定在同一次编辑会话里。
- **不加 `deleted_by`**：要审计「谁删的」需要新列 + 回填，M1 不为一个 30 秒的撤销窗口加列；需要追溯时看活动日志（`activity_logs` 已有删除动作记录）。

### 5.5 新增：`node_favorite`（收藏，M2）

`id uuid PK DEFAULT uuidv7()`、`organization_id`、`user_id`、`node_id`、公共列；`UNIQUE (organization_id, user_id, node_id) WHERE deleted_at IS NULL`，复合外键到 `node (organization_id, id)`。收藏是 per-user 数据，因此不能放 `node` 列（那是全组织共享的）。

### 5.6 字段落点

M1 用到的 8 个字段里，`node` 现有 `name` / `surname` / `full_name` / `sex` / `is_alive` / `birth_text` / `death_text` / `birth_year` / `death_year` / `burial_place` / `biography` 已覆盖 7 个，**只有「出生地」没有落点**——`node` 没有 `birth_place`，`event` 表的 `place` 也没有读写路径。因此 **M1 需要一列加法迁移**：

### 5.7 不需要改的

- `node` 的 `path` / `generation` / `sort` 语义不变，拆支与挂接只是重算它们（`FR-LIN-8` 已有重算能力）。
- `person` / `person_name` / `event` / `family` / `family_child` 表结构不变：别名多值与承嗣录入都落在既有列上（§5.2、§5.6）。
- 导出（§3.12）不改表：读现有 `node` / `family` / `family_child` / `person_name` 结构后序列化为 GEDCOM 7。**前置依赖与 §5.2 相同**：`family` / `family_child` / `person_name` 是事实层表，仓库里没有查询函数、DTO 与 UI（[实现状态](./implementation-status.md) §2），导出必须先补查询层，不能默认它已就绪。
- **父子事实以 `node.parent_id` 为准**：画布、世次、统计、导出都从 `node` 读父子关系；`family_child`（含承嗣类型）只用来给 GEDCOM 的 `FAM` 补充 `PEDI` / 关系类型注释。否则同一个孩子在画布上一个父亲、在导出文件里另一个父亲，两套父子关系必然对不上。`node.role = 'spouse'` + `spouse_of_id` 映射到 `FAM.HUSB` / `WIFE`，血亲子女映射到 `CHIL`。

## 6. 权限角色

沿用 [产品需求](./prd.md) §3.2 的四角色与 `hasPermission` 权限字符串，本节不新增角色、不新增权限串。

| 能力 | 权限 | owner | admin | editor | viewer |
|---|---|:--:|:--:|:--:|:--:|
| 打开编辑器、看画布与实时预览 | `content.read` | ✅ | ✅ | ✅ | ✅ |
| 录入 / 编辑人丁、添加亲属、删除 | `lineage.write` | ✅ | ✅ | ✅ | — |
| 拆支 / 挂接 / 分房 / 删除房支（M2） | `lineage.write` | ✅ | ✅ | ✅ | — |
| 导出世系文件（M2） | `content.read` | ✅ | ✅ | ✅ | ✅ |
| 收藏 / 取消收藏人丁、改自己的详略模式（M2） | **不走 `hasPermission`**（见下，实施前需 ADR） | ✅ | ✅ | ✅ | ✅ |

- `FR-LEP-69`（M1）`viewer` 打开编辑器为只读态：右侧工具条**隐藏**（不是禁用），实时预览可用，检查器字段只读；M2 上线详略切换与收藏后，这两项对 `viewer` 同样可用（它们是本人视图设置，不改谱系内容）。来源：设计。
- `FR-LEP-70`（M1）所有写操作在服务端复核权限（`withOrg` 事务内查成员关系 + `hasPermission`）；越权返回中文 `ActionState.error`，不依赖前端隐藏。来源：设计（沿用 AGENTS.md 数据规则 2）。

**「收藏」与「详略模式」为什么不用权限串**（M2）：这两者是「本人对自己视图的设置」，写的是 per-user 行（§5.3、§5.5），不改谱系内容。若挂在 `content.read` 下就变成「用读权限写数据」，语义不通；挂 `lineage.write` 又会让 `viewer` 无法设置自己的视图。因此这两条写路径只校验会话用户（`getSessionUser()`）与行内 `user_id` 相等。

> **这是对 AGENTS.md 数据规则 2 的有意例外，必须在 M2 实施前补一条 ADR**（按 [ADR 索引](./decisions/README.md) 的下一个可用编号），写明例外范围（仅 per-user 视图行）、为什么不能复用现有权限串、以及后续若新增 `view.self` 类权限串如何收敛。ADR 未落地前不得先写代码——否则这就是一条没有记录的规则破坏，M1 不碰这条路径，所以 M1 不受影响。
