# 0020. 目标数据模型整体重建：单一全量 SQL 基线 + 事实层主数据源 + 生成列闭包

- **状态**：`accepted`
- **日期**：2026-11-09
- **可逆性**：单向门
- **关联**：`roadmap S8` / `docs/data-model.md` / `lib/db/migrations/0000_target_schema.sql` / `scripts/verify-target-schema.mjs` / `tests/fixtures/target-schema-*.sql`

## 背景与问题

重构前的数据层把身份事实当作谱系树节点的回填快照：`node` 同时承载姓名、性别、生卒与树位置，事实层只是冻结副本；两棵分类树靠邻接表 + 触发器防环；业务表普遍软删；隔离依赖「组织来源查表」的 RLS 策略与一个共享业务角色；28 条历史迁移与 19 个 snapshot 叠在一起，DDL 没有唯一真相源。

产品没有生产存量（G1 书面确认「库内非正式业务数据、可删」），也没有灰度环境。这同时创造了一个机会和一个约束：可以一次性替换整个数据层，但**没有共存窗口、没有双写、没有 down 迁移**，任何遗漏都只能在切换前发现。

需要一次回答四组问题：DDL 以什么形态落地；事实与谱系谁是主体；树与删除语义靠什么保证；隔离与运行期角色怎么切。

## 考虑过的选项

| 选项 | 优点 | 代价 / 风险 |
| --- | --- | --- |
| ① 整体重建基线（删旧迁移、journal 重置为 1 条，唯一全量 SQL） | DDL 只有一处可审；切换时不依赖迁移器逐条推断历史 | 需要停服一次性切换；目标库旧迁移记录必须清空；失败只能整体恢复 |
| ② 追加 `0028_*` 过渡迁移 | 看起来保留历史、可增量应用 | 要写一长串 `DROP` / `ALTER` 过渡，等于变相 coexistence 窗口；历史 28 条里还有与旧模型绑定的断言，收益为负 |
| 邻接表 + 防环触发器 + 递归视图 | 实现直观、改挂简单 | 每棵树都要触发器；整树读要递归；「只删中间行」要靠运行时检查，不是 DDL 不变量 |
| `ltree` 物化路径 + `parent_path` 生成列 + 自引用复合 FK | 父、深度、祖先、兄弟序都在一列；闭包由 DDL 保证；整树一次索引有序扫 | 需要 `ltree` / `btree_gist`；重排要三阶段改名；PG18 硬下限；移子树 O(子树行数) |
| 保留软删 + 回收站 UI | 误删可自助恢复 | 每条查询都要过滤，唯一约束要改部分索引；「归档」与「删除」两套状态长期并存；产品没有排期做回收站 |
| 全量 `ON DELETE RESTRICT`、无软删 | 一条 SQL 不能静默抹掉数据；没有查询过滤与部分索引的隐性成本 | 误删无法按行恢复，只能从恢复点整体恢复；删除前必须有预览 |
| 业务与认证统一一个角色 | 连接与权限矩阵最简单 | PG18 实测 `auth.*` 四表 `relrowsecurity=f`；共用角色会让业务连接无 RLS 直读密码哈希与会话 token，是安全退化 |
| 启用 `FORCE ROW LEVEL SECURITY` | 表属主也受策略约束 | 迁移 / 运维直连会一并被拦，部署与排障路径要重新设计；实测基线属主写库不需要这层 |

## 决策与理由

**选 ① 整体重建基线。** 因为 D1 + D2 已经把「无存量、可停服」变成硬前提，追加过渡迁移的唯一收益是保留一条用不上的历史；而它的代价是引入一个必须逐条验证的中间态，正好与「big-bang 没有上线后慢慢验」冲突。SQL 基线因此成为**唯一 DDL 真相源**，TS schema 逐批追平而不是反过来从 TS 反推基线。

**事实层升为主数据源，`node` 退为位置引用。** 因为「一个人可以同时出现在多部谱、多个位置」是家谱常态，把身份焊在树节点上会让每次改挂都变成一次身份复制；反过来让 `node` 只记 `path` + `person_id`，身份就不会有两份。代价是录入链路要在同一事务里写事实层与位置行，写路径变长但语义唯一。

**树用 `ltree` + 生成列 + 自引用复合 FK。** 因为闭包、防环、深度派生都能由 DDL 表达，不需要触发器或运行时检查；选「闭包 + 零延迟」而放弃「一条 `UPDATE` 完成前缀交换」，是因为重排是低频维护，把一条 UPDATE 换成事务内三条更容易验证。「三选二」里这是唯一能让「父行必须存在 / 不能只删中间行」同时成立的搭配。

**无软删、删除走 `RESTRICT`。** 因为软删把成本摊到每一条查询与每一个唯一约束上，而产品明确不做回收站；`RESTRICT` 让「还有引用就删不掉」成为数据库事实。`organization` 的归档改用 `status = 'closed'`，读写两侧都要带状态过滤——这是删掉软删后必须补上的唯一关停手段。

**业务侧统一 `genealogy_app`、认证侧保留独立 `auth_service`。** 原规格想全量统一到 `genealogy_app`，但 PG18 探针实测 `auth.*` 四表完全没有 RLS；给业务角色 `auth` schema 权限等于把凭据表暴露给它。因此规格修订为「业务侧统一、认证侧独立」，两条连接不混用、两角色不互为成员，由 `verify:deploy` 逐项断言。

**不启用 FORCE RLS。** 迁移 / 运维直连需要 `BYPASSRLS`，启用 FORCE 会把部署与排障路径一起锁死，而目标态的隔离边界本来就落在「只有应用服务持有数据库账号」这一部署前提上；RLS 是纵深防御，不是身份伪造防线。

**组织 / 成员写走库内 `SECURITY DEFINER`。** 拆掉 Better Auth 的组织能力后，改名 / 归档 / 移除成员 / 改角色失去认证侧入口；表级权限放开给业务角色后，越权直写会被 RLS 静默过滤成 0 行、调用方看不出自己被拦。把认证、组织可见、角色与 last-owner 守卫放进函数体，才能明确抛 `42501` / `22023`。

## 代价与后续影响

- **不可逆且无 down 迁移**：切换失败只能从切换前的 Neon 分支 / PITR 恢复点整体恢复，不能回滚应用版本了事；切换前必须留可恢复性演练的命令输出（G4 / T50）。
- **PG18 是硬下限**：`uuidv7()` 是 18 新增核心函数，目标库主版本必须在切换前实测 `SHOW server_version`，否则整份基线执行不了。
- **误删不可按行恢复**：运维手册的 RB-1 从「按时间戳 `UPDATE` 复活」改成「从恢复点整体恢复」，用户侧需要删除前预览。
- **认证表仍无 RLS**：这是刻意的，但意味着任何把业务角色加进 `auth` schema 的改动都是安全退化，必须被部署自检拦住。
- **`RESTRICT` 的 SQLSTATE 是 `23001` 且 postgres.js 报 `constraint_name`**：不是 `23503` / `constraint`；错误分类 helper 与 `deleteProject` 的主路径都为此改过，后者还必须在 DELETE 前探查子表，因为 postgres.js 会记住事务内第一条失败 query 并在 COMMIT 重抛。
- **TS 与基线必须零漂移**：`pnpm db:generate` 与 `verify:target-schema --parity` 把两侧钉住；本批据此发现并追平 `project.description` / `folder.seq` 两处真实漂移。
- **仍有两处未收敛**：`folder` 层级（附录 A.2 扁平单层 vs 实现多级分类）从未拍板，基线按超集建表；§7 的 Q1 / Q3 性能数字来自设计阶段的独立容器，尚未在目标环境重跑。二者都在 `docs/roadmap.md` 的阶段 E 挂起项里登记，不算已兑现。

## 何时重新评估

- 出现真实误删投诉且「删除前预览」不够用时，重新评估是否引入不可变版本行 / 回收站——注意那会与「库内书不做快照」的取舍冲突，需要另开 ADR。
- 整树渲染在目标环境实测超过 `docs/nfr.md` 的阈值时，重估 `ltree` 物化路径与「三选二」的取舍。
- 引入第二个数据库角色或让应用直连 `auth.*` 时，重估隔离边界与 `FORCE RLS` 的决策。
- 出现多环境 / 灰度上线诉求时，重估「整体重建基线 + 无 down 迁移」这一条单向门。

## 验证方式

- `pnpm verify:target-schema`（CI 的 T36–T42）：在自建干净库重建唯一基线，整份 DDL 0 ERROR，数出 17 张 public 表 / 12 个 `app.*` 函数 / 17 条 RLS 策略；逐条执行 `tests/fixtures/target-schema-positive.sql` 的 P1–P32 与 `target-schema-negative.sql` 的 N1–N31，正例用 `DO` 块做语义断言、反例逐条比对 SQLSTATE；T41 验 fail-closed；`--parity` 把 snapshot（由 `pnpm db:generate` 零漂移钉住 ≡ TS）与真实 catalog 逐表比结构。
- `pnpm verify:deploy`：运行期角色 `NOBYPASSRLS`、两角色不互为成员、业务角色不能触达 `auth`、public 表 RLS enabled 且 FORCE 刻意关闭。
- `tests/s8-stage-*.test.ts` 静态门禁钉住每一批的目标态结论，防止文档与代码回退。
- **尚未兑现**：T40 的 Q1 / Q3 `EXPLAIN` 计划形状与耗时须在 G1 书面确认的目标环境重跑，脚本对 P21 / P22 恒显式 `SKIP`，本地 Docker PG18 数字不作验收依据；切换日 T50–T52 与 G0–G5 全绿留档未执行，因此 `S8` 仍是 `in_progress`，本 ADR 不构成交付声明。
