# 0017. 单支世系导出提前到 M2，格式用 GEDCOM 7（不是 5.5.1）

- **状态**：已接受
- **日期**：2026-11-01
- **可逆性**：双向门（导出是只读序列化：不改表、不加迁移、不加后台任务，换格式只需重写序列化器。但已经发出的 `.ged` 文件用户已经带走，改格式不会回收——见「重估触发条件」）
- **相关**：[产品需求 §6.2 / §6.3 / §6.4](../architecture/11-需求与实现状态.md) · [谱系录编与实时预览规格](../../specs/001-lineage-edit-preview/spec.md) · [数据模型](../architecture/04-数据视图-数据架构.md) · [ADR 0005](./0005-zero-background-jobs.md) · [ADR 0016](./0016-tenant-columns-immutable.md)

## 背景

[产品需求](../architecture/11-需求与实现状态.md) §6.2 原本把「GEDCOM 导入导出」整体排除，理由是「用户量不足」；§6.4 又把「导出」与「PDF 排版成书」一起放在 M3。这是一个**收益侧**判断：当时没有用户，导出不带来新增用户，先做录入。

谱系专项规格的第一块（[谱系录编与实时预览](../../specs/001-lineage-edit-preview/spec.md)，边录边看成品）做完后，情况变了：用户手里第一次有了结构完整的数据——人丁、世系、婚配、亲子都在库里，录完就能看到成品。但**没有把数据带走的通道**。

「录进去出不来」是家谱类产品的信任底线问题，不是功能清单问题：家谱数据往往是用户几十年的家族资料（老谱、口述、走访记录），一旦怀疑被锁定，用户就不会开始录入——损失的**不是导出这个功能，而是录入行为本身**。这个成本比「用户量不足」的收益侧判断更硬，所以导出不能等 M3。

**范围收窄是决策的一部分，不是附带说明**：只做「单支世系导出」——选中一个人丁，导出其溯源 + 后代子树。不做整库导出，也不做导入。整库导出仍走合同 + 手工 `pg_dump`（§6.2 那一行保持结论，只补一句区分）。理由：单支导出是「用户手里这支数据能被带走」的信任证明，成本是一个序列化器；整库导出牵涉备份、脱敏、审计与合同责任；导入是解析问题（脏数据、私有标签、编码猜测、重复合并），两者都远超 M2 的边界。

## 决策

**M2 做单支世系导出，作为独立的 M2 交付块；格式为 FamilySearch GEDCOM 7.0。**

- 版本与语法：GEDCOM 7.0（2021 年发布），UTF-8 编码，文件扩展名仍是 `.ged`，行语法改为 payload 式——标签后跟带类型声明的 payload，而不是 5.5.1 的位置约定。
- 范围：选中一个人丁 → 导出其溯源 + 后代子树（含兄弟等变体由专项规格的 FR 定义）。不含整库导出，不含导入。
- 实现形态：只读序列化，读取现有 `node` / `family` / `family_child` / `person_name` 结构后写出文件。不改表、不加迁移、不加后台任务——导出在请求内同步完成（与 [ADR 0005](./0005-zero-background-jobs.md) 的零常驻进程立场一致）。
- 权限：导出是只读操作，走 `content.read`，`viewer` 可用（详见专项规格）。

### 为什么是 7 而不是 5.5.1

5.5.1 是 1999 年的产物，处在 ANSEL / 字符集时代：对中文与生僻字、多值名称、非拉丁姓名的表达能力弱，表达同样的语义需要大量私有扩展标签（`_XXX`）。私有标签的代价是**导出文件变成「我们的方言」**：别的软件读不进去，我们自己将来也要为这些 `_XXX` 维护兼容。

GEDCOM 7 用 UTF-8 + 显式 payload 类型（`g7:` URI）表达同样的语义，扩展不需要私有标签。本项目**全部中文姓名**，编码与名称表达是首要问题，不是边角问题——所以这里选 7，不是选「更新的那个」。

### 承认的代价与缓解

GEDCOM 7 的第三方读取方兼容性目前弱于 5.5.1：很多老牌家谱软件只认 5.5.1，用户把文件拿去导入别的软件可能失败。这是本决策最真实的风险，不回避：

- 导出文件在 `<HEAD>` 里声明版本，让读取方与用户都能判断格式。
- 实施时用**至少 2 个真实第三方工具**做导入回归（如 FamilySearch、Gramps），而不是只验证「文件能被我们自己的解析器读回」。
- 回归不通过则退回「GEDCOM 7 为主 + 5.5.1 兼容开关」，并重估默认格式（见「重估触发条件」①）。

## 后果

### 正面

- 用户在 M2 就拿到了把数据带走的通道：信任问题在「开始录入」之前被解决，而不是在续费时被追问。
- M3 少一项：原「PDF 排版成书、导出、字体授权」只剩排版与字体授权，M3 的主题更集中。
- 导出是只读序列化，[数据模型](../architecture/04-数据视图-数据架构.md) 不需要为导出改表——读取现有 `node` / `family` / `family_child` / `person_name` 结构后序列化即可，没有新表、没有新迁移。
- 选 7 让中文与生僻字不需要私有扩展标签，导出文件是标准 GEDCOM 7，而不是「我们的 GEDCOM 7 方言」。

### 负面

- **第三方兼容性弱于 5.5.1**（见上节缓解）。若回归失败，M2 会多出一个兼容开关的工作量，且两套输出要各写一套回归。
- **只支持单支**：用户会问「为什么不能一次导出全部」。答案在 §6.2（整库走合同 + `pg_dump`），必须写进销售话术与帮助文档，不能假装不存在。
- **不做导入**：导出的文件回不到本产品，round-trip 只有单向。这是有意的范围收窄，但意味着「从别处迁入」仍需人工或运维介入。
- GEDCOM 7 是 payload 式行语法，序列化器不能照抄 5.5.1 的位置拼接写法；实现时要有自己的编码与转义测试（生僻字、多值名称、非拉丁姓名），不能只靠「导出成功」一条用例。

### 中性

- 谱系专项 PRD 的 FR 清单里，导出属 M2 范围（具体编号以该文件为准，本文不复制）。
- 文件扩展名仍是 `.ged`：用户与工具链不需要为格式升级改扩展名。
- §6.2 的那一行从此只针对**导入**；「客户自助数据导出」那一行保留结论，只补一句「整库」的区分。

## 放弃的方案

| 方案 | 为什么不够好 |
|---|---|
| 只做 GEDCOM 5.5.1 | 中文与生僻字、多值名称要靠私有扩展标签 `_XXX` 表达，导出即被自家扩展污染；5.5.1 的 ANSEL 时代假设与本项目全中文姓名正面冲突 |
| 先做 5.5.1，以后再迁 7 | 迁移成本落在「已经发给用户的文件」上，而不是代码上；私有扩展一旦成为既有事实，越晚换越贵 |
| 同时输出 7 与 5.5.1 两种格式 | 两套序列化器 + 两套回归，M2 的收益不足以付这份成本；作为 7 的兼容性回退方案保留（见缓解），不作为默认 |
| 整库导出自助化 | 牵涉备份、脱敏、审计与合同责任，不是 M2 的量级；仍走合同 + 手工 `pg_dump` |
| 导出与导入一起做 | 导入是比导出难得多的解析问题（脏数据、私有标签、编码猜测、重复合并），需单独立项 |
| 不做导出，靠合同承诺「数据是你的」 | 承诺不是通道：用户看不到文件就不会开始录入，而这正是本决策要解决的成本 |
| 把导出做成后台任务（异步生成、下载链接） | 单支导出是秒级同步序列化，引入队列只会多一个没有消费者的常驻进程，违反 [ADR 0005](./0005-zero-background-jobs.md) |

## 重估触发条件

1. **第三方导入回归连续失败**（例如 FamilySearch、Gramps 都无法完整读入中文姓名或世系结构）→ 退回「GEDCOM 7 为主 + 5.5.1 兼容开关」，并重估默认格式。
2. **出现「必须先支持导入」的客户需求**（老谱数字化迁移、从竞品迁入）→ 导入单独立项，不要塞进导出块；本 ADR 的范围收窄不因此自动失效。
3. **客户要求整库导出自助化**（不只是单支）→ 走合同 + `pg_dump` 的数据导出服务，或单独立项，不要顺手扩大本决策的范围。
