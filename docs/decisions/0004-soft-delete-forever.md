# 0004. 软删永存，M1 无回收站

- **状态**：已接受
- **日期**：2026-10-21（原始决策）· 2026-10-22（补记为 ADR）
- **可逆性**：**单向门**（数据形态；改为硬删需要先确认已存数据中哪些可销毁）
- **相关**：[data-model §11](../data-model.md) · [05-data §8.6](../architecture/05-data.md) · [08-evolution R4 / R10 / R18](../architecture/08-evolution.md) · [runbooks](../guides/runbooks.md)
- **修订**：2026-10-24，表计数与硬删除例外按 ADR 0007 落地后的 schema 校正。

## 背景

家谱数据的误删对一个家族是**不可接受的损失**：一本纸谱可能修了三十年，一次误删丢掉一整支人丁，没有第二份可对照。

同时，M1 没有回收站界面（PRD §6.2 明确排除），也没有后台清理任务。

## 决策

- 8 张软删实体表（organization/project/folder/lineage/node/article/book/book_catalog）带 `deleted_at`，非空即已删除。
- `organization_member` 与 `invite` 由 Better Auth 硬删除，不保留软删列。
- `activity_logs` 是产品活动流，不带 `deleted_at`。
- **不做物理删除**。`app_rw` 不授予 `DELETE` 权限，物理删除在数据库层被挡住。
- `organization_member`/`invite` 的物理删除由 `auth_service` 执行，这是受控例外。
- 唯一约束一律用**部分索引**（`WHERE deleted_at IS NULL`），保证「删了还能建同名」。
- 同一次删除操作的所有行共享**完全相同的 `deleted_at`**（`now()` 取事务开始时间），供运维整组恢复。
- M1 **不提供恢复界面**，恢复由运维按 [runbook](../guides/runbooks.md) 在数据库层面执行。

## 后果

### 正面

- 误删是「零成本保险」：恢复只需把 `deleted_at` 置空，不需要从备份回滚整个库。
- 引用完整性不受影响：编目引用一条已软删的谱系时，外键仍然成立，不会产生悬空引用。
- 与 RLS、复合外键、部分唯一索引都能自然组合。

### 负面

- **数据永久增长**，永不回收。十万级人丁下约 30MB/2 年，可接受；但没有上限。
- **与数据删除权存在张力**。家谱包含在世人口的姓名、性别、生卒、葬地、行传；数据主体是族人，账号所有者是修谱人/组织。当前架构对「某个族人要求删除自己的信息」的答案是「永久保留、界面不可见」。这不是技术缺陷，是**未做的产品决策**。
- **恢复粒度是事务级，不是实体级**。恢复脚本按 `deleted_at` 时间戳整组恢复，无法只恢复「这一支里的三个人」。若两个删除操作恰好落在同一微秒，会被一起恢复（概率极低，但脚本本身也不按组织/谱系限定范围，存在误恢复风险）。
- 恢复必须走运维工单，**没有自助能力**，也没有 SLA。
- 查询处处要带 `deleted_at IS NULL`，漏一处就是数据泄漏或计数错误。

### 中性

- `activity_logs` 没有 `deleted_at`（它是产品活动流，不是业务实体，也不是审计表）。

## 放弃的方案

| 方案 | 为什么不够好 |
|---|---|
| 硬删 + 依赖备份恢复 | 恢复粒度是「整个数据库回滚到某时刻」，为了找回三个人要丢掉之后的所有写入。不可接受 |
| 回收站表（把删除的行搬到另一张表） | 需要双写、双读路径、恢复时的唯一约束冲突处理；M2 用 `delete_batch` 做 |
| 软删 + 定时清理（超过 90 天物理删除） | **这个方案其实是对的**，但它需要 ADR-0005 破例引入后台任务，M1 未做 |

## 重估触发条件

1. **首个客户询问数据处置能力**（「我们注销后数据还在吗？」）→ 必须先定义保留期与物理删除路径，再答复。
2. 出现明确的合规要求（个人信息删除权）。
3. 软删数据量超过 500 万行或影响查询性能 → 引入归档。

> **补齐方向**（见 [05-data §8.6](../architecture/05-data.md)）：数据分级（账号凭据 / 在世人口 PII / 已故人口信息 / 谱文内容）→ 分级保留期 → 一条物理删除路径（需要 `app_admin` 角色或运维脚本，打破「永不 DELETE」）→ 一个清理任务（打破 ADR-0005）。
