# 0003. 树存储用邻接表 + ltree 物化路径，且严格父系

- **状态**：已接受
- **日期**：2026-10-21（原始决策）· 2026-10-22（补记为 ADR）
- **可逆性**：**单向门**（有真实数据后改动 = 跨全表迁移 + 已排版版本重排）
- **相关**：[data-model §6.2](../data-model.md) · [05-data](../architecture/05-data.md) · [08-evolution R9](../architecture/08-evolution.md) · [待决策 D-4](../architecture/08-evolution.md#15-待决策项)

## 背景

世系数据需要支持四类查询：

1. 取某节点的全部后代（按代渲染、世系表、谱书章节）
2. 取某节点的祖先链（搜索定位、面包屑）
3. 移动子树并重算世次（`moveNode`）
4. 按世次批量取（按代加载）

同时，族谱有一项硬性语义：**配偶不占世次、不进世系路径**，但要与血亲并排渲染。

## 决策

`node` 表同时使用两种表示：

- **邻接表**：`parent_id` 指向父节点（真外键）。
- **物化路径**：`path ltree`，label 是该节点 UUID 去掉横线（32 位十六进制）。`path` 的每一段就是一位祖先的 id，因此「祖先链」与「后代集合」都能一次索引扫描得到。

约束 `ck_node_spouse_has_no_path` 强制：`role='blood'` 必须有 `path`，`role='spouse'` 必须 `path IS NULL` 且 `spouse_of_id NOT NULL`。配偶通过 `spouse_of_id` 挂在血亲上，不进路径。

## 后果

### 正面

- 后代查询是一次 GiST 索引扫描（`path <@ $1`），不随树深度退化。
- 移动子树是一条批量 `UPDATE`：把前缀替换掉、`nlevel` 差值加到 `depth`/`generation`。
- 祖先链不需要递归 CTE。
- `path` 天然给出**房支顺序**（祖先必为前缀），这正是世系表需要的排序依据。

### 负面

- **`path` 是严格父系单链**。这意味着：
  - **过继 / 嗣子**无法表达——改 `parent_id` 会抹掉生父关系，历史不可追溯；
  - **兼祧**（一人承两房）无法表达——除非把同一人复制成两条人丁，数据从此分叉；
  - **入赘**（子女随母系）无法表达——`path` 只能沿父系延伸；
  - **女儿入谱后其子女无法形成支系**——能录她，但她的子女挂不到她下面成为独立分支。
- `path` 的 label 是 UUID，**不含排行或字辈信息**，所以排序必须依赖 `sort` 列。而 `sort` 是「同一父节点内的排行」，跨房支排序时不能直接用它（会交错）。
- 每次 `moveNode` 要重写整棵子树的 `path`（+ `depth` + `generation`），写入量与子树规模成正比。
- `depth` 与 `generation` 两列是 `path` 的派生量，却作为独立列维护，存在漂移可能。

### 中性

- `ltree` 路径长度上限约 65535 字节，单代约 33 字节 → 理论上限约 1900 代，现实中不存在（原文档写的「>200 代」偏保守）。

## 放弃的方案

| 方案 | 为什么不够好 |
|---|---|
| 纯邻接表 + 递归 CTE | 每次查后代都要递归，深度越大越慢；无法一次索引扫描 |
| 闭包表（closure table） | 查询最快，但每次插入/移动要写 O(n²) 行关系，写入成本与树规模平方相关 |
| 嵌套集（nested set） | 读极快，但任何插入/移动都要重编号大量节点，不适合频繁编辑 |
| 多态关系表（`node_relation` 边表） | **能表达过继/兼祧，但成本高**：路径计算、世次推导、渲染全部要改；M1 排期不足 |

## 重估触发条件

**必须在 M1 GA 之前明确回答一个问题**：「关系」是节点属性，还是独立实体？

- 若坚持节点属性（现状）：把「不支持过继/兼祧/入赘」写进 [PRD §6.3](../prd.md) 的已知缺口，作为销售前置说明。这是可接受的取舍，但**必须显式**，不能让它成为客户上线后才发现的问题。
- 若要支持：M2 引入 `node_parent(child_id, parent_id, kind: birth|adoptive|foster, sort)` 边表，`path` 降级为「主系缓存」或直接移除。

**为什么不能拖到 M3**：M3 的 PDF 排版会把当前结构固化进成品谱书。届时改成边表，意味着已排好的每一本书都要重排页码。

其他重估信号：

1. 首个客户提出「我们这一支有过继」。
2. 需要按「房」而非「世次」组织谱书目录。
