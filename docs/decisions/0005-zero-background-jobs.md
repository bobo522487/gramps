# 0005. 零后台任务

- **状态**：已接受（存在已知的破例触发条件）
- **日期**：2026-10-21（原始决策）· 2026-10-22（补记为 ADR）
- **可逆性**：双向门（引入第一个任务不改数据形态，但要补一整套运维面）
- **相关**：[02-context §3.2](../architecture/02-context.md) · [08-evolution R18](../architecture/08-evolution.md) · [ADR-0004](./0004-soft-delete-forever.md)
- **修订**：2026-10-24，认证已切换到 Better Auth 数据库会话（ADR 0007），原“无会话表、会话自带过期”不再成立。

## 背景

M1 的需求里，所有「时间相关的动作」都可以在**查询时判断**，不需要预先执行：

| 需求 | 通常做法 | M1 的做法 |
|---|---|---|
| 邀请 7 天过期 | 定时清理过期邀请 | 查询时判断 `expires_at > now()`；`idx_invite_expiry` 支持 |
| 软删数据清理 | 定时物理删除 | 不清理（见 ADR-0004） |
| 会话过期 | 定时清理会话表 | 数据库会话由 Better Auth 管理；过期判断在读取时完成。M1 没有独立的会话清理任务，不依赖后台任务；如有清理需求，与数据保留期一起破例 |
| 统计与报表 | 定时聚合 | 现查 |

同时，引入后台任务不是「加一个 cron」，而是引入：调度器、任务幂等、失败重试、死信处理、任务可观测性、以及「任务失败没人知道」这个永久运维面。对 1–3 人无专职运维的团队，这是一条不该在 M1 跨过的线。

## 决策

**M1 后台任务数量为 0。** 没有 cron、没有队列、没有 worker、没有定时器。

## 后果

### 正面

- 部署形态最简：一个无状态应用 + 一个数据库。没有「应用健康但 worker 挂了」这种半故障状态。
- 不需要任务幂等设计，不需要死信队列，不需要任务监控。
- 冷启动、超时、并发度这些 serverless 的坑全部不适用。
- 成本可预测（Vercel 按请求计费，无常驻进程）。

### 负面

- **任何「到期自动做某事」的需求都无法满足**。这不是「暂时不做」，是「架构上做不到」。具体包括：
  - 邀请过期后自动清理（现在靠索引 + 查询判断，表会缓慢增长）；
  - 软删数据按保留期物理删除（**与数据删除权直接冲突**）；
  - 账号注销冷静期到期后执行删除；
  - 任何异步重活（批量导入、PDF 排版、导出）。
- **第一次破例的成本很高**。当第 1 个任务出现时，需要同时补上：调度机制、幂等键、失败重试、执行日志、失败告警。这一整套在 M1 完全不存在。
- 「零任务」这个决策会给人一种「永远不需要任务」的错觉，掩盖了上面这些需求的存在。

### 中性

- M3 的 PDF 排版被设计为**独立进程**（ADR-16），它不走「后台任务」这条路，而是第二个运行时。这两件事要分开看。

## 放弃的方案

| 方案 | 为什么不够好 |
|---|---|
| 现在就引入 cron（Vercel Cron） | 没有真实需求，先建基础设施是负债；且会诱使设计依赖「反正有定时任务」 |
| 用数据库 `pg_cron` 扩展 | 把业务逻辑塞进数据库，与「应用层承载业务」的分层冲突，且难以测试 |
| 用一个「兜底任务」提前占位 | 空跑的任务同样需要监控，等于用真实成本换心理安慰 |

## 重估触发条件

**预计第一个破例来自数据保留期清理**（[08-evolution R18](../architecture/08-evolution.md)）。破例时应该：

1. 新写一篇 ADR 说明「为什么这个任务可以破例」，而不是修改本文；
2. 明确任务的最小实现：Vercel Cron 或 Neon 定时函数，单实例执行，幂等键落在表上；
3. 同时补上执行日志与失败告警——**没有告警的定时任务是负债，不是能力**；
4. 明确「任务失败时业务是否可用」：清理任务失败不应影响任何用户操作。

其他信号：

- 出现批量导入需求（GEDCOM 导入在 M1 明确排除，但 M2 之后可能回归）；
- 出现需要预先计算的统计报表。
