# 0018. 文档只保留一层：根级事实层并入 `docs/architecture/`

- **状态**：已接受
- **日期**：2026-11-02
- **可逆性**：双向门（纯文档搬家：代码零改动，链接可机械回改。但**旧路径已被外部引用**——AGENTS.md、`specs/`、`decisions/` 里的历史链接会失效，回退成本高于一次改对）
- **相关**：[文档中心](../README.md) · [00-文档说明](../architecture/00-文档说明.md) · [11-需求与实现状态](../architecture/11-需求与实现状态.md) · [12-风险与演进规划](../architecture/12-风险与演进规划.md)

## 背景

`docs/` 曾分两层：根级放「事实层」文档（`data-model.md`、`api.md`、`setup.md`、`ops-target.md`、`implementation-status.md`、`prd.md`、`architect.md`），`architecture/` 放 15 份架构视图。两层用**目录位置**表达「as-is / to-be」，而不是在文档内部标注。

2026-11-02 的全量审计（65 个 `.md`、22,942 行）量出了这套结构的代价：

- **同一事实写了两三份**。表结构在 `data-model.md` 与 `04-数据视图-数据架构.md` 各有一套说法；环境变量在 `setup.md` 与 `ops-target.md` 各抄一遍；需求摘要列在 `prd.md` 与 `12-需求追溯矩阵.md` 重复；ADR 索引在 `11-技术选型与决策记录.md` 与 `decisions/README.md` 重复。跨文档同源冲突 6 组：表数量（4 处写 11，实际 17）、迁移数量（2 处写 4，实际 25）、扩展归属、部署状态（3 处三种说法）、权限串、已删除的 `node.attributes`。
- **漂移是结构性的，不是手误**。同一事实有两份副本时，改一份忘另一份是必然结果；`docs:check` 能查链接与措辞，查不出「两处写同一件事」。
- **导航要人肉维护两套**：`README.md` 的树、`00-文档说明.md` 的导航表、`architect.md` 的跳转页、`14-附录.md` 的旧文件对照表，四份都在描述「文档在哪」。`architect.md` 全文 46 行只有 1 条入链，是纯转接层。
- **两层口径互相矛盾**：`README.md` 说 `architect.md` 是目标设计，`.backup-2026-10-22/README.md.bak` 说它是历史，`architect.md` 自己说它是跳转页。

结论：用**目录位置**表达 as-is / to-be 不成立——`data-model.md` 里同时有已落地的表和 M2 才建的表，`prd.md` 里同时有已实现和未实现的 FR。真正需要标注的是**段落级**的，不是**文件级**的。

## 决策

**`docs/` 只保留一层文档集：根级文档全部并入 `docs/architecture/`，`docs/` 根目录只留 `README.md`（入口）。**

映射（14 份，编号 00–13）：

| 原位置 | 新位置 |
|---|---|
| `architect.md` + `00-文档说明.md` + `14-附录.md` | `architecture/00-文档说明.md` |
| `11-技术选型与决策记录.md` 的技术栈与依赖立场 | `architecture/02-架构目标与约束.md`（ADR 索引与待决策表只留链） |
| 原 `04-数据视图-数据架构.md` + `data-model.md` | `architecture/04-数据视图-数据架构.md` |
| 原 `05-接口与集成设计.md` + `api.md` | `architecture/05-接口与集成设计.md` |
| 原 `06-部署视图-部署架构.md` + `ops-target.md` | `architecture/06-部署视图-部署架构.md` |
| `prd.md` + `12-需求追溯矩阵.md` + `implementation-status.md` | `architecture/11-需求与实现状态.md`（**唯一状态表**） |
| 原 `13-风险与演进规划.md` | `architecture/12-风险与演进规划.md` |
| `setup.md` | `architecture/13-本地开发与命令.md` |

配套规则：

- **as-is / to-be 改成段落级标注**：同一文档里既有现状又有目标时，用 `[现状]` / `[目标]` 前缀标出边界；文档头的「目标 vs 现状」字段说明本文哪部分是哪种。
- **一个事实只有一个来源**，见 [文档中心 §5.1](../README.md)。合并时删副本，不搬副本。
- **状态只写 [11-需求与实现状态 §7](../architecture/11-需求与实现状态.md)**：需求定义（§5）、追溯矩阵（§7）、模块实现状态（§8）在同一份文档里，状态列只有一处。
- 历史材料不参与合并：评审、已完成计划、历史底稿进 `docs/archive/`，不参与 `docs:check`，不被当作规范。

## 后果

### 正面

- 删掉的是**重复副本**而不是内容：合并后活跃文档行数从 8,533 降到约 6,900，减少的部分几乎全是同一事实的第二份写法。
- 修一处只改一处。此前「表数量写 11」这类错误分散在 4 份文档，现在只在 04 与 11 出现，且 11 用「见 04」代替复述。
- 导航从 4 份（README 树、00 导航表、architect 跳转页、14 附录对照）收敛到 1 份（README §2 + 00 的术语与历史对照）。
- `docs:check` 的检查范围变大：原先 `contradictionScope` 硬编码了 6 个根级文件，合并后只剩 `README.md` + `architecture/` + `decisions/` + `guides/`，新增文档自动进入检查范围。

### 负面（必须诚实写）

- **链接大面积改动**：活跃文档 79 条、`decisions/` 18 条、`guides/` 4 条、`AGENTS.md` 19 条、`specs/001` 6 条指向根级文档的路径全部要改。这次靠脚本批量改 + `docs:check` 兜底，但**脚本改不了语义**：`api.md` 的 §4.2 这种带锚点的链接，锚点跟着标题变了，必须人工复核。
- **文件名不再能猜**：根级的 `data-model.md` 好记，`architecture/04-数据视图-数据架构.md` 不好记。缓解：`README.md` §5.1 的单一事实来源表按「你要找什么」索引，不按文件名索引。
- **单文件变长**：`04` 从 148 行涨到约 1,300 行，`11` 约 700 行。缓解：每份文件开头有目录，章节号稳定，跨文档用锚点链接。
- **编号语义被破坏**：`architecture/` 的文件编号本来是阅读顺序（01 总览 → 02 目标 → …），现在 11 是需求、13 是本地命令，编号更多是「槽位」而不是「阅读顺序」。真正的阅读顺序由 `README.md` §3 的阅读路径承担。
- **旧路径的历史引用无法全部修复**：`docs/archive/` 里的评审记录仍写根级旧路径，永久失效。这是归档的代价，接受。

### 中性

- `specs/` 仍在仓库根（不在 `docs/` 内），是 spec-kit 的规格层，不参与这次合并。
- `decisions/` 与 `guides/` 保持独立子目录：前者是不可改写的历史，后者是操作手册，都不适合按架构视图编号。

## 放弃的方案

- **保留根级 6 份 + 只合并 `architecture/` 内部的 11/14**：改动最小，但重复副本一个没删——`data-model.md` 与 `04` 仍是两份，问题原样保留。
- **根级文档保留、`architecture/` 改成「只是索引」**：等于把架构视图降级成目录页，架构内容无处安放。
- **按 as-is / to-be 重建两个目录**：需要先把每份文档按段落拆开再重组，工作量数倍于合并，且 `data-model.md` 这类文档本身就是混合体，拆完两份都要维护。
- **生成式文档索引**（脚本从文档头生成导航表）：能消除「导航表手抄」这一类重复，但解决不了「同一事实两份正文」，且引入一个需要维护的生成器；等文档数量再翻一倍时再考虑。

## 重估触发条件

- 单份文档超过 1,500 行，或 `architecture/` 回到 18 份以上——说明合并在制造「大杂烩」，需要按新维度（而不是旧的 as-is / to-be）再切一层。
- 出现第二类读者（例如只读 PRD 的产品同学）明确要求「不用翻架构文档就能读完需求」——那说明 `11` 的 §1–§6 需要拆成独立文档，但**状态列仍只能有一份**。
- `specs/` 的规格层开始承载 as-is 内容（而不只是增量需求）——那时要把 `specs/` 也纳入同一套编号与检查。
