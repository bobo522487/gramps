# 0002. M1 不做编辑锁，接受 last-write-wins

- **状态**：已接受
- **日期**：2026-10-21（原始决策）· 2026-10-22（补记为 ADR）
- **可逆性**：双向门（加锁是加法，不改数据形态）
- **相关**：[PRD §6.3 缺口 3](../prd.md) · [07-运行视图-关键流程](../architecture/07-运行视图-关键流程.md) · [13-风险与演进规划 R3](../architecture/13-风险与演进规划.md)

## 背景

M1 的目标用户是「一个家族里 2–3 个熟人」或「2–5 人的修谱工作室」。他们通常分工明确（各房支联络人录自己那一支），且当面或微信沟通成本极低。

在这个前提下，做并发保护需要一整套机制：`resource_lock` 表、心跳续期、锁超时回收、fencing token 防脑裂、UI 只读态、锁冲突提示。这套机制的复杂度不低于 M1 的半个业务模块，而它防范的是「两个熟人同时改同一个节点」——概率低且可沟通。

## 决策

M1 **不做任何并发保护**：没有编辑锁，也没有乐观锁（没有 `version` 列）。同一资源的并发写入是 last-write-wins，后提交的整行覆盖先提交的。

## 后果

### 正面

- 写路径只有「业务 → 失效缓存」两步，没有锁的获取、续期、释放、异常回收。
- 没有僵尸锁问题（浏览器崩溃后锁不释放）。
- 没有 fencing token 这类分布式正确性负担。
- 数据模型少一张表和一组状态机。

### 负面

- **同一节点被两人编辑时会静默丢数据**：A 载入节点 #5（姓名「元英」），B 改成「元瑛」并保存，A 再补生卒年保存 → 姓名被写回「元英」，B 的修改消失。
- **没有任何检测能力**。因为没有 `version` 列，服务端无法判断「提交的是不是基于最新版本」，所以连「提示用户可能覆盖了别人的修改」都做不到。
- 不同节点之间**不会**互相覆盖（不同行），所以风险面比「多人协作」听起来小；真正的风险集中在同一节点的不同字段、以及 `moveNode` 的子树批量更新与另一人的编辑撞车。
- 用户在界面上没有任何信号。覆盖发生后不可感知，往往到排版成书时才发现。

### 中性

- 冲突概率与「同时打开同一谱系的人数 × 停留时长」正相关。M1 用户量下低，但会随客户规模线性上升。

## 放弃的方案

| 方案 | 为什么不够好 |
|---|---|
| 悲观锁（`resource_lock` + 心跳 + fencing） | 表 + 心跳 + 超时回收 + UI 只读态 + 异常路径，复杂度接近半个模块；M1 冲突概率不足以支撑 |
| 乐观锁（`version` 列 + 409 冲突） | **成本只有悲观锁的 1/10**，但需要每个写 Action 都处理冲突分支与 UI 合并提示；M1 排期不足 |
| CRDT / OT 实时协同 | M4 才考虑；需要改变整个编辑模型 |
| 只在 UI 提示「建议一人编辑完」 | 这不是方案，是缓解措施。当前实际采用的就是这一条 |

## 重估触发条件

出现以下任一信号时，**先加乐观锁（检测 + 提示），再考虑编辑锁（阻止）**：

1. 有客户明确反馈「我的修改被覆盖了」。
2. 单个组织出现 ≥3 人同时编辑同一谱系。
3. 谱书排版（M3）开始消费数据——届时覆盖导致的错误会被固化进成品，代价从「改一个字段」变成「重排一本书」。

> **建议的中间步骤**：加一列 `version int NOT NULL DEFAULT 0`，写入时 `WHERE version = $n` 并 `SET version = version + 1`，影响 0 行则返回 `CONFLICT_STALE`。这是 1 天的活，能覆盖 90% 的实际损失场景，且不需要锁表、心跳与只读态。
