## 日志

结构化 JSON，一行一条，由 `lib/logger.ts` 写出。级别顺序 `debug < info < warn < error`，级别来自 `LOG_LEVEL`（`instrumentation.ts` 启动时注入；未配置时默认只输出 `error`）。

| 字段 | 来源 | 何时出现 |
|---|---|---|
| `level` | 调用方 | 每条 |
| `time` | `new Date().toISOString()` | 每条 |
| `message` | 调用方 | 每条 |
| `request_id` | `x-request-id` 头或 `randomUUID()` | **仅 Route Handler**（`withApiLogging` 建立请求上下文）；`proxy.ts` 会给页面请求注入该头，但 Server Action 路径没有建立上下文 |
| `method` / `path` | 请求对象 | 仅 Route Handler |
| `user_id` | `getSessionUser()` 里的 `addLogContext` | 解析出会话之后的任何日志 |
| `route` / `status` | `withApiLogging` | 仅 Route Handler 的完成日志 |
| `duration_ms` | `withApiLogging` | 仅 Route Handler 的完成日志与失败日志 |

`org_id` 在请求上下文类型里声明了，但**没有任何代码写入它**——按组织聚合日志目前做不到。

约定与红线：

- 服务端日志自动带上请求上下文，不需要把 `request_id` 逐层传参；业务代码不散落 `console.log`。
- 日志写 stdout/stderr，不写文件（函数实例随时回收）。
- **禁止记录**：密码、Cookie、会话 token、邀请 ID、完整邮箱、身份证、完整住址。数据库错误只记 `SQLSTATE`（`scripts/verify-deployment.mjs` 的 `safeDbError` 就是这个做法），不记原始错误与参数。
- 日志保留期由平台决定，超出保留期的逐条追溯只能靠日志导出或 PITR。

## 健康检查

`GET /api/health` 是唯一的运维探针入口，**匿名可访问**，`dynamic = 'force-dynamic'`。

- 它**会查数据库**：执行 `select 1`，成功返回 `{ status: 'ok', database: 'up' }` 与 200，失败返回 `{ status: 'error', database: 'down' }` 与 503。
- 它带 `x-request-id` 响应头，失败时写一条 `error` 日志。
- 用途：CI 的部署验证步骤轮询它就绪后才跑 `scripts/verify-deployment.mjs`；`verify:deploy` 也会断言状态码与响应体。

盲区（这三件事它都不知道）：迁移是否已应用（只 `select 1`，不查表结构）、登录角色是否有权限（用的是业务连接，但只做一次空查询）、RLS 是否还生效。这三项由 `scripts/verify-deployment.mjs` 单独断言，属于部署后验证，不是运行时探针。

## 错误处理与用户可见文案

- **Server Action 返回 `ActionState`**：`{ error?, code?, success?, fieldErrors?, email?, name? }`。文案是简体中文，`code` 是稳定枚举（`UNAUTHORIZED` / `FORBIDDEN` / `NOT_FOUND` / `CONFLICT` / `VALIDATION` / `RATE_LIMITED` / `INTERNAL`），由 `lib/errors.ts` 的 `actionError()` 统一构造——这是唯一入口，不要手拼。
- **Route Handler 返回英文 JSON + 明确状态码**：401 / 403 / 404 / 500，错误体是 `{ error: '...' }`，500 不泄露内部信息。
- **不把数据库错误与堆栈展示给用户**：约束冲突（`23505` / `23514` / `23503`）在 `lib/db/errors.ts` 识别后转成中文文案；识别不了的归到通用失败文案，原始错误只进日志。

## 告警与监控现状

**没有外部告警系统、没有 APM、没有分布式追踪。** 现在能看的只有三样：Vercel 函数日志、Neon 的连接数与计算指标、`/api/health` 的响应。

| 想知道的事 | 现在怎么看 | 缺口 |
|---|---|---|
| 站点是否活着 | 手动 `curl /api/health`；CI 部署验证会轮询 | 没有外部探针定时探测，挂了没人被叫醒 |
| 错误率是否升高 | 翻 Vercel 日志，按 `level: error` 过滤 | 没有聚合与阈值，没有错误预算 |
| 慢请求在哪 | Route Handler 的 `duration_ms`；页面侧没有 | 没有 p95 聚合；页面 TTFB 无法从日志得出 |
| 某个用户报的错怎么定位 | 让用户提供 `x-request-id`（Route Handler 有） | Server Action 没有 `request_id`，只能靠时间窗 + `user_id` 猜 |
| 数据库是否健康 | Neon 控制台指标 | 没有与应用日志关联的 trace |
| 谁改了哪条数据 | 产品活动流 `activity_logs` | 不是审计日志（可缺失、无防篡改、无保留期） |

目标蓝图里规划了外部探针 + 5xx 阈值告警（[ops-target](../ops-target.md) §6.3），**当前未配置**。

## 故障处理

| 症状 | 先查什么 | 处置 |
|---|---|---|
| 登录不上，密码正确 | 是否用 `http://localhost:3000` 访问（Cookie 带 `Secure`，IP 或其它域名会被丢弃）；`.env` 是否存在且被读取 | 换回 `localhost`；确认配置文件是 `.env` 而不是 `.env.local` |
| 大量 500，日志出现 `too many connections` | Neon 连接数是否打满；实例数与每实例池上限（5） | 用 pooled 端点、降 `max`、确认 `attachDatabasePool` 生效；见 runbook RB-5 |
| 所有写操作都报权限错误 | 登录角色是否仍是 `app`；`withOrg` 内 `SET LOCAL ROLE app_rw` 是否执行；RLS 策略是否被改坏 | 跑 `pnpm verify:deploy` 的数据库检查；见 runbook §0.3 |
| 构建成功但运行报「列不存在」 | 迁移是否已应用到目标库；`_journal.json` 与库内 `drizzle.__drizzle_migrations` 是否一致 | 应用迁移后重发；见 runbook RB-6 |
| 构建与单测都过，E2E 失败 | E2E 是否跑在 production server；测试库是否被清空；Playwright 浏览器是否装好 | 看 CI 上传的 Playwright 报告与截图 |
| 误删了成员或邀请 | 是否是硬删除（这两张表没有软删） | 只能从备份恢复；见 runbook RB-1 与 RB-3 |
| 组织没有 owner | 最后一个 owner 是否被删；触发器是否还在 | 按 runbook RB-3 修复；触发器是兜底，不能替代预检 |
| 用户忘记密码 | 没有自助找回（无邮件通道） | 走 runbook RB-2 的强制下线流程 |

## 恢复能力

| 场景 | 手段 | 最坏情况的数据损失 |
|---|---|---|
| 误删业务数据（谱系、人丁、谱文、谱书） | 软删可查库恢复（同一次操作的行共享 `deleted_at`），**没有 UI 恢复入口** | 从误删到发现之间的所有后续写入可能已改变树结构，恢复需要人工判断 |
| 误删成员 / 邀请 | 不可恢复（硬删除），只能从备份恢复 | 备份间隔内的全部成员与邀请变更 |
| 数据库故障 | Neon PITR / 分支恢复 | 取决于可恢复时间点，**没有演练过，没有 RPO/RTO 承诺** |
| 发布引入缺陷 | Vercel 重新部署上一版本；迁移必须先于代码且向后兼容一个版本 | 回滚窗口内新写入的数据要按新 schema 解释 |
| 密钥疑似泄露 | 轮换 `BETTER_AUTH_SECRET` → 全员重新登录 → 排查异常登录 | 轮换期间所有会话失效 |

**当前没有应用层备份脚本**：备份与恢复是 Neon 侧能力，操作步骤在 [ops-target](../ops-target.md) §6.1–6.2 与 [runbooks](../guides/runbooks.md) 里，**尚未演练**。这也是「可运维性」目标只写到「一次发布 = 合并」而没有 RPO/RTO 的原因，缺口登记在 [13-风险与演进规划](./13-风险与演进规划.md)。
