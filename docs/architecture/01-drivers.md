## 1. 目标与约束

### 1.1 架构目标

| # | 目标 | 可验证的判据 |
|---|---|---|
| G1 | 单组织数据不可被跨组织访问 | 隔离测试：换一个 `organizationId` 查询必须返回 0 行 |
| G2 | 十万级人丁的谱系图可交互 | 首屏 ≤ 1.5s，拖拽 ≥ 45fps（1000 节点） |
| G3 | 一人一套代码可维护 | 新增一个业务实体 ≤ 3 个文件 + 1 个迁移 |
| G4 | 故障可定位 | 每个错误响应带 `request_id`，能在日志里串起完整链路 |
| G5 | 基础设施成本可控 | 月成本 ≤ ¥900（百级组织规模） |
| G6 | M1 的每一行代码都在为 M2 铺路 | 编目结构、`cover_spec`、`hide` 字段现在就正确，M2 只加渲染不改模型 |

> **G2 与容量的关系**：`prd.md` §7 的容量是**组织级**上限（人丁 ≤ 50 万），不是单谱系上限。G2 的「十万级」指的是组织内人丁总量。单谱系规模与画布同时可见节点数是另外两个约束，见 [05-data §8.5](./05-data.md) 与 [07-quality](./07-quality.md)。

### 1.2 约束

| 类型 | 约束 |
|---|---|
| 团队 | 1–3 人全栈，无专职运维、无 DBA |
| 规模 | 百级组织、十万级人丁/组织、峰值 QPS < 50 |
| 合规 | 家谱含在世人口信息，数据不得跨组织泄露 |
| 交付 | M1 只做「录入与结构化」，不做渲染、分享、协作 |
| 运维 | 使用 Vercel + Neon 托管，无专职运维；允许分钟级发布中断 |

### 1.3 非目标

微服务、事件驱动、多 region 双活、实时协同（CRDT）、插件化模板市场、字段级权限。理由见 [decisions/](../decisions/README.md)。

## 2. 这些驱动因素如何落到设计上

架构文档的价值在于**可追溯**：每个重要设计都应该能回答「它服务于哪个目标」。下表是本文档集中唯一的一处映射。

| 目标 | 主要设计手段 | 在哪份文档 |
|---|---|---|
| G1 隔离 | RLS + 应用层过滤 + 复合外键；组织不入 JWT | [05-data §8.2](./05-data.md) · [ADR-0006](../decisions/0006-rls-isolation.md) |
| G2 画布性能 | 纯函数布局 + 按代渲染窗口 + `onlyRenderVisibleElements` | [04-runtime §6.3](./04-runtime.md) |
| G3 可维护 | 模块化单体 + 垂直切片 + 每表单一 owner | [03-components §4](./03-components.md) |
| G4 可定位 | 结构化日志 + `request_id` 贯穿 | [06-crosscutting §9.3](./06-crosscutting.md) |
| G5 成本 | 托管 Vercel + Neon；零后台任务、零队列、零缓存层 | [02-context §3](./02-context.md) |
| G6 铺路 M2 | 编目引用真外键、`cover_spec` 结构化、`hide` 字段 | [05-data §8.4](./05-data.md) |

> **G3 的判据需要一次修订**：现行判据「≤ 3 个文件 + 1 个迁移」在实践上不可达——schema、迁移、query、action、页面、测试至少 6 处。建议改为「≤ 5 个源文件 + 1 个迁移 + 1 处状态更新」，并把可执行清单写进 [guides/add-a-feature](../guides/add-a-feature.md)。这是待决策项，见 [08-evolution](./08-evolution.md)。
