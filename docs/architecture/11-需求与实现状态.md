## 1. 产品定位与范围

### 1.1 定位

面向**家族修谱场景**的在线谱系编纂平台。一个组织（一个家族或一个修谱工作室）在云端建立「云谱空间」，录入世系、撰写谱文、编排谱书目录。

**M1 只解决「把信息结构化地存下来」。** 呈现（预览、成书、分享）与协作（编辑锁、多人在线）是 M2 之后的事。

### 1.2 目标用户

| 用户 | 特征 | 核心诉求 |
|---|---|---|
| 修谱主事人 | 家族中负责修谱的长辈或热心人，60 后为主 | 把散落在纸质族谱、口述、微信里的信息结构化存下来 |
| 修谱工作室 | 承接多个家族修谱业务的小团队（2–5 人） | 一个账号服务多个客户，数据互不串 |
| 族内协作者 | 各房支的联络人，负责录入本房人丁 | 只改自己那一支，不怕改坏别处 |

### 1.3 价值主张

| 对比对象 | 差异 |
|---|---|
| 纸质族谱 | 可检索、可增量修订、不惧损毁 |
| 通用在线文档 | 原生表达世系关系（父子、配偶、世次、字辈），不是画表格 |
| 本地修谱软件 | 免安装、多人共享同一份数据 |

### 1.4 不做什么

不做社交、不做 DNA 检测、不做家族电商、不做 AI 自动生成族谱内容。产品边界是**记录**，M1 阶段连呈现都不做。

### 1.5 M1 范围

#### 1.5.1 M1 包含

账号（邮箱密码）、**注册即得默认组织**、成员与邀请、云谱空间、分类、谱系与人丁（四种新增方式）、谱文、谱书与编目。

#### 1.5.2 M1 不包含

| 项 | 原编号 | 原因 |
|---|---|---|
| 手机号验证码登录 | — | 需要短信服务商，先验证邮箱密码是否够用 |
| 第三方登录（微信 / Google） | — | OAuth 配置与账号合并逻辑，非核心价值 |
| 版式设置 | FR-PROJ-4 | 没有渲染，版式无消费者 |
| **谱书预览与分享** | FR-PREV-1~6 | 渲染引擎是独立工程，M2 做；M1 只保证编目数据正确 |
| **回收站** | FR-TRASH-1~5 | 数据层软删已就位，缺的是 UI；恢复先由运维兜底 |
| **协作编辑锁** | FR-COLLAB-1~6 | 需要锁表 + 心跳 + fencing，M1 用户量下冲突概率低 |
| **媒体上传** | FR-MEDIA-1~5 | 头像、封面图仍不做；谱文正文插图已随 [specs/002-article-authoring](../../specs/002-article-authoring/spec.md) 落地（图片只进谱文正文，见 §5.5） |
| 邮件通道 / 自助密码找回 | — | M1 不接入邮件投递；忘记密码只能人工处理 |
| PDF 排版成书 | — | 排版引擎与字体授权，M3 单独做 |
| 任何后台任务、定时器 | — | 无必要 |
| OCR 识别老谱 | — | 识别质量不可控 |
| 微信小程序 | — | Web 优先 |
| GEDCOM 导入 | — | 用户量不足；单支世系导出已提前到 M2，见 [ADR 0017](../decisions/0017-single-branch-export-gedcom7.md) |
| 站内信 / 通知中心 | — | 无邮件通道，邀请靠手动复制链接 |
| 客户自助数据导出（整库） | — | 与「单支世系导出」不同：整库导出走合同 + 手工 `pg_dump` 兜底 |

#### 1.5.3 M1 的已知缺口

砍掉上面这些之后，M1 有 6 个必须承认的缺口：

| # | 缺口 | 影响 | 缓解 |
|---|---|---|---|
| 1 | 看不到成品 | 用户录完不知道长什么样 | M2 第一块由 [谱系录编与实时预览专项规格](../../specs/001-lineage-edit-preview/spec.md) 补齐（边录边看）；M1 期间用编目顺序 + 世系表视图给「结构感」 |
| 2 | 无法分享 | 族人看不到 | 暂用截图 / 导出图片沟通 |
| 3 | 两人同时编辑会互相覆盖 | 数据可能被旧内容覆盖 | 界面提示「建议一人先编辑完」；M2 加锁，[ADR 0002](../decisions/0002-no-edit-lock.md) |
| 4 | 删了找不回 | 误删需运维介入 | 软删兜底 + [运维手册](../guides/runbooks.md)；M2 加回收站 |
| 5 | 忘记密码无法自助找回 | 只能联系运维人工处理 | 注册时提示妥善保管密码；M2 接入邮件后补找回流程 |
| 6 | 日志保留期外无法逐条追溯修改 | 纠纷或合规审计缺少细粒度记录 | 软删 + PITR/备份兜底；有明确需求时再引入审计表 |

这 6 条要写进销售话术与帮助文档，不能假装不存在。

#### 1.5.4 后续里程碑

| 阶段 | 主题 |
|---|---|
| M2 | 谱系录编与实时预览（专项）、谱书预览与分享、回收站、编辑锁、媒体上传、版式设置、单支世系导出（GEDCOM 7） |
| M3 | PDF 排版成书、字体授权 |
| M4 | 手机验证码 / 第三方登录、邮件通道与密码找回、实时协同、OCR |

**M2 专项的现行规格**：[`specs/001-lineage-edit-preview/spec.md`](../../specs/001-lineage-edit-preview/spec.md) 是权威来源（2026-11-01 澄清后范围收缩到「把录入闭环做到可交付」）；其输入草案原样保存在 [`source-prd.md`](../../specs/001-lineage-edit-preview/source-prd.md)；被它取代的历史底稿（含视频 ASR/OCR 证据与逐条设计理由）在 [archive/prd-lineage-editing-preview.md](../archive/prd-lineage-editing-preview.md)。本文件 §5.4 的 `FR-LIN-*` 仍是 M1 的验收基线，M2 增量不在此重写。

## 2. 术语

| 术语 | 英文标识 | 定义 |
|---|---|---|
| 组织 | `organization` | 隔离单位。一个家族或一个修谱工作室 |
| 云谱空间 | `project` | 组织内的一套族谱资料集合。一个组织可有多个 |
| 谱系 | `lineage` | 一棵世系树。一个云谱空间可有多个 |
| 人丁 | `node` | 谱系中的一个人。含血亲与配偶 |
| 世次 | `generation` | 第几世。始祖为 1 |
| 字辈 | `generation_words` | 用于命名的辈分用字序列 |
| 谱文 | `article` | 独立的文章：谱序、凡例、传记、像赞 |
| 谱书 | `book` | 一本书的元信息与封面配置，**不含正文** |
| 编目 | `book_catalog` | 谱书的目录，引用谱系或谱文 |

**「谱书不含正文」是核心设计**：书的内容由编目引用谱系与谱文构成。改一次谱系，多本书同时更新——这个结构在 M1 就要建对，虽然 M1 还不渲染它。

## 3. 角色与权限

### 3.1 角色

角色只有 4 个，全部在**组织级**。不存在项目级角色。

| 角色 | 说明 | 典型使用者 |
|---|---|---|
| `owner` | 组织所有者，唯一 | 建组织的人 |
| `admin` | 管理员 | 修谱主事人 |
| `editor` | 编辑者 | 各房支联络人 |
| `viewer` | 只读 | 审核者、顾问 |

### 3.2 能力矩阵

| 能力 | owner | admin | editor | viewer |
|---|:--:|:--:|:--:|:--:|
| 查看内容 | ✅ | ✅ | ✅ | ✅ |
| 编辑谱系 / 人丁 | ✅ | ✅ | ✅ | — |
| 撰写谱文 | ✅ | ✅ | ✅ | — |
| 编排谱书 / 编目 | ✅ | ✅ | ✅ | — |
| 删除内容（谱文 / 谱书 / 人丁） | ✅ | ✅ | ✅ | — |
| 删除谱系 | ✅ | ✅ | — | — |
| 创建 / 删除云谱空间 | ✅ | ✅ | — | — |
| 邀请成员 | ✅ | ✅ | — | — |
| 修改成员角色 / 移除成员 | ✅ | ✅ | — | — |
| 组织设置 / 停用 | ✅ | — | — | — |
| 转让所有权 | ✅ | — | — | — |

### 3.3 权限实现（按代码）

代码用**权限字符串**判断，不直接判角色：`hasPermission(role, '<permission>')`。业务代码里不出现 `role === 'owner' || role === 'admin'` 这类比较。

权限字符串共 10 个，与 §3.2 一一对应（定义在 `lib/auth/access-control.ts` 的 `ORG_PERMISSIONS`）：

| 权限字符串 | 对应 §3.2 的能力 | owner | admin | editor | viewer |
|---|---|:--:|:--:|:--:|:--:|
| `content.read` | 查看内容 | ✅ | ✅ | ✅ | ✅ |
| `lineage.write` | 编辑谱系 / 人丁 | ✅ | ✅ | ✅ | — |
| `lineage.delete` | 删除谱系 | ✅ | ✅ | — | — |
| `article.write` | 撰写谱文 | ✅ | ✅ | ✅ | — |
| `book.write` | 编排谱书 / 编目 | ✅ | ✅ | ✅ | — |
| `project.write` | 创建 / 删除云谱空间 | ✅ | ✅ | — | — |
| `member.invite` | 邀请成员 | ✅ | ✅ | — | — |
| `member.manage` | 修改成员角色 / 移除成员 | ✅ | ✅ | — | — |
| `org.settings` | 组织设置 / 停用 | ✅ | — | — | — |
| `org.transfer` | 转让所有权 | ✅ | — | — | — |

角色到权限的映射**逐项列举，没有通配符**：

- `roles` 用 Better Auth 的 `createAccessControl(statement)` + `ac.newRole({...})` 为四个角色分别声明「能对哪些资源做哪些操作」（`organization` / `member` / `invitation` / `content` / `lineage` / `article` / `book` / `project`）。
- `PERMISSION_REQUESTS` 把每个业务权限字符串翻译成一次精确的 access-control 请求，例如 `'lineage.delete' → { lineage: ['delete'] }`。
- `hasPermission(role, permission)`（`lib/auth/permissions.ts`）返回 `roles[role].authorize(PERMISSION_REQUESTS[permission]).success`，是纯函数、不查库；事务内复核角色用 `getOrgRoleInTx()`。
- 拒绝文案集中在 `lib/auth/permissions.ts` 的 `PERMISSION_DENIED_MESSAGES`，按权限给出中文提示（如 `'lineage.delete': '只有所有者或管理员可以删除谱系'`）。

> 目标设计曾写成 `owner: ['*']` 的通配 + 「遇到 `*` 直接放行」。实现改成了逐项列举：通配会让「owner 能做什么」无法从代码读出来，也无法在评审时对照 §3.2 的矩阵；现在每条权限的四个角色取值都能在 `access-control.ts` 里逐行核对。

## 4. 信息架构

### 4.1 对象模型

```
组织 organization
├── 成员 / 邀请
└── 云谱空间 project
    ├── 分类 folder（谱系 / 谱文 / 谱书 三棵树）
    ├── 谱系 lineage ── 人丁 node
    ├── 谱文 article
    └── 谱书 book ── 编目 book_catalog
```

### 4.2 导航

| 层级 | URL | 内容 |
|---|---|---|
| L0 | `/dashboard` | 我所属的组织列表 + 最近访问 |
| L1 | `/dashboard/org/[orgSlug]` | 组织概览、成员、设置 |
| L2 | `/dashboard/project/[projectRef]` | 云谱空间首页：谱系 / 谱文 / 谱书 |
| L3 | `/dashboard/project/[projectRef]/lineages/[id]` | 谱系图编辑器 |
| L3 | `/dashboard/project/[projectRef]/articles/[articleId]` | 谱文编辑器（三区：分类树 / 正文 / 页列表）· 已实现 |
| L3 | `/dashboard/project/[projectRef]/books/[id]/catalog` | 谱书编目三栏（目标路由） |

`projectRef` 全局唯一；项目页按 `projectRef` + 当前用户解析 scope，不要求在 URL 里重复 `orgSlug`。

`orgSlug` 与 `projectRef` 都是 20 位 `[0-9a-z]` 随机公开 ID，由服务端生成且不可修改；它们只用于定位，不是授权凭证，服务端解析时必须同时按当前用户的成员关系过滤。

公开页面只有营销首页 `/` 与登录 / 注册；M1 没有匿名业务数据页、分享页或公开 API。

> 表中标「目标路由」的谱书编目 L3（`/books/[id]/catalog`）尚未建；谱书列表页仍渲染占位 `EmptyState`。谱文列表与 `articles/[articleId]` 三区编辑器已实现（见同行 L3 与 §7 FR-ART）。现行路由清单与各页面的实际形态见 §8.3。

## 5. 功能需求

需求编号规则 `FR-<模块>-<序号>`，共 43 条，覆盖六个模块。每条含验收标准，验收标准是可测的。**本节只写需求，不写状态**；某条做到哪一步看 §7.2 的矩阵。

### 5.1 FR-AUTH 账号与认证

M1 只支持**邮箱 + 密码**。手机验证码与第三方登录见 §1.5.2。

M1 **不接入邮件通道**：注册无需等待验证邮件，忘记密码也不能自助找回；邀请通过手动复制的链接完成。

| # | 需求 | 验收标准 |
|---|---|---|
| FR-AUTH-1 | 邮箱 + 密码注册 | 密码 ≥ 8 位含字母数字；注册成功即登录，无需等待验证邮件 |
| FR-AUTH-2 | 邮箱 + 密码登录 | 邮箱与密码正确即可登录；不存在的邮箱与密码错误使用同一文案 |
| FR-AUTH-3 | 会话保持 | 关闭浏览器再打开仍登录；Better Auth 数据库会话 7 天有效、`updateAge` 1 天滑动续期；会话被删除或撤销后立即失效 |
| FR-AUTH-4 | 登出 | 登出后当前会话立即失效，其他设备不受影响 |
| FR-AUTH-5 | 登录失败限流 | 同一来源 + 账号在 15 分钟内失败 10 次后，短时拒绝登录；计数保存在应用进程内，不持久化，多实例下为尽力而为；错误文案统一为「账号或密码错误」 |
| FR-AUTH-6 | 修改密码（登录态） | 验证当前密码；成功后撤销其他设备会话，当前设备保持登录 |

### 5.2 FR-ORG 组织与成员

| # | 需求 | 验收标准 |
|---|---|---|
| FR-ORG-1 | **注册即得默认组织** | 账号创建成功后自动生成 1 个组织，用户为 `owner`，直接可用，不需要额外「创建组织」步骤 |
| FR-ORG-2 | 新建额外组织 | 填名称即可；`slug` 由服务端生成（20 位 `[0-9a-z]` 随机公开 ID），全局唯一且不可修改 |
| FR-ORG-3 | 多组织切换 | 一个账号可属于多个组织；切换组织不重新登录 |
| FR-ORG-4 | 邀请成员 | 生成一次性邀请链接 / token，7 天有效，由邀请人手动复制；接受后成为指定角色（不能邀 owner）；不发邮件 |
| FR-ORG-5 | 修改成员角色 | owner/admin 可改；不能把最后一个 owner 降级 |
| FR-ORG-6 | 移除成员 | 移除后该成员立即失去访问权；其创建的内容保留 |
| FR-ORG-7 | 组织设置 | 仅可修改名称；`slug` 是 URL 标识，不可修改；仅 owner 可改 |
| FR-ORG-8 | 组织停用 / 归档 | `suspended` 状态下写操作返回 `ORG_SUSPENDED`、只读放行；`closed`/`deleted_at` 表示归档并从控制台隐藏。M1 UI 只提供归档入口 |

**FR-ORG-1 的默认值**

| 项 | 规则 |
|---|---|
| `name` | 取邮箱 `@` 前缀，如 `chen@x.com` → `chen`；为空则「我的家族」 |
| `slug` | 20 位 `[0-9a-z]` 随机公开 ID，由数据库默认值生成，全局唯一且不可修改 |
| `role` | `owner` |
| 时机 | 与账号创建**同一事务**，由数据库触发器完成 |

用户不需要理解「组织」这个概念就能开始用——**先可用，再理解**。

### 5.3 FR-PROJ 云谱空间

| # | 需求 | 验收标准 |
|---|---|---|
| FR-PROJ-1 | 创建云谱空间 | 填项目名、姓氏、地区、主题名，设置状态、重要等级与可选备注；姓氏与主题名创建后不可修改；项目名 ≤24 字符；服务端自动生成 20 位 `ref` 作为 URL 第二段 |
| FR-PROJ-2 | 多个云谱空间 | 一个组织可建多个，数量不限 |
| FR-PROJ-3 | 分类管理 | 三种类型（谱系 / 谱文 / 谱书）各自独立树，最多 3 层；删除分类不影响其中的内容（变为「未分类」） |

### 5.4 FR-LIN 谱系与人丁

这是产品的核心模块。

| # | 需求 | 验收标准 |
|---|---|---|
| FR-LIN-1 | 创建谱系 | 填谱系名称（≤24 字）、所属分类、地区、可选郡望堂号与备注；姓氏与主题名继承云谱空间、不可修改；创建后进入空谱系并引导录入始祖 |
| FR-LIN-2 | 录入始祖 | 空谱系上点击「添加始祖」，生成第一个节点，世次 = 1 |
| FR-LIN-3 | 添加配偶 | 在任意血亲节点上添加；配偶不占世次，不参与世系路径 |
| FR-LIN-4 | 添加兄弟 | 在节点上添加同辈；继承父节点，世次相同 |
| FR-LIN-5 | 添加子女 | 在节点上添加子代；世次 +1，可连续添加多个 |
| FR-LIN-6 | 编辑人丁信息 | 姓名、字号、性别、生卒、葬地、行传、自定义字段 |
| FR-LIN-7 | 删除人丁 | 删除节点连带其全部子孙；一次操作作为一组软删，从界面消失（**M1 无恢复界面**） |
| FR-LIN-8 | 移动人丁 | 改挂到另一个父节点；重算该子树世次与路径 |
| FR-LIN-9 | 谱系图交互 | 拖拽平移、滚轮缩放、点击选中、双击编辑；1000 节点下 ≥ 45fps |
| FR-LIN-10 | 按代加载 | 超过 500 节点的谱系默认只渲染前 5 代，向右平移或点按钮每次追加 5 世 |
| FR-LIN-11 | 人丁搜索 | 按姓名模糊搜索，结果定位到画布节点 |
| FR-LIN-12 | 字辈提示 | 录入姓名时按世次提示对应字辈用字 |
| FR-LIN-13 | 世系表视图 | 表格形式按世次列出全部人丁，支持打印视图（不含 CSV / PDF 导出） |

**FR-LIN-7 的删除语义**：M1 采用**软删**（`deleted_at`），不物理删除，但**不提供回收站界面**。误删的恢复由运维在数据库层面完成。

这样取舍的原因：软删是零成本的保险，硬删是不可逆的灾难。家谱数据的一次误删，对一个家族是不可接受的损失。UI 可以后补，数据没了就补不回来。见 [ADR 0004](../decisions/0004-soft-delete-forever.md)。

- `auth` schema 的 `SECURITY DEFINER` 辅助函数：`auth.has_org_role()`、`auth.archive_organization()` 等；旧的自研认证函数已删除。

- 最后 owner 保护触发器 `trg_org_member_last_owner_delete` / `trg_org_member_last_owner_update`。
- `FORCE ROW LEVEL SECURITY`：`app_rw` 以及表属主都受策略约束；迁移角色通过 `SET LOCAL ROLE app_rw` 降权后查询。
- 扩展 `ltree`、`pg_trgm`、`btree_gist`；GiST 用于 `node` 的 `path` 索引。人丁与谱文标题搜索都在客户端；`idx_node_search` / `idx_article_search` 已删除。`pg_trgm` 扩展保留，正文检索（FR-ART-5 后置项）落地当天再建索引（[ADR 0011](../decisions/0011-search-boundary-node-client-article-trgm.md)）。
- `idx_node_spouse_sort`：手写 custom migration 新增的 B-tree 部分索引（`deleted_at IS NULL`，列 `(organization_id, spouse_of_id)`），服务 `nextSpouseSort` 的 `max(sort)` 查询，避免配偶写入在 `FOR UPDATE` 锁内扫描整谱系。它只活在迁移里，不进 `lib/db/schema/`，与已删除的 `idx_node_search` 同思路——每个索引都有消费者。
- 登录角色存在时补 `GRANT app_rw TO app` / `GRANT auth_service TO auth_runtime`；角色创建仍属本地 / 运维步骤。
- 租户列不可变（[ADR 0016](../decisions/0016-tenant-columns-immutable.md)）：`app.forbid_tenant_move()` + 16 个 `trg_<table>_tenant_immutable` 触发器（`organization_member`、`invite`、`project`、`folder`、`lineage`、`node`、`person`、`person_name`、`family`、`family_partner`、`family_child`、`event`、`article`、`book`、`book_catalog`、`activity_logs`）挡住「双组织用户把行搬到另一个组织」——RLS 的 `WITH CHECK` 只看新值，policy 无法比较新旧行。改归属列报 SQLSTATE `42501`；结构关系列（`parent_id`、`spouse_of_id`、`folder_id` 等）保持可写。`USAGE` / `EXECUTE` 同时授 `app_rw` 与 `auth_service`。新增组织级表必须挂这个触发器，`tests/integration/tenant-immutability.test.ts` 断言精确的 16 张表。
- 事实层六张表全部 `ENABLE` + `FORCE ROW LEVEL SECURITY`、三策略、无 `DELETE` 授权，并各挂租户列不可变触发器；`project` 另有 `allow_consanguineous_marriage`；`app.check_family_blood_side()` 保证「至多一个 `blood` 配偶」（下界故意不约束）。
- 回填与对账：`lib/db/backfill/fact-layer.ts` + `fact-layer-rules.ts`（单事务、只写事实层、`person.legacy_node_id` 作锚点），CLI `data/backfill-fact-layer.ts`（`pnpm data:backfill:fact --org <uuid>`）；`lib/db/backfill/reconcile-fact-layer.ts` 从 `node` 重算十四项计数再与事实层比较（`RECONCILE_CHECKS`：人数、出生名、字号名、`primary_name` 指针、`person` 软删、家庭、配偶、子女边、孤儿子女、生 / 卒 / 葬事件、无内容事件、事件主体；其中家庭 / 配偶 / 子女边是把回填的分层约定重写一遍，只能发现实现漂移），CLI `data/reconcile-fact-layer.ts`（`pnpm data:reconcile:fact`）。两个脚本以迁移角色直连、启动时断言 `rolsuper` / `rolbypassrls`，只能人工执行。

### 8.4 Route Handler

当前 7 个 Route Handler：4 个只读业务路由 + 3 条谱文图片通道。

- `GET /api/health`（数据库 `SELECT 1`；正常 200、不可用 503）
- `GET /api/orgs`
- `GET /api/orgs/[orgId]/projects`
- `GET /api/user`（DTO 仅为 `{ id, name, email }`）
- `GET /api/media/[...key]`（谱文图片读取授权入口：按 pathname 里的 `orgId` 复核成员关系并确认谱文未软删，未登录 / 非成员 / 形状不合法 / 已删 / 缺失一律 404；命中时 Blob 模式回 `302` 到私有桶签名 URL（`presignUrl` 本地 HMAC 签发、delegation 按进程缓存），兜底驱动直接发字节，`Cache-Control: no-store`，见 [ADR 0019](../decisions/0019-media-storage.md)）
- `POST /api/blob/upload`（Vercel Blob 客户端直传的令牌通道，只在 blob 模式注册；未登录 401、越权与不存在一律 404（不泄露谱文存在性）、模式不匹配 404）
- `POST /api/media/upload`（本地/CI 的兜底上传通道，只在 fs 模式注册；400 / 401 / 404 / 413 / 415）

后三条是「写入只走 Server Action」的唯一例外：单张 10MB 的图片字节同时超过 Server Action 的 1MB 请求体上限与 Vercel 函数的 4.5MB 上限，装不进去（契约见 [05 §7](./05-接口与集成设计.md)）。

前四个业务路由未登录时都返回 `401 { error: 'Unauthorized' }`；组织级项目列表先校验成员，非成员返回 403，`orgId` 不是合法 UUID 时返回 404；项目 DTO 为 `{ id, name, ref }`。客户端 `lib/fetcher.ts` 对非 2xx 响应抛错，错误对象带 `status`。所有路由通过 `withApiLogging()` 导出：生成或透传 `x-request-id`，记录 `duration_ms`，未捕获异常返回 JSON 500。认证类 handler 数量为 0，不新增 `/api/auth/*`；这些路由是过渡形态，见 [ADR 0008](../decisions/0008-read-only-route-handlers.md)。

### 10.1 实现层风险

风险登记簿（R1–R29，含缓解措施与状态）在 [12-风险与演进规划](./12-风险与演进规划.md)，那里是风险判定的唯一来源。本节只记**与实现状态直接相关**的事实，并标出对应编号；没有对应编号的是尚未进登记簿的实现观察。

### 12.3 判定纪律

- 只有代码、迁移、测试都落地后，状态才能从 🟡 / ⬜ 改为 ✅；「表已建、索引已加、外键已加」不算实现入口，见 §7.1。
- 表数量、迁移编号、测试文件数 / 用例数**不手抄**：分别以 `lib/db/schema/*.ts` 的 `pgTable`、`lib/db/migrations/meta/_journal.json`、`pnpm test` 输出为准。本文件只写口径与当前核对结果。
