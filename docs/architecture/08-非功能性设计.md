# 非功能性设计

> **回答什么问题**：性能、可用性、可扩展性、可维护性承诺到什么程度？靠什么证明？先坏在哪？
> **读者**：开发 · 运维　**长度上限**：4 页
> **目标 vs 现状**：本文描述当前实现（as-is）。目标设计见 [PRD](../prd.md) 与 [decisions](../decisions/README.md)。

质量属性的定义与业务目标见 [02-架构目标与约束](./02-架构目标与约束.md)；本文只写目标值、现在的实际手段、以及**谁在自动检查**。目标值只写能从脚本或配置里读出来的数，读不出来的写定性判定，不编造。

## 质量属性与目标

| 属性 | 目标 | 现在的实际手段 | 未达标时的症状 |
|---|---|---|---|
| 性能（读） | 首屏一个请求内完成上下文解析与数据查询 | RSC 直出 + `requireOrgContext` 请求级缓存 + 按渲染单元合并查询 | 首屏出现瀑布式多次往返，TTFB 随请求数上升 |
| 性能（交互） | 画布拖拽不卡；新鲜度只由 `staleTime`（30 秒）决定 | 客户端渲染窗口限制同屏代数 + 纯函数布局 + 单一 `staleTime` | 单 hook 上出现 `refetchOnMount: 'always'`，同一份数据被打两遍 |
| 可用性 | 单区域部署，无降级路径；实例无状态可水平扩 | 无状态函数 + `/api/health` 探针 + 数据库托管 | 数据库不可用时整站 500，没有只读降级模式 |
| 可扩展性 | 组织数与人丁数增长时先坏在明确的点上 | 见下方「可扩展性边界」三处 | 症状出现时才发现没有分页/归档 |
| 安全 | 跨组织读取 0 行；越权与信息泄露在评审第一顺位 | 应用层 `orgId` 过滤 + `withOrg` 内 RLS + 复合外键 + 触发器 | 集成测试的隔离用例变红，或 `verify:deploy` 的 RLS 检查失败 |
| 可维护性 | 单文件 ≤ 400 行；依赖方向三条硬规则 | `pnpm arch:check`（F6/F7）+ Biome `noRestrictedImports` | `arch:check` 报违规；豁免名单只能缩不能涨 |
| 可测试性 | 关键查询与事务模块覆盖率高于全局门槛 | `pnpm test:coverage`：全局 lines 60 / statements 60 / functions 55 / branches 50；`lib/db/queries/**`、`lib/db/services.ts`、`lib/lineage/node-services.ts` 另设 lines 70 / functions 60 | 覆盖率门槛下降，或豁免范围扩大 |
| 可运维性 | 一次发布 = 合并到 `main`；一次回滚 = 重新部署上一版本 | CI 的 13 个阻塞阶段全绿才可合并；迁移与业务代码分开提交 | 靠人工步骤发布，或回滚需要手改数据库 |
| 一致性 | 多步写要么全成要么全不成 | 单事务 + 约束 + 触发器兜底 | 出现「有账号没有组织」「没有 owner 的组织」这类中间态 |

**明确没有目标的**：没有跨区域容灾目标（单区域部署）、没有 RPO/RTO 承诺（恢复靠 Neon 分支与 PITR，没有演练）、没有 SLA（没有外部探针与错误预算）。这些是已知缺口，登记在 [13-风险与演进规划](./13-风险与演进规划.md)，不在本文件承诺。

## 容量口径

不写具体数字承诺，只写「按什么估、现在被什么卡住」。

| 维度 | 估算方式 | 现在的约束 |
|---|---|---|
| 组织数 | 每个注册用户自动获得一个组织，所以组织数 ≈ 用户数 | 无上限约束；列表查询按成员关系过滤，组织多了之后组织切换器与 `/api/orgs` 会先变大 |
| 单组织成员 | 邀请链接 + 4 角色 | `listOrgMembers` 走 Better Auth `api.listMembers` 全量返回，**没有分页**——成员上百后成员页会一次拉全量 |
| 单谱系人丁 | 按 `lineage.node_count` 计数 | `getNodes` 一次取该谱系**全部**未删节点，无 limit 无分页；渲染窗口（`generationLimit`）只限制同屏渲染的代数，不减少传输量。这是最先坏的一点 |
| 活动日志年增长 | 每次关键写一条 `activity_logs` | 没有归档、没有分区、没有保留期清理；表只增不减 |
| 事实层体积 | `person`/`family`/`event` 六表由回填 CLI 从 `node` 派生 | 现在是**只回填不双写**：应用写路径不维护事实层，体积 = 一次回填的快照 |
| 函数并发 | Vercel 按请求自动扩 | 每实例连接池上限 5；实例数上升时先撞数据库连接上限，不是 CPU |
| 数据库连接 | `attachDatabasePool` 在实例冻结时回收连接 | 只在 Vercel 生效；本地与 CI 用直连驱动，不受这层保护 |

## 可扩展性边界

会先坏的三个点，按发生顺序：

1. **单谱系人丁全量加载**。`getNodes` 无分页，整条谱系一次进内存再进浏览器；渲染窗口只省渲染不省传输。先坏的症状：大谱系打开变慢、内存上涨、客户端解析布局耗时线性增长。修法是服务端按代取窗口，属于结构性改动。
2. **活动日志无归档**。表只增不减，且每次关键写都插一行。先坏的症状：`activity_logs` 成为最大表，活动页查询变慢，备份体积与恢复时间被它主导。修法是加保留期或分区，需要先决定保留策略。
3. **连接池与并发**。每实例池上限 5，实例数增长时先撞数据库连接上限。先坏的症状：高并发下出现连接获取超时与 500，而 CPU 与内存都还宽裕。修法是换 pooled 端点并复核所有长事务。

不在边界内的：读写分离、多区域、缓存层、外部搜索索引——这些都有明确的触发条件写在 [01-架构总览](./01-架构总览.md) 的「架构刻意不做什么」里，触发前不建。

## Fitness functions

只有下表中的条目算约束：每条都有一个会变红的执行者。**没有执行者的约束不是约束，删掉而不是承诺。**

| 编号 | 约束 | 执行者 | 违反时 |
|---|---|---|---|
| F1′ | `lib/db/**` 不得 import `next/*` | Biome `noRestrictedImports`（`pnpm check`） | 提交被 lint 挡住 |
| F2′ | 客户端组件不得 import `@/lib/db/*` 与 `drizzle-orm` | Biome `noRestrictedImports`（`pnpm check`） | 提交被 lint 挡住 |
| F2″ | `lib/db/queries/**` 不得 import `@/lib/*/actions` | Biome `noRestrictedImports`（`pnpm check`） | 提交被 lint 挡住 |
| F3 | 每张业务表都启用并强制 RLS | `scripts/verify-deployment.mjs` 查 `pg_class.relrowsecurity` | `verify:deploy` 失败 |
| F5 | 业务表策略必须调 `auth.has_org_role()`，不得用裸子查询 | `scripts/verify-deployment.mjs` 查 `pg_policies` | `verify:deploy` 失败 |
| F6 | 单文件 ≤ 400 行（扫 `app/`、`components/`、`lib/`、`hooks/`） | `scripts/check-file-size.mjs`（`pnpm arch:check`）；存量豁免带行数预算，只许缩不许涨 | `arch:check` 失败；豁免过期也失败 |
| F7 | `process.env` 只在 `lib/config.ts` 读；根入口只放行 `NEXT_RUNTIME`/`NEXT_PHASE` | `scripts/check-env-access.mjs`（`pnpm arch:check`），零豁免 | `arch:check` 失败 |
| F8 | 迁移与 schema 无漂移 | CI `Check migration drift`：重新生成迁移后必须无新文件 | CI 失败 |
| F9 | 文档相对链接、锚点、过期路径、矛盾措辞、文件头字段 | `scripts/check-docs.mjs`（`pnpm docs:check --strict`） | CI 失败 |

配套的两个非编号检查：`scripts/verify-deployment.mjs` 还验证健康检查、安全响应头、`/api/auth/*` 未被路由、登录角色不可绕过 RLS、租户列不可变触发器就位；`tests/docs-consistency.test.ts` 把「文档不得手抄测试数与迁移数」这类规则钉成断言。

## 性能取舍

- **按渲染单元合并查询**，不按组件查：页面在服务端一次取齐该页要用的数据，不把查询散到组件里各查一次。所以同一请求内共享的数据用 React `cache()`（`lib/auth/context.ts`、`lib/lineage/nav.ts`）做请求级记忆化。
- **不产生 N+1**：列表页的关联数据用一次 `IN` 或 `with` 取回，不在循环里查库。这条没有自动检查，靠评审。
- **首屏不走客户端瀑布**：首屏由 RSC 直出并用 `dehydrate` 注入缓存，客户端 `useQuery` 只读已注入的数据；需要客户端刷新时才打只读 Route Handler。
- **画布限制同屏规模**：布局是纯函数，渲染窗口按代裁剪，折叠状态在客户端；服务端不参与渲染决策，也不为此增加接口。
