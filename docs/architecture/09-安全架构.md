## 认证

认证由自托管 Better Auth 负责（[decisions/0007](../decisions/0007-self-hosted-better-auth.md)），表在 `auth` schema，业务代码不直接读写这些表。

| 项 | 当前值 |
|---|---|
| 会话存储 | 数据库会话（`auth.session`），不是 JWT |
| Cookie 缓存 | 关闭（`cookieCache.enabled: false`）——每次校验都查库，撤销即时生效 |
| 过期 | 7 天 |
| 滑动续期 | 1 天（`updateAge`） |
| 密码存储 | scrypt，由 Better Auth 处理；应用层从不接触哈希 |
| 密码长度 | 8–100 |
| 邮箱验证 | 关闭；邮箱只读，不提供改邮箱 |
| 找回密码 | 不提供（没有邮件通道） |
| 改密 | `auth.api.changePassword({ revokeOtherSessions: true })`：当前会话保留，其他设备失效 |
| 删号 | `auth.api.deleteUser`，删前检查该用户是否为任何组织的唯一 owner |
| 组织插件 | `creatorRole: 'owner'`；邀请 7 天过期；`cancelPendingInvitationsOnReInvite: true`；`disableOrganizationDeletion: true`（组织只能归档，不能删） |
| 认证接口 | 不暴露 `/api/auth/*`，不引入浏览器 auth client；只从 Server Action 调 `auth.api.*` |

两条连接是两个角色：业务连接用 `APP_POSTGRES_URL`（登录角色 `app`，事务内 `SET LOCAL ROLE app_rw`），认证连接用 `AUTH_POSTGRES_URL`（登录角色 `auth_runtime`，连接以启动参数固定 `role=auth_service`）。混用会要么写不进 `auth.*`，要么绕过 RLS 读业务表。`AUTH_POSTGRES_URL` 必须是直连端点——pooler 不接受启动参数，配置校验会在启动时拒绝 pooled 地址。

## 会话校验链路

三层，每层职责不同：

- **`proxy.ts` 是乐观门禁**：只检查 `better-auth.session_token` Cookie 是否存在，不存在就 302 到 `/sign-in`。它**不是授权边界**，伪造或过期的 Cookie 会通过这一层。
- **`getSessionUser()` 是权威校验**：`auth.api.getSession` 查库，用 React `cache()` 做请求级记忆化，只返回 `{ id, name, email }` 或 `null`。
- **页面 / Action / Route Handler 内再做组织成员校验**：`requireOrgContext` / `requireProjectContext` 或 `getOrgRole`。

只信 Cookie 存在而不查库 = 伪造与过期会话直接通过；只靠 `proxy.ts` 保护资源 = 绕过路由直接调 Server Action 就失效。这两条是禁止清单里的头两条。

## 授权矩阵

四个角色 × 九个业务权限。**矩阵从 `lib/auth/access-control.ts` 的 `roles` 定义逐个推导**，不是按直觉填的。

| 角色 | `content.read` | `lineage.write` | `article.write` | `book.write` | `project.write` | `member.invite` | `member.manage` | `org.settings` | `org.transfer` |
|---|---|---|---|---|---|---|---|---|---|
| `owner` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| `admin` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | — | — |
| `editor` | ✓ | ✓ | ✓ | ✓ | — | — | — | — | — |
| `viewer` | ✓ | — | — | — | — | — | — | — | — |

判定入口是 `hasPermission(role, permission)`，内部把业务权限映射到 Better Auth 的访问控制请求（`PERMISSION_REQUESTS`）再交给 `roles[role].authorize()`。**业务代码检查权限字符串，不比较角色名**——写 `role === 'owner' || role === 'admin'` 会让矩阵变成两份真相。

三个入口按场景分工：页面用 `requireOrgAccess`（无权限重定向 `/dashboard`）、Action 用 `checkOrgPermission`（返回中文文案）、事务内用 `getOrgRoleInTx`（锁定读复核，避免事务外读到的角色已过期）。权限字符串全集只在 `lib/auth/permissions.ts` 与上表列头出现，别处不重复列举。

## 租户隔离

四层，缺一层都不算隔离：

- **应用层按成员关系过滤**：组织级查询必须带 `orgId`，并通过 `withOrg(userId, fn)` 执行。RLS 是兜底，不是替代品。
- **RLS 兜底**：`app_rw` 上启用并强制行级安全，策略调 `auth.has_org_role()`，不写裸子查询。`verify:deploy` 会查 `pg_class.relrowsecurity` 与 `pg_policies` 两条。
- **复合外键 + 租户列不可变**：子表的 `organization_id` 与外键一起约束，`trg_<table>_tenant_immutable` 触发器阻止改租户列（[decisions/0016](../decisions/0016-tenant-columns-immutable.md)）。
- **公开 ID 不是授权凭证**：URL 里的 20 位 `slug` / `ref` 只用于寻址，解析时必须同时按 `userId` 过滤；非成员与不存在的 ID 一律 404，不泄露存在性。

`withOrg` 内只用 `SET LOCAL`（事务级）。会话级 `SET` 会把角色与用户声明泄漏给下一个借用该连接的请求——这是这套隔离模型最容易踩的坑。

## 威胁建模

| 威胁 | 现在的缓解 | 残余风险 |
|---|---|---|
| 猜 ID 越权读（换别人的 `orgSlug` / `projectRef` / 子资源 UUID） | 公开 ID 按 `userId` 解析 + 应用层 `orgId` 过滤 + RLS + 非成员 404 | 已接受；集成测试覆盖 |
| 越权写（伪造客户端传来的 `orgId` / `projectId` / 角色） | 写入的 UUID 只来自服务端 scope；角色只从数据库成员关系读；事务内 `getOrgRoleInTx` 复核 | 已接受 |
| 会话伪造 / 固定 | Cookie 带 `Secure` + 每次校验查库 + 关闭 cookie cache + 改密撤销其他会话 | 已接受；本地必须用 `localhost`，否则登录不上 |
| 密码泄露 | scrypt 存储，应用不接触哈希；不返回密码；不回显密码 | 没有找回密码与二次验证，撞库只能靠限流 |
| 密钥进客户端 bundle | `BETTER_AUTH_SECRET` 只在服务端 `lib/config.ts` 读取；`process.env` 全仓库只允许这一处（F7） | 已接受 |
| SQL 注入 | 全部走 Drizzle 参数化查询；动态片段用 `sql` 模板绑定；迁移由生成器产出后人工 review | 已接受 |
| 信息泄露（整行用户、堆栈、内部错误） | 出口只传 `SessionUser`；Action 返回中文文案 + 稳定 `code`；API 返回英文 JSON 错误体；日志记 `SQLSTATE` 不记原始错误 | 已接受 |
| 限流绕过 | 进程内滑动窗口：注册 5 次/小时/IP，登录 10 次/15 分钟/IP+邮箱 | **缺口**：重启清零、多实例不共享。不能当安全边界 |
| 无主组织（最后一个 owner 被删） | 应用层预检 + `trg_org_member_last_owner_delete/update` 触发器兜底 | 已接受 |
| 硬删除不可恢复（`organization_member` / `invite`） | `app_rw` 无 `DELETE` 授权；生产清理走工单与备份 | **缺口**：误删只能靠备份恢复，没有行级恢复 |
| 跨站脚本与点击劫持 | CSP 目前是 Report-Only；`X-Frame-Options: DENY`、`nosniff`、`Referrer-Policy`、`Permissions-Policy`、HSTS 已下发 | **缺口**：CSP 未强制（Tailwind/RSC 的内联样式与脚本要先收敛） |

## 数据安全

- **密码不可逆**：scrypt 存储，应用层没有解密路径，也没有「查看密码」入口。
- **日志脱敏**：不记录密码、token、身份证、完整住址；数据库错误只记 `SQLSTATE`，不把原始错误与参数写进日志。
- **出口最小化**：任何出口只传 `SessionUser`（`{ id, name, email }`）；不返回整行用户、不返回 `session.user`、不返回哈希。
- **删除语义要分清**：业务表是软删（`deleted_at`），`organization_member` 与 `invite` 是硬删除。物理删除只能走运维，`app_rw` 没有 `DELETE` 授权。
- **传输与响应头**：HSTS（`max-age=63072000; includeSubDomains`）、`X-Frame-Options: DENY`、`X-Content-Type-Options: nosniff`、`Referrer-Policy: strict-origin-when-cross-origin`、`Permissions-Policy` 关闭摄像头/麦克风/定位；`poweredByHeader: false`。

## 合规与审计现状

**没有独立审计表。** `activity_logs` 是产品活动流，不是审计日志：`organization_id` 可为空（账号级事件），写入是 best-effort（失败只记 warn），没有防篡改、没有保留期承诺、没有导出。所以「谁在什么时候改了什么」的完整追溯**不成立**。

**没有数据主体请求流程**：没有自助导出、没有删除请求入口、没有保留期策略。软删的数据会一直留在库里。

**没有做过合规评估**：没有 GDPR / 个保法评估，没有数据分级文档，没有跨境传输分析。当前的数据形态（姓名、亲属关系、生平文字）属于个人信息甚至敏感信息，但这一点没有在代码或流程上被处理。

做合规之前需要先补三件事：① 一份数据分级与保留期策略（决定 `activity_logs` 与软删数据的寿命）；② 一条真正可用的硬删路径（按组织/按用户，含级联与备份处理）；③ 一个带防篡改与保留期的审计通道，与产品活动流分开。这三件都不在 M1 范围，登记在 [13-风险与演进规划](./13-风险与演进规划.md)。
