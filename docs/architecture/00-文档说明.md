## 这套文档是什么

`docs/architecture/` 是**当前实现**的架构说明：15 份文档描述代码**现在**怎么分层、数据现在怎么存、接口现在长什么样、部署现在跑在哪。它不是目标设计，也不是路线图。

- **目标设计**在 [PRD](../prd.md)（要做什么）与 [decisions](../decisions/README.md)（为什么不做别的方案）。
- **需求状态**只在 [实现状态](../implementation-status.md)：本目录不写「实现了没有」，只写「代码里有什么、怎么搭的」。
- **字段级细节**（列定义、索引、策略体、DTO、错误码、环境变量逐条、命令）仍只在 [数据模型](../data-model.md)、[接口契约](../api.md)、[运维蓝图](../ops-target.md)、[本地搭建](../setup.md) 里。本目录写结构与判断，细节一律链接过去。

判据只有一条：**某条事实变了，需要改几个文件？** 答案必须是 1。会同时影响两份文档的内容，说明它写错了地方。

## 术语表

本表定义一次，其余 14 份文档照用，不再各自解释。

| 术语 | 含义 | 别写成 |
|---|---|---|
| 云谱空间 | 组织（`organization`）在产品里的叫法，一个租户边界 | 「工作区」「家谱空间」「团队」 |
| 组织成员 | `organization_member` 的一行，是**账号**与云谱空间的关系，角色为 `owner`/`admin`/`editor`/`viewer` | 「人丁」 |
| 人丁 | `node` 表的一行，谱系里的一个人物条目 | 「成员」「人物」 |
| 谱系 | `lineage`，一棵人丁树的根与范围 | 「家谱」（家谱指整本谱） |
| 公开 ID | URL 里用的 20 位字符串：`organization.slug`、`project.ref`；UUIDv7 主键只在内部使用 | 不要当授权凭证 |
| 事实层 | `person`/`person_name`/`family`/`family_partner`/`family_child`/`event` 六张表 | 「人丁表」「新表」 |
| 软删 | 业务表的 `deleted_at` 时间戳；查询默认 `isNull(deletedAt)` | 「回收站」（没有回收站 UI） |
| 硬删 | 物理删除，不可恢复：`organization_member`、`invite` | 「软删」 |
| RLS | PostgreSQL 行级安全；业务表用 `app_rw` 角色，策略调 `auth.has_org_role` | 「唯一的隔离手段」 |
| `app_rw` / `auth_service` | 两个数据库登录角色：业务连接 `app` 在事务内 `SET LOCAL ROLE app_rw`；认证连接 `auth_runtime` 固定 `auth_service` | 「一个连接搞定」 |
| `withOrg` | 业务事务包装器，在事务内切角色并按成员关系过滤 | 事务外会话级 `SET` |
| Server Action | 唯一写通道，放在 `lib/<domain>/actions.ts` | 「API」「接口」 |
| Route Handler | `app/api/**/route.ts` 的只读 HTTP 入口 | 「写入口」 |
| RSC | React Server Component，首屏在服务端渲染并直接查库 | 「SSR 页面」 |
| `ActionState` | Server Action 的返回形状：`error` / `success` / `fieldErrors` | 「抛异常 + 前端 catch」 |
| 谱系工作区 | 谱系编辑页的整块交互区域，UI 状态存 zustand | 「工作区」（单独出现时含义不明） |

## 参考标准

结构上借鉴 C4 模型（上下文 / 容器 / 部署三级，见 01 与 06）、ISO/IEC/IEEE 42010 的视图划分（逻辑 / 数据 / 运行 / 部署，见 03–07）与 ADR 格式（见 11 与 [decisions](../decisions/README.md)）。**不强制套用这些标准的术语**：本目录用中文写实际的东西，图是 mermaid，不追求符号一致性。
