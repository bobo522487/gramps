# 架构文档说明

> **回答什么问题**：这套文档是什么、怎么读、术语怎么讲？旧引用怎么翻译成新文件名？
> **读者**：所有人（进入本目录的第一份）　**长度上限**：5 页
> **目标 vs 现状**：本文是文档集入口，本身不描述实现。每份文档头各自声明「目标 vs 现状」；目标设计（要做什么）见 [11-需求与实现状态](./11-需求与实现状态.md) 与 [decisions](../decisions/README.md)。

## 这套文档是什么

`docs/architecture/` 是**唯一一层架构文档集**，共 14 份（编号 00–13）：描述代码**现在**怎么分层、数据现在怎么存、接口现在长什么样、部署现在跑在哪、命令现在怎么用。它同时承担原来写在根级的字段级与操作级细节——表与列、契约与错误码、环境变量与发布顺序、本地命令——这些细节各自只写在对应的一份文档里，不跨文件复制。

- **目标设计**（要做什么、做到哪一步）在 [11-需求与实现状态](./11-需求与实现状态.md)；**为什么不做别的方案**在 [decisions](../decisions/README.md)。
- **结构级事实**（模块边界、依赖方向、表分组、流程步骤、接口清单、部署单元）与**字段级细节**写在同一份文档里：找表与列去 [04-数据视图-数据架构](./04-数据视图-数据架构.md)，找契约与错误码去 [05-接口与集成设计](./05-接口与集成设计.md)，找环境变量与发布顺序去 [06-部署视图-部署架构](./06-部署视图-部署架构.md)，找命令去 [13-本地开发与命令](./13-本地开发与命令.md)。
- **状态**只在 [11-需求与实现状态](./11-需求与实现状态.md) 写一次；本目录其余文档只写「代码里有什么、怎么搭的」，不判断某个功能做完了没有。

判据只有一条：**某条事实变了，需要改几个文件？** 答案必须是 1。会同时影响两份文档的内容，说明它写错了地方。

## 术语表

本表定义一次，其余 13 份文档照用，不再各自解释。

| 术语 | 含义 | 别写成 |
|---|---|---|
| 云谱空间 | 组织（`organization`）在产品里的叫法，一个租户边界 | 「工作区」「家谱空间」「团队」 |
| 组织成员 | `organization_member` 的一行，是**账号**与云谱空间的关系，角色为 `owner`/`admin`/`editor`/`viewer` | 「人丁」 |
| 人丁 | `node` 表的一行，谱系里的一个人物条目 | 「成员」「人物」 |
| 谱系 | `lineage`，一棵人丁树的根与范围 | 「家谱」（家谱指整本谱） |
| 公开 ID | URL 里用的 20 位字符串：`organization.slug`、`project.ref`；UUIDv7 主键只在内部使用 | 不要当授权凭证 |
| 事实层 | `person`/`person_name`/`family`/`family_partner`/`family_child`/`event` 六张表 | 「人丁表」「新表」 |
| 软删 | 业务表的 `deleted_at` 时间戳；查询默认 `isNull(deletedAt)` | 「回收站」（没有回收站 UI） |
| 硬删 | 物理删除，不可恢复：`organization_member`、`invite` | 「软删」 |
| RLS | PostgreSQL 行级安全；业务表用 `app_rw` 角色，策略调 `auth.has_org_role` | 「唯一的隔离手段」 |
| `app_rw` / `auth_service` | 两个数据库登录角色：业务连接 `app` 在事务内 `SET LOCAL ROLE app_rw`；认证连接 `auth_runtime` 固定 `auth_service` | 「一个连接搞定」 |
| `withOrg` | 业务事务包装器，在事务内切角色并按成员关系过滤 | 事务外会话级 `SET` |
| Server Action | 唯一写通道，放在 `lib/<domain>/actions.ts` | 「API」「接口」 |
| Route Handler | `app/api/**/route.ts` 的只读 HTTP 入口 | 「写入口」 |
| RSC | React Server Component，首屏在服务端渲染并直接查库 | 「SSR 页面」 |
| `ActionState` | Server Action 的返回形状：`error` / `success` / `fieldErrors` | 「抛异常 + 前端 catch」 |
| 谱系工作区 | 谱系编辑页的整块交互区域，UI 状态存 zustand | 「工作区」（单独出现时含义不明，见上一行） |

### 术语补充（实现层）

上面覆盖了业务与数据层的核心词。以下是读代码时容易卡住的实现层词汇：

| 术语 | 含义 |
|---|---|
| `ltree` | PostgreSQL 扩展类型，用点分标签表示树路径（如 `a.b.c`）。`node.path` 用它存物化路径，子树查询写成 `<@`，祖先查询写成 `@>` |
| 物化路径 | 把从根到当前节点的路径直接存在行里，读子树不用递归查询；代价是移动节点要重写整棵子树的路径 |
| 部分唯一索引 | 带 `WHERE` 条件的唯一索引。本仓库用它表达「同一组织只能有一个 owner」「同一组织同一邮箱只能有一个待处理邀请」 |
| 复合外键 | 多列外键，用来表达「子行的父行必须属于同一组织/同一谱系」。它是租户隔离的第三层，不是可选的整洁性优化 |
| `SET LOCAL` | 只在当前事务内生效的 `SET`。`withOrg` 用它切到 `app_rw`；会话级 `SET` 会污染连接池里的连接 |
| RLS 策略里的 `auth.has_org_role` | 策略调用的函数，按当前会话用户与目标组织查成员关系。策略本身不写裸子查询 |
| `AsyncLocalStorage` | Node 的请求级上下文容器。`lib/server/request-context.ts` 用它携带 `request_id` 与 `user_id`，日志不需要逐层传参 |
| Flight | React Server Component 的传输协议。`dehydrate` 的首屏数据就是随 Flight 响应一起下发的 |
| HydrationBoundary | TanStack Query 的边界组件，把服务端注入的缓存交还给客户端 `QueryClient` |
| Fitness function | 可自动执行的架构约束检查。清单在 [08-非功能性设计](./08-非功能性设计.md)，那里也是唯一来源 |
| 豁免清单 | `scripts/check-file-size.mjs` 里允许超过 400 行的文件列表。规则是**只许缩小**，新增条目要评审 |

## 文档集的分层约定

现在是**一层文档集**：`docs/architecture/` 的 14 份文档都描述代码当前怎么搭的，不存在「根级事实层 / `architecture/` 差异层」这种目录划分，也不需要读者先判断一份文档属于哪一层。

- **分层在文档头里，不在目录里**：每份文档头自己声明「目标 vs 现状」——是 as-is 描述、还是仍带 M2 目标段。判据是文档头，不是它放在哪个目录。
- **结构级事实与字段级细节同处一份文档**：字段级细节只写在它所属的那一份里（表与列在 04、契约在 05、环境变量在 06、命令在 13），其他文档链接过去而不是抄一遍。
- **状态只有一处**：某个功能到底实现了没有，只看 [11-需求与实现状态](./11-需求与实现状态.md)。架构文档只写结构，不写状态。
- **文档集之外只剩两类材料**：`docs/decisions/`（为什么不做别的方案，含未决项）与仓库根的 `specs/`（M2 专项需求，现行）。历史底稿与评审记录在 `docs/archive/`，不参与 `docs:check`，也不作为事实依据。
