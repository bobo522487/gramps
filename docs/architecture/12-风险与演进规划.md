## 风险登记簿

「状态」只有三种：`已接受`（有意共存，不再投入）、`缓解中`（有兜底但没消除）、`需决策`（不能长期挂着，要拍板）。

| 编号 | 风险 | 影响 | 触发信号 | 现在的缓解 | 状态 |
|---|---|---|---|---|---|
| R1 | Neon 项目低于 PostgreSQL 18 | 建表与插入直接失败（没有 `uuidv7()`） | 部署前置自检 `SELECT uuidv7();` 失败 | 创建项目时选 18+；`verify:deploy` 断言版本 | 已接受 |
| R2 | 画布在 1000+ 节点时的帧率 | 核心体验，直接决定产品可用性 | 真实族谱压测掉帧 | 按代渲染窗口 + `onlyRenderVisibleElements` | 缓解中 |
| R3 | 无编辑锁导致并发覆盖（last-write-wins） | 两人同时编辑，后保存的覆盖先保存的 | 客户反馈覆盖问题 | UI 提示；[ADR 0002](../decisions/0002-no-edit-lock.md) | 已接受 |
| R4 | 无回收站，业务删除只能由运维在库里恢复 | 恢复依赖人工，有响应延迟 | 误删投诉 | 软删兜底 + [runbook](../guides/runbooks.md) RB-1 | 缓解中 |
| R5 | 注册触发器失败会连带注册失败 | 新用户无法注册 | 注册 500 | 触发器只做两条 INSERT；失败整体回滚不留半残账号；集成测试覆盖 | 已接受 |
| R6 | `BETTER_AUTH_SECRET` 泄露或轮换不当 | 会话可被伪造，或轮换导致全员登出 | 密钥出现在日志/仓库 | 只存服务端环境变量；轮换按 runbook RB-4 执行 | 已接受 |
| R7 | 无自助密码找回 | 忘记密码只能人工重置 | 用户求助 | runbook RB-2：验证身份后重置并撤销会话 | 已接受 |
| R8 | `app_rw` / `auth_service` 授权矩阵写错 | 密码哈希泄露，或业务角色越权读 `auth.*` | 集成测试出现意外放行 | 显式 `GRANT`/`REVOKE`；集成测试断言两个角色边界 | 缓解中 |
| R9 | `ltree` 路径长度上限 | 超深谱系无法表达 | 单条路径接近上限 | 单代约 33 字节，现实世代数远低于上限 | 已接受 |
| R10 | 软删数据永不清理，长期膨胀 | 存储成本与查询变慢；与保留期要求冲突（见 R18） | 表体积或查询耗时上升 | 超过阈值再评估归档；当前无清理任务 | 需决策 |
| R11 | Vercel / Neon 平台故障与函数冷启动 | 短时不可用或首请求变慢 | 平台状态页告警 | 依赖托管状态页；Vercel 即时回滚上一版本 | 已接受 |
| R12 | 无客户自助数据导出 | 数据主权争议 | 客户要求导出 | 合同约定 + 手工 `pg_dump` 兜底 | 需决策 |
| R13 | Serverless 多实例耗尽 Neon 连接数 | 新请求连不上库 | 日志出现 `too many connections` | pooled 端点 + 每实例池上限 5 + `attachDatabasePool`；runbook RB-5 | 缓解中 |
| R14 | 函数执行时长超限 | 长请求被中断 | 超时错误 | M1 没有长任务；批量写有行数上限 | 已接受 |
| R15 | 登录限流只存在于进程内 | 多实例下失败计数不共享，暴力尝试可分散到不同实例 | 异常登录量 | 接受为 best-effort；`x-forwarded-for` 可伪造这一点已记录 | 已接受 |
| R16 | 无 staging / preview 环境 | 生产已上线，但任何改动仍直接落在生产，没有「先验证再上线」的一站；生产形态的三个假设（`pg` + `attachDatabasePool` 的连接生命周期、非属主 `app` 角色下 RLS 的兜底、pooled/direct 双 URL 分离）只能事后确认 | 需要对外承诺稳定性时 | `verify:deploy` 可对生产跑；没有 staging 与 external E2E | 需决策 |
| R17 | 谱系图全量加载 | 画布的按代加载只约束渲染，不约束传输与内存；数万人丁的谱系会把整棵树传到浏览器 | 单谱系人丁数增长 | `getNodes` 无分页；`generationLimit` 只裁剪渲染 | 缓解中 |
| R18 | 数据生命周期与删除权缺口 | 软删永存意味着账号注销后个人信息仍在；家谱含在世人口信息，数据主体与账号所有者不是同一人 | 客户询问数据处置能力 | 无保留期、无物理删除路径（需要打破 ADR 0004 与 ADR 0005） | 需决策 |
| R19 | 可用性目标不可测量（无外部探针、无错误聚合） | 指标存在但测量手段不存在，等于没有承诺；页面写错误统一返回 200，服务端错误率恒为 0 | 需要对外承诺 SLA 时 | 只有 `/api/health` 可被手动探测，没有定时探针与告警 | 需决策 |
| R20 | `BETTER_AUTH_SECRET` 没有平滑轮换路径 | 轮换使现有 Cookie 全部失效，于是实际不轮换——最需要轮换时最不敢按 | 泄露事件 | 数据库会话可在轮换后按用户撤销；若认证库支持密钥版本再评估双密钥 | 已接受 |
| R21 | 事实层六表已落库但读写仍全部走 `node` | 存在两套数据形态：活写入在 `node`，事实层是冻结快照；切换前任何谱系写入都不会进事实层 | 有人开始写事实层查询或假定回填可重跑 | 回填每个组织一次（已有 `person` 则 `FactLayerAlreadyBackfilledError`）；对账 CLI 可重复；谱系写入不更新事实层。2026-11-05 已拍板事实层为目标真源（决策记在 [P1 读写切换计划](../superpowers/plans/2026-11-05-p1-read-write-switch.md)，未新增风险条目）；计划已编写并有冻结门禁，切换待谱书编目 / 排版主线跑通后启动。禁止在每个 `node` 写入口双写 | 缓解中 |
| R22 | 谱书表已落库但没有读写路径（谱文已接入） | 谱书表结构随需求变化要改迁移，而没人用；评审若仍把谱文算进「无路径」会误判进度 | 开始做谱书编目 UI | 谱文：列表 + 三区编辑器 + Action 已落地（见 [11](./11-需求与实现状态.md) §7 FR-ART）；谱书：`books/page.tsx` 仍只渲染占位 `EmptyState` | 缓解中 |
| R23 | `organization_member` 与 `invite` 是硬删除 | 误删成员/邀请不可恢复，只能从备份恢复 | 误删工单 | 移除成员前预检 + 最后 owner 触发器兜底；备份恢复见 runbook | 已接受 |
| R24 | 没有审计表，`activity_logs` 是可变的产品活动流 | 无法回答「谁改了哪条数据」；日志保留期外无法逐条追溯 | 合规或纠纷追溯需求 | 活动流 + 结构化日志；明确声明它不是审计日志 | 已接受 |
| R25 | 迁移与业务代码在同一 PR 里混提交 | 回滚代码时迁移已在库上，出现版本不匹配 | 需要紧急回滚 | 约定迁移与业务分开提交；CI 有迁移漂移检查；回滚策略要求迁移向后兼容一个版本 | 缓解中 |
| R26 | 单文件行数上限的豁免清单只增不减 | 400 行约束逐渐失效，大文件继续变大 | 豁免条目数增加 | 豁免只许缩小不许扩大（`scripts/check-file-size.mjs`）；评审盯住新增豁免 | 缓解中 |
| R27 | 公开 ID 冲突重试上限为 3 次 | 极端情况下创建失败 | 出现 `conflict` 失败 | 每次重试都生成新 ID（不复用冲突值）；20 位空间下冲突概率极低 | 已接受 |
| R28 | 活动日志与业务写不在同一事务 | 组织级写入的日志可能永久缺失；谱系写入的日志失败会回滚业务（语义不一致） | 日志与数据对不上 | 日志失败只告警不回滚（组织侧）；差异已登记 | 缓解中 |
| R29 | 生产库迁移靠人工执行 | 部署不会自动迁移；没人记得跑，线上就停在新代码 + 旧库，每个 Server Component 都抛错（React #441 + digest，页面全白）。2026-10-31 就是这样坏了整站 | 每次改 schema 并合入 `main` | `.github/workflows/migrate-production.yml` 在 `lib/db/migrations/**` 变更时自动迁移并校验；不放进 Vercel 构建（preview 会重复执行 DDL） | 缓解中 |
| R30 | 世系表跨房支顺序错（**已修，2026-11-03**，记录见 `.specify/bugs/lineage-generation-order/`）：旧 `blood.sort` 先比 `generation`、再比 `sort`，而 `sort` 是「同一父节点内的排行」，同一世次里不同房支的兄弟被交错排列，得不到「长房整支 → 次房整支」的深度优先序 | 修复前 FR-LIN-13 的验收标准不成立：世系表看起来有序，实际不是族谱要求的房支序；一旦有人按世系表排版或导出，错序只能人工重排 | 多房支的真实族谱上打开世系表；有人按世系表成书 | 顺序规则收敛到一处：`components/lineage/derived.ts` 的 `index.blood` 改为从 `roots` 出发的**显式栈深度优先前序**（根之间按 `sort` → 全名；父链成环的脏数据按 `generation → sort` → 全名兜底追加，不丢人丁），世系表世次卡片、画布纵向堆叠、搜索首匹配、打印视图全部继承它；`lib/db/queries/nodes.ts` 的 `orderBy` 降为只按 `createdAt` 的稳定化排序。**`ORDER BY generation, path` 不可行**：`ltree` 的 label 是 UUID（`nodeLabel`），path 字典序与房支长幼无关（[ADR 0003](../decisions/0003-tree-storage-ltree.md)）。用例 `tests/lineage-derived-order.test.ts`；按世系表成书/导出立项时复核这一序能否直接复用 | 缓解中 |
| R31 | 写操作无幂等：双击、慢网重试或 Server Action 被重放会静默多插一行。**人丁创建这条主路径已修**（`node.request_id` + 部分唯一索引 `uk_node_org_request_id`，见 `0027`），但只有创建路径带键：组织 / 项目 / 分类 / 谱系 / 谱书的创建仍只靠各自的业务唯一索引挡重复，更新与移动仍是 last-write-wins | 族谱里「多一个人」比「少一个人」更难发现，往往到排版成书才暴露——人丁这条已堵住；其余对象的重复提交仍可能多一行 | 用户在慢网/移动端点两次；任何客户端重试 | `lib/lineage/lineage-write.ts` 的 `withCreateWrite`：`FOR UPDATE` 锁内先按 `(organization_id, request_id)` 查，命中返回已有那一行；并发双飞撞 `23505` 则整体回滚后重查，同样返回已有行而不是报错。键由录入对话框每次打开生成一次（`components/lineage/node-create-dialog.tsx`），五个创建类 Action 的 Zod 入参必填；用例见 `tests/integration/nodes.test.ts`（幂等 7 条）与 `tests/integration/constraints.test.ts`（索引），契约见 [05-接口与集成设计 §5.3](./05-接口与集成设计.md) | 缓解中 |

## 技术债偿还顺序

顺序不是按工作量排，而是按**「不做会不会堵住后面的路」**排。

1. **先让谱书编目 / 排版主线端到端跑通，再动数据层**——R21 与 R22 的谱书半边。谱文读写已落地，不再算「路径无」。事实层今天是一次性回填后的冻结快照，并没有在「持续维护两套」——利息来自有人误以为第二套是活的。2026-11-05 已拍板事实层为目标真源，[P1 读写切换计划](../superpowers/plans/2026-11-05-p1-read-write-switch.md) 已编写，第一步（切换计划 + 「`node` 写不碰 `person`」的冻结门禁）已完成；**启动闸门**是谱书编目 / 成品排版能端到端导出一份谱书，闸门之前冻结（不加表 / 列 / 索引，不双写、不切读）。**禁止**在每个 `node` 写入口双写：写路径是替换，不是同步。闸门之后按计划先定唯一写入路径，再对账、切写、切读、最后退役 `node`。谱书仍按 [add-a-feature](../guides/add-a-feature.md) 补查询与 Action，且须先有 `book_catalog` 复合外键（见 [2026-11-03 评审](../archive/reviews/2026-11-03-linus-architecture-review.md) P1-6）。
2. **再补回收站**——R4、R18。软删数据已经在库里，缺的只是界面与恢复流程；它不阻塞其它工作，但每多一天，误删就多一天只能靠运维。做它的同时必须回答保留期问题（R18），否则回收站会变成「永久保留」的入口。
3. **再补告警与探针**——R19。它不阻塞开发，但阻塞「敢对外承诺可用性」；成本低（一条探针 + 三条 SLO），收益是把 R11、R13 从「不知道」变成「知道」。
4. **最后补审计**——R24。它需要先有明确的合规诉求（谁要、保留多久、能否篡改），否则会做成一张没人查的表；在诉求出现前，活动流 + 结构化日志够用。

被刻意排在最后的：编辑锁（R3，等客户反馈）、缓存层与外部搜索索引（等 R17 的量级信号出现）、拆服务（等团队规模信号）。

**插队项**：R30（世系表顺序）与 R31（写操作幂等）是数据正确性问题，不算「债」，按缺陷处理——登记在这里是因为它们由归档评审发现、目前没有修复计划。谁先动世系表排序或创建类 Action，谁就顺手把它们修掉，不要再开一条独立的技术债。R31 的人丁创建部分已按此处理（`0027` + `withCreateWrite`，状态改记「缓解中」：其余对象的创建仍没有幂等键）；R30 也已按此处理（世系表显示序改为深度优先前序，顺序规则只留 `components/lineage/derived.ts` 一处，状态改记「缓解中」：成书/导出还没立项，届时复用同一条序）。

## 演进方向

三条路线，每条只写触发条件、第一步和不做什么。**本文件不重新设计目标架构**——目标形态在 [11-需求与实现状态](./11-需求与实现状态.md) 与 [decisions](../decisions/README.md) 里。

### 方向一：家谱业务 M1 收尾（谱文、谱书接入）

- **触发条件**：无外部信号，是既定下一步。
- **第一步**：给 `content` / `publishing` 两个域补查询函数与 Action（按 [guides/add-a-feature](../guides/add-a-feature.md) 的顺序），富文本先按 [ADR 0010](../decisions/0010-rich-text-editor-selection.md) 的格式边界落地，编辑器依赖单独 PR 引入。
- **不做什么**：不引入新存储、不加后台任务、不做实时协同；谱书预览与分享（`FR-PREV-*`）仍留在 M2。

### 方向二：多实例化（共享限流、后台任务）

- **触发条件**：单实例承载不住流量，或限流被证明需要真正生效（R15 升级为实际威胁）。
- **第一步**：把限流计数搬到共享存储（同一数据库的一张表即可），再评估是否需要队列。
- **不做什么**：不引入消息中间件、不拆微服务；[ADR 0005](../decisions/0005-zero-background-jobs.md) 的破例条件必须先被满足，且需要新 ADR。

### 方向三：生产化（Preview 环境、告警探针）

- **触发条件**：生产已上线（Vercel + Neon，`verify:deploy` 已验证），剩下的不是「要不要生产化」而是「怎么让改动先验证再上线」；不再等外部信号。
- **第一步**：建 preview/staging（Vercel Preview Deployment + Neon 分支，每个 PR 一套独立库），把 `verify:deploy` 与 external E2E 跑在 preview 上，一次验证掉 R16 的三个假设；同时加一条 5 分钟探针与三条 SLO（R19）。
- **不做什么**：不为了「生产级」提前引入多 region、双活、APM 全家桶——先把一条链路真正跑通。

> **为什么 Preview 排在告警前面**：归档对标评审把「补一个 preview 环境」列为 ROI 最高的一件事（[2026-10-22 对标评审 §3.B](../archive/reviews/2026-10-22-architecture-benchmark-and-doc-structure.md)）——它同时消掉「地基未验证」与「没有 staging」两个问题，让隔离测试第一次能在真实生产角色配置下跑。同一份评审的 §4「明确不建议做的」列了五项（拆微服务/消息队列、tRPC/OpenAPI/GraphQL、把 RLS 换成应用层过滤、完整 arc42 + 正式 ATAM + C4 L4、CQRS/事件溯源）：理由是没有外部消费者、团队与 QPS 都远低于拆分门槛，做了是负收益——这些方向不进本文件的演进路线。

## 待决策项

需要拍板的问题只有一个来源：[decisions 索引](../decisions/README.md) 的「待决策」一节（D 编号、候选方案与影响都在那里）。本文件不复制，只引用其中会改变架构演进节奏的条目：R18/R10 的数据生命周期、R16 的 preview 环境、R15/D-11 的登录限流、D-4 的关系模型（过继/兼祧/入赘）与 D-10 的表单栈。
