## 1. 部署拓扑

### 1.1 容器视图（C4-L2）

```mermaid
flowchart TB
  U[浏览器<br/>React 19 客户端组件] -->|HTTPS · 自定义域名 · Vercel CDN| V
  subgraph V[Vercel · Next.js 16 App Router · 多实例无状态]
    RSC[RSC 渲染<br/>服务端直出首屏]
    SA[Server Action<br/>全部写操作]
    RH[Route Handler<br/>4 条只读]
    BA[Better Auth<br/>数据库会话 + scrypt]
  end
  V -->|pg.Pool + attachDatabasePool<br/>APP_POSTGRES_URL · pooled| P[(Neon PostgreSQL 18+<br/>public schema · app_rw · FORCE RLS)]
  V -->|pg.Pool<br/>AUTH_POSTGRES_URL · direct · role=auth_service| A[(Neon PostgreSQL 18+<br/>auth schema · auth_service)]
  P -.同实例.-> A
  CI[GitHub Actions] -->|构建 · 校验 · E2E| V
  CI -->|migrate-production.yml<br/>POSTGRES_URL_DIRECT| P
```

两条连接指向同一个 Neon 计算实例的两个角色，但在配置上是两个 URL：业务连接走 pooled 端点，认证连接必须走 direct 端点（认证连接用启动参数固定 `role=auth_service`，pooler 不接受该参数）。同区域部署，不在函数与数据库之间跨区。

### 1.2 部署单元（C4-L3）

| 部署单元 | 跑什么 | 伸缩单位 | 冷启动影响 |
|---|---|---|---|
| Vercel 函数 | RSC 渲染、Server Action、Route Handler、Better Auth（进程内） | 按请求数自动水平扩，实例之间无共享状态 | 首个请求要建连接并加载配置；`attachDatabasePool` 让平台冻结/恢复连接池 |
| Neon 计算实例 | PostgreSQL 18+，`public` 与 `auth` 两个 schema | 托管，按负载升降；空闲可自动挂起 | 挂起后首个连接会等待恢复，表现为一次慢请求 |
| 本地 Docker | 仅 PostgreSQL，不含应用 | 单实例 | 不适用 |
| CI runner | 构建、单测、集成测试、E2E | 每次运行一台 GitHub 托管机 | 不适用 |
| 生产迁移 job | 对 Neon 生产库执行迁移，再用同一份 journal 校验 | 每次触发一台 GitHub 托管机；`concurrency` 保证不并发、不被取消 | 不适用；用 `POSTGRES_URL_DIRECT` 直连，不占应用连接池 |
| 运维 CLI（`data:backfill:fact` / `data:reconcile:fact`） | 事实层回填与对账 | 人工执行一次 | 不适用；用直连角色，长事务不占应用连接池 |

### 1.3 没有的东西

没有独立的后台 worker、没有队列消费者、没有定时任务、没有独立缓存层、没有独立 API 网关。这些不是待补的空白，是部署模型的一部分，见 [ADR 0005](../decisions/0005-zero-background-jobs.md)。对象存储只有一处例外：谱文正文插图走 Vercel Blob 私有桶（本地与 CI 落 `.data/media/`），见 [ADR 0019](../decisions/0019-media-storage.md)。

## 2. 环境与发布顺序

### 2.1 环境分层

| 环境 | 数据库 | 驱动 | 启动方式 |
|---|---|---|---|
| 本地开发 | Docker PostgreSQL 18，由 `pnpm db:setup` 生成 | `postgres.js`（直连，可用 prepared statements） | `pnpm dev` |
| 本地生产模式 | 同本地 | 本地仍走 `postgres.js`（`isVercel()` 为假） | `pnpm build && pnpm start`，用 `pnpm verify:deploy` 验证 |
| CI | `postgres:18-alpine` service，库名以 `_test` 结尾 | `postgres.js` | GitHub Actions，见 §5 |
| Preview（Vercel） | 未配置独立分支/库 | 同生产（`isVercel()` 为真 → `pg`） | 平台构建；**不得指向生产直连 URL** |
| 生产 | Neon PostgreSQL 18+ | `pg` 的 `Pool`（`max: 5`）+ `attachDatabasePool` | Vercel 构建后由平台启动 |
| Staging（仅外部 E2E） | 无独立环境，可临时指一个 Neon 分支 | 同生产 | 需 `E2E_EXTERNAL_SERVER` 与 `E2E_ALLOW_EXTERNAL` 同时开启 |

变量名不在这张表里重复，一律见 §3。

### 2.2 发布顺序

```text
1. PR：CI 全绿（§5.1 的 13 个阻塞步骤）
2. 合并到 main：
   a. 若改了 lib/db/migrations/** → migrate-production.yml 先对生产库执行迁移（§5.3）
   b. Vercel 构建并部署 main
3. 部署后自检：GET /api/health 返回 200；关键路径手点一遍
4. 外部验证（有凭据时）：pnpm verify:deploy 指向线上域名
5. 回滚：Vercel 即时回退到上一部署；数据按 §6.2 恢复
```

**迁移必须先于应用启动**。顺序反了会出现「新代码访问旧表」的窗口期；反过来把迁移塞进构建，则可能在多次构建或预览部署中重复执行 DDL。这条顺序曾经只靠人记，结果生产库停在 `0003_better_auth`，代码却在读 `0004` 之后才有的列，于是每个 Server Component 都抛错，页面只剩 React #441 与 digest——现在由 §5.3 的 job 承担。

**回滚**：Vercel 重新部署上一版本 + Neon 分支/PITR 恢复数据。没有应用层回滚脚本，也没有自动化数据回滚；业务表的软删与 `deleted_at` 分组是唯一的行级恢复手段。`organization_member` 与 `invite` 是硬删除，`app_rw` 没有 `DELETE` 授权，物理删除只能走运维。

### 2.3 环境缺口 `[目标]`

仓库里**没有独立的 staging，也没有 PR preview 库**，所以任何改动都直接落在生产，没有「先验证再上线」的一站。生产形态的三个假设（`pg.Pool` + `attachDatabasePool` 的连接生命周期、非属主 `app` 角色下 `FORCE RLS` 的兜底、pooled/direct 双 URL 分离）目前靠 `verify:deploy` 与生产日志事后确认。这条登记在 [12-风险与演进规划](./12-风险与演进规划.md)。

Preview 需要数据库时，可选方案：共享一个 staging 分支（迁移在分支上手工执行）、每个 Preview 一个 Neon 分支、或纯 UI 改动不接数据库。无论哪种，**Preview 不得拿到生产直连 URL**，生产库迁移只由 §5.3 执行。

### 2.4 本地

本地只跑 PostgreSQL（Docker）+ `next dev`，不构建应用镜像、不起反向代理。搭建步骤、`.env` 写法、`pnpm db:setup` 与三个常见陷阱（`.env` 不是 `.env.local`、必须用 `http://localhost:3000`、`pnpm test:e2e` 会清空测试库）全在 [13-本地开发与命令](./13-本地开发与命令.md)。

## 3. 环境变量

**本节是环境变量的唯一来源**，其他文档只链接、不重复。全部读取集中在 `lib/config.ts`（F7 约束：`process.env` 只允许出现在这里，`drizzle.config.ts` 属于工具链例外）。

| 变量 | 必填 | 作用域 | 用途与约束 |
|---|:--:|---|---|
| `POSTGRES_URL` | ✅ | 所有环境 | 业务运行期连接串的兜底。本地 `postgresql://postgres:postgres@localhost:54322/postgres`；生产为 Neon **pooled** 端点 |
| `APP_POSTGRES_URL` | 生产必填 | Vercel 生产/Preview | 业务查询专用，Neon **pooled** 端点，登录角色 `app`；经 `withOrg` 在事务内 `SET LOCAL ROLE app_rw`。本地可省略，回退 `POSTGRES_URL` |
| `AUTH_POSTGRES_URL` | 生产必填 | Vercel 生产/Preview | Better Auth 专用，Neon **direct（unpooled）** 端点，登录角色 `auth_runtime`；连接固定 `role=auth_service`。本地可省略，回退 `POSTGRES_URL` |
| `POSTGRES_URL_DIRECT` | 迁移必填 | **只放 GitHub Actions secret 与运维终端，不进 Vercel** | 迁移、DDL、备份用的直连 URL；`drizzle.config.ts` 优先读它，缺省回退 `POSTGRES_URL` |
| `BETTER_AUTH_SECRET` | ✅ | 所有环境 | Cookie 与会话签名密钥，**≥ 32 字符**；每个环境独立，轮换后全员重新登录 |
| `BETTER_AUTH_URL` | ✅ | 所有环境 | Better Auth 基地址，决定 Cookie 与邀请链接。本地 `http://localhost:3000`，生产为自定义域名 |
| `LOG_LEVEL` | — | 所有环境 | `debug` / `info` / `warn` / `error`；未设时生产为 `info`、其他为 `debug`。生产不要设 `debug` |
| `TEST_POSTGRES_URL` | — | 本地 / CI | 集成测试库，**库名必须以 `_test` 结尾** |
| `E2E_EXTERNAL_SERVER`、`E2E_ALLOW_EXTERNAL`、`E2E_BASE_URL` | — | 仅 staging | 外部模式 E2E，两个开关必须同时为真，禁止对生产跑 |
| `NODE_ENV`、`VERCEL` | 平台注入 | 由 Vercel / Next 设置 | `VERCEL` 为真时 `APP_POSTGRES_URL` 与 `AUTH_POSTGRES_URL` 变为必填 |

### 3.1 启动校验

`getServerConfig()`（`lib/config.ts`）用 Zod 校验并在 `instrumentation.ts` 里于进程启动时调用，缺项或格式错直接抛错，不会带病运行：

```text
❌ Invalid environment variables:
   POSTGRES_URL: Required
   BETTER_AUTH_SECRET: String must contain at least 32 character(s)
```

两条 `superRefine` 规则：

- 非构建阶段，若 `AUTH_POSTGRES_URL ?? POSTGRES_URL` 的主机名含 `-pooler.` → 直接报错：认证连接用启动参数固定 `role=auth_service`，pooler 不支持。
- `process.env.VERCEL` 为真时，`APP_POSTGRES_URL` 与 `AUTH_POSTGRES_URL` 必填（报 `… is required in production`）。

构建阶段跳过数据库可达性校验——构建不该要求数据库在线。

### 3.2 驱动与连接串拆分

| 环境 | 驱动 | 连接 | 说明 |
|---|---|---|---|
| 本地 Docker PostgreSQL 18 | `postgres.js` + `drizzle-orm/postgres-js` | `localhost:54322` 直连 | 轻量；可用默认 prepared statements |
| Vercel + Neon 生产 | `pg` 的 `Pool` + `drizzle-orm/node-postgres` + `attachDatabasePool` | `APP_POSTGRES_URL`（pooled）+ `AUTH_POSTGRES_URL`（direct） | Vercel 官方推荐；实例冻结时平台回收空闲连接 |

| 用途 | 变量 | 取值 |
|---|---|---|
| 业务运行期查询 | `APP_POSTGRES_URL`（回退 `POSTGRES_URL`） | Neon **Pooled connection**（主机名含 `-pooler`） |
| 认证与租户写 | `AUTH_POSTGRES_URL`（回退 `POSTGRES_URL`） | Neon **Direct connection**（不带 `-pooler`）；登录角色 `auth_runtime` |
| 迁移 / 备份 / DDL | `POSTGRES_URL_DIRECT` | Neon **Direct connection** |

| 规则 | 说明 |
|---|---|
| 连接池 | 每个函数实例 `max: 5`，不要在请求里新建连接 |
| 两个连接 | 业务连接固定 `app` → `app_rw`；认证连接固定 `auth_runtime` → `auth_service`，**不能互换** |
| 模块级单例 | 连接池在模块作用域创建并复用；`db` 是延迟 Proxy |
| 直连隔离 | `POSTGRES_URL_DIRECT` 不配置到 Vercel 运行期，避免应用拿到绕过连接池的管理连接 |
| 类型边界 | `lib/db/drizzle.ts` 与 `lib/db/auth-db.ts` 吸收驱动差异，查询层只 import 这两个模块，不直接 import `pg` 或 `postgres` |

Neon 的 Vercel 集成可能注入 `DATABASE_URL` / `DATABASE_URL_UNPOOLED`。若使用该集成，在 Vercel 里映射成本文的目标变量名，**不要同时保留两套变量**。

### 3.3 环境作用域

| 环境 | 数据库 | `BETTER_AUTH_URL` | 说明 |
|---|---|---|---|
| Development | 本地 Docker | `http://localhost:3000` | 不需要 Neon |
| Preview | 未配置独立库（§2.3） | 该预览部署的域名 | **禁止**指向生产直连 URL |
| Production | Neon 生产分支 | 自定义域名 | 迁移先于部署，见 §2.2 与 §5.3 |

Vercel 的环境变量同时用于构建与运行。构建命令中**不得**包含迁移；构建环境只需要能通过配置校验的运行期变量。

## 4. 数据库初始化、迁移与角色授权

### 4.1 迁移清单

**唯一来源是 `lib/db/migrations/meta/_journal.json`，本文不手抄编号**（当前 25 个，最新 `0024_certain_tinkerer`）。新增迁移后不要回来改这张表，改 journal 就够了。

只需要知道开头几个和几个关键的：

| 迁移 | 做了什么（现状） |
|---|---|
| `0000_baseline.sql` | 三个扩展 `ltree` / `pg_trgm` / `btree_gist`（文件第 1、3、5 行）、`public.generate_public_id()`、`CREATE SCHEMA "auth"`、11 张 public 业务表 + `auth.users` |
| `0001_auth_rls.sql` | `CREATE ROLE app_rw NOLOGIN`（第 6 行）、注册触发器 `trg_auth_user_created` / `handle_new_user()`、RLS 策略与部分唯一索引、`auth.*` 函数 |
| `0002_app_role_grant.sql` | `GRANT app_rw TO app`（第 6 行；登录角色不存在时安全跳过） |
| `0003_better_auth.sql` | `CREATE ROLE auth_service`（第 16 行）、`GRANT app_rw TO app`（第 24 行）、`GRANT auth_service TO auth_runtime`（第 27 行）、双角色边界与 organization 插件所需的策略/触发器。**要求 auth 与租户数据为空** |
| `0016` / `0018` / `0020` | 事实层（`fact_person` / `fact_family` / `fact_event`）建表与 RLS |

**当前 17 张业务表**（`public` schema，`lib/db/schema/*.ts` 的 `pgTable(` 计数）加 `auth` schema 的 4 张认证表。表与列的定义见 [04-数据视图-数据架构](./04-数据视图-数据架构.md)。

### 4.2 角色与授权

顺序是：先创建两个运行期登录角色 `app` 与 `auth_runtime`（一次性），再执行迁移。`0001` 创建受限角色 `app_rw`，`0002`/`0003` 在登录角色存在时补授权，`0003` 另外创建 `auth_service`。密码只存在于环境变量与 Neon 中，不写进迁移文件。

**第 1 步：运行期登录角色（迁移之前，一次性）**

```sql
-- 本地由 db:setup 生成的 POSTGRES_USER=postgres 提供；生产手工执行一次
-- 不要用 Neon 控制台创建运行期角色：控制台创建的角色会加入 neon_superuser
CREATE ROLE app LOGIN PASSWORD '<generated>'
  NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE;

CREATE ROLE auth_runtime LOGIN PASSWORD '<generated>'
  NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE;
```

**第 2 步：迁移创建受限角色并补授权**

```sql
-- 0001_auth_rls.sql（节选）
CREATE ROLE app_rw NOLOGIN NOSUPERUSER NOBYPASSRLS;

-- 0003_better_auth.sql（节选）
CREATE ROLE auth_service NOLOGIN NOSUPERUSER NOBYPASSRLS;
```

`app` 的密码写入 Vercel 的 `APP_POSTGRES_URL`，`auth_runtime` 的密码写入 `AUTH_POSTGRES_URL`，都不进 Git。迁移连接用 Neon 项目所有者角色（默认 `neondb_owner`），与运行期角色分离。

**授权矩阵（现状）**

```sql
GRANT USAGE ON SCHEMA public TO app_rw;
GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA public TO app_rw;
-- 不授予 DELETE：软删统一走 UPDATE deleted_at
REVOKE INSERT, UPDATE, DELETE ON organization_member FROM app_rw;
REVOKE SELECT, INSERT, UPDATE, DELETE ON invite FROM app_rw;

-- 认证与租户写只属于 auth_service
GRANT USAGE ON SCHEMA auth TO auth_service;
GRANT SELECT, INSERT, UPDATE, DELETE ON auth.users, auth.session, auth.account, auth.verification TO auth_service;
GRANT SELECT, INSERT, UPDATE, DELETE ON organization_member TO auth_service;
GRANT SELECT, INSERT, UPDATE ON organization, invite TO auth_service;

-- app_rw 不得直接读写 auth 表
REVOKE ALL ON auth.users FROM app_rw;
```

> `GRANT ... ON ALL TABLES` 只影响执行时已存在的表。新增表后要在同一迁移里重新授权，或配置 `ALTER DEFAULT PRIVILEGES`。
>
> 密码由 Better Auth 以 scrypt 存入 `auth.account`，只有 `auth_service` 能读写。
>
> 迁移角色必须能绕过 RLS（Neon 所有者角色与本地超级用户满足），否则 `SECURITY DEFINER` 触发器在 `FORCE RLS` 表上仍会失败，注册会整体回滚。

### 4.3 执行迁移

本地（登录角色由 `db:setup` 提供）：

```bash
pnpm db:generate   # Schema 变更后生成 SQL，人工 review
pnpm db:migrate    # 对本地 PostgreSQL 执行
```

Neon（生产或分支，只在可信终端或 CI 里执行，**不要写进 Vercel Build Command**）：

```bash
POSTGRES_URL_DIRECT='postgresql://<迁移角色>:<pwd>@<direct-host>/<db>?sslmode=require' \
  pnpm db:migrate
```

`drizzle.config.ts` 已实现直连优先：

```typescript
export default defineConfig({
  schema: './lib/db/schema/index.ts',
  out: './lib/db/migrations',
  dialect: 'postgresql',
  dbCredentials: {
    url: process.env.POSTGRES_URL_DIRECT ?? process.env.POSTGRES_URL!,
  },
});
```

| 规则 | 原因 |
|---|---|
| 迁移不在 Vercel 构建中执行 | 构建可能重复、并发，Preview 也可能触发；DDL 必须单点、有序 |
| Preview 不自动迁移生产库 | 预览部署数量多，任何一次构建都不应改动生产 schema |
| 迁移先于应用发布 | 避免「新代码访问旧表」的窗口期 |
| 迁移只前进 | 不做 down 迁移；破坏性变更用「新增列 → 回填 → 后续删除」三段式 |
| 执行前确认目标 | 先跑 `SELECT current_database(), current_user;`，确认是哪个分支 |
| 已应用的迁移不修改 | 修正用新迁移 |

### 4.4 RLS 验证

**必须做的一步**。Neon 控制台与迁移连接通常是所有者角色，可能绕过 RLS；验证必须实际切到 `app_rw`。

先用直连写入最小测试数据（一个用户、两个组织、各一条 `node`），再用运行期连接验证：

```sql
BEGIN;
SET LOCAL ROLE app_rw;

-- 不设 claims，auth.uid() 为 NULL
SELECT count(*) FROM node;      -- 必须返回 0

SELECT set_config('request.jwt.claims',
  '{"sub":"<user-uuid>","role":"authenticated"}', true);
SELECT auth.uid();              -- 必须等于 <user-uuid>
SELECT count(*) FROM node;      -- 必须只等于该用户所属组织的行数

-- 换一个组织 ID 查询，必须仍是 0 行
SELECT count(*) FROM node WHERE organization_id = '<other-org-uuid>';
ROLLBACK;
```

认证表的越权检查放在单独事务里（`permission denied` 会中止当前事务）：

```sql
BEGIN;
SET LOCAL ROLE app_rw;
SELECT count(*) FROM auth.users;   -- 期望：permission denied for table users
ROLLBACK;
```

| 断言 | 期望 |
|---|---|
| 无 claims 查询 `node` | 0 行 |
| 带本组织 claims | 本组织行数 |
| 带其他组织 claims | 0 行 |
| `SELECT auth.uid()` | 返回 claims 中的 `sub` |
| `SELECT * FROM auth.users`（`app_rw`） | `permission denied` |

> 空表上会「天然通过」，测试库必须先插数据。这几条断言在 `tests/integration/org-scope.test.ts` 里有自动化版本（`permission denied for table users`）。

`withOrg` 用 `SET LOCAL ROLE app_rw` 与会话内的 `set_config(..., true)` 注入用户声明，都是事务级设置。会话级 `SET` 会把角色与声明泄漏给下一个借用该连接的请求——这是这套隔离模型里最容易踩的坑。

## 5. CI 流水线

### 5.1 阶段（`.github/workflows/ci.yml`，单 job 顺序执行）

每阶段的命令只在这里写一次。CI 的 PostgreSQL 是 `postgres:18-alpine` service，测试库 `gramps_test`。

| # | 阶段名 | 命令 / 动作 | 拦发布 |
|--:|---|---|:--:|
| 1 | Install dependencies | `pnpm install --frozen-lockfile` | ✅ |
| 2 | Lint & format check | `pnpm check`（Biome，含三条 `noRestrictedImports` 依赖方向规则） | ✅ |
| 3 | Docs consistency | `pnpm run docs:check --strict` | ✅ |
| 4 | Architecture constraints (F6/F7) | `pnpm arch:check`（单文件 ≤400 行、`process.env` 只在 `lib/config.ts`） | ✅ |
| 5 | Typecheck | `pnpm typecheck` | ✅ |
| 6 | Migrate test database | `pnpm db:migrate`（空库一次跑完） | ✅ |
| 7 | Provision runtime login roles | psql 建 `app` / `auth_runtime`，`GRANT app_rw TO app`、`GRANT auth_service TO auth_runtime` | ✅ |
| 8 | Unit + integration tests with coverage | `pnpm test:coverage`（真实 PostgreSQL + 覆盖率门槛） | ✅ |
| 9 | Upload coverage | 上传覆盖率产物，`if: always()` | — |
| 10 | Check migration drift | `pnpm db:generate` 后 `test -z "$(git status --porcelain lib/db/migrations)"` | ✅ |
| 11 | Build | `pnpm build`（构建不要求数据库可达） | ✅ |
| 12 | Install Playwright browser | `pnpm exec playwright install --with-deps chromium` | ✅ |
| 13 | E2E critical path | `pnpm test:e2e`（对 production server） | ✅ |
| 14 | Upload Playwright artifacts | 失败时留报告与截图，`if: failure()` | — |
| 15 | Deployment verification | 3100 端口起 production server，等 `/api/health` 就绪，再跑 `node scripts/verify-deployment.mjs --base-url http://127.0.0.1:3100` | ✅ |

### 5.2 阻塞规则

除第 9、14 步外，其余 **13 步任何一步失败都拦发布**：仓库里没有 `continue-on-error`；两个上传步骤带 `if-no-files-found: ignore`，只留证据、不判定。

CI 里第 7 步是必须的：集成测试要验证「非属主角色 + RLS」的真实行为，而迁移自己创建的是 `NOLOGIN` 的 `app_rw` / `auth_service`，登录角色得由流水线补。

### 5.3 生产库迁移 job（`.github/workflows/migrate-production.yml`）

- **触发**：`push` 到 `main` 且改到 `lib/db/migrations/**`；也支持手动 `workflow_dispatch`。
- **并发**：`concurrency: group: production-migration, cancel-in-progress: false`——迁移不能并发、不能被新提交取消。
- **前置闸门**：secret `POSTGRES_URL_DIRECT` 为空时直接 `::error::` 退出（「Refuse to run without the direct database URL」），绝不用池化或应用连接跑 DDL。
- **执行**：`pnpm db:migrate`。
- **校验**：`node scripts/verify-deployment.mjs --skip-http`，用同一份 journal 核对生产库是否已应用全部迁移，不一致即红。

**不放进 Vercel 构建**：多次构建与 Preview 部署会重复执行 DDL。改 schema 的 PR 合进 `main` 后必须确认这个 job 绿了，否则线上会跑在新代码 + 旧库上（§2.2 的事故）。

## 6. 备份、恢复、监控

### 6.1 备份 `[现状]` + `[目标]`

| 类型 | 频率 | 保留 | 位置 | 状态 |
|---|---|---|---|---|
| Neon PITR / 历史分支 | 连续 | 按 Neon 当前配置的历史窗口 | Neon | `[现状]` 主备份手段，随项目提供 |
| 逻辑备份（`pg_dump -Fc`） | 每日 | 30 天 | 对象存储 | `[目标]` 未配置定时任务 |

`pg_dump` 不包含角色与扩展，恢复时必须先重建 `app_rw` / `app` 与 `ltree` / `pg_trgm` / `btree_gist`。

```bash
# public、auth 与 Drizzle 迁移记录（默认 drizzle schema）都要备份
pg_dump "$POSTGRES_URL_DIRECT" \
  --schema=public --schema=auth --schema=drizzle \
  -Fc -f backup-$(date +%F).dump
```

### 6.2 恢复

**首选 Neon 分支恢复**：从目标时间点创建分支 → 在分支上验证 schema、RLS 与注册触发器 → 把连接串指向新分支 → 重新部署 → 保留旧分支作为回退。

逻辑恢复：

```bash
# 先确保目标库存在 app_rw / app 角色与三个扩展
pg_restore -d "$POSTGRES_URL_DIRECT" --no-owner --clean --if-exists backup-<date>.dump
```

恢复后**必须**重跑 §4.4 的 RLS 验证，并确认注册触发器仍在——`--clean` 会重建表，策略与触发器可能丢失。

**演练状态**：`[目标]` 计划每季度做一次恢复演练并记录 RPO / RTO 实测值，**至今未演练**，因此没有 RPO / RTO 承诺（见 [10-可观测性与运维](./10-可观测性与运维.md) 的「恢复能力」与 [12-风险与演进规划](./12-风险与演进规划.md)）。行级恢复的取舍（软删 vs 硬删除）也在那两处。

### 6.3 监控 `[目标]`

监控现状、日志字段与告警缺口见 [10-可观测性与运维](./10-可观测性与运维.md)。这里只留目标阈值，供以后接探针时对照：

| 项 | 阈值 | 动作 |
|---|---|---|
| `GET /api/health` | 连续 3 次失败 | 外部探针告警；检查 Neon 连接与 Vercel 部署 |
| Vercel 函数 5xx | > 1%（5 分钟） | 按 `request_id` 查 Vercel 日志 |

| Vercel 函数时长 | 接近平台上限 | 拆分批量写（当前无长任务） |

**当前没有外部探针、没有 APM、没有错误聚合服务**：能看的只有 Vercel 日志、Neon 指标与手动 `curl /api/health`。

| 密钥疑似泄露 | runbook RB-4（轮换 `BETTER_AUTH_SECRET` → 全员重新登录） |
