## 12. 演进路线

| 阶段 | 范围 | 架构影响 |
|---|---|---|
| **M1**（当前） | 录入、编目、成员、默认组织 | 本文档描述的全部 |
| M2 | 谱书预览与分享、回收站、编辑锁、媒体上传、版式设置 | 加 4 张表（`share_link`、`delete_batch`、`resource_lock`、`media`）+ `collab` / `media` 两个模块 + 第 2 个 Route Handler |
| M3 | PDF 排版成书、导出 | 加 `edition` 表 + 排版服务；渲染进程独立部署（Vercel 之外），不进入主应用运行时 |
| M4 | 手机验证码 / OAuth、邮件通道与密码找回、实时协同、OCR | 邮件通道引入第三方投递依赖；实时协同需 CRDT 或 OT |

### 12.1 条件触发

| 触发条件 | 引入什么 |
|---|---|
| 客户反馈编辑覆盖影响使用 | 把编辑锁从 M2 提前 |
| 某查询 p95 > 200ms 且 QPS > 50 | 引入缓存层 |
| `node` 单表 > 500 万行或搜索 p95 > 300ms | 引入外部搜索索引 |
| 单模块团队 > 3 人，或单模块部署频率影响其他模块 | 拆服务 |

**M3 的排版为什么必须独立进程**：Chromium 常驻内存 300MB+，与主应用同进程会把主应用的 GC 压力和 OOM 风险放大一个量级。这是「何时该有第二个运行时」的唯一明确触发条件。

## 14. 已知技术风险

### 14.1 M1 已接受的风险

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | Neon 项目低于 PostgreSQL 18 | 建表与插入直接失败（无 `uuidv7()`） | 创建项目时选 18+；部署前置自检 `SELECT uuidv7();` |
| R2 | React Flow 1000+ 节点帧率 | 核心体验 | Phase 0 第二项验证；不达标则降级为「按代折叠」 |
| R3 | **无编辑锁导致并发覆盖** | 用户数据被旧内容覆盖 | UI 提示 + 帮助文档；客户反馈强烈时把锁提前到 M2 首批。见 [ADR-0002](../decisions/0002-no-edit-lock.md) |
| R4 | **无回收站，误删需运维恢复** | 恢复依赖人工，有响应延迟 | 软删兜底 + [runbook](../guides/runbooks.md)；见 [ADR-0004](../decisions/0004-soft-delete-forever.md) |
| R5 | 注册触发器失败导致注册失败 | 新用户无法注册 | 触发器极简（2 条 INSERT）；集成测试覆盖；失败即回滚，不产生半残账号 |
| R6 | `BETTER_AUTH_SECRET` 泄露或轮换不当 | 会话 Cookie 可被伪造，或轮换导致全量用户登出 | 仅存服务端环境变量；轮换等价全量登出，作为可接受的应急操作。数据库会话仍可单独撤销，见 R20 |
| R7 | **无自助密码找回** | 忘记密码只能人工重置 | [runbook](../guides/runbooks.md)：验证身份后通过 Better Auth 管理入口重置密码并撤销该用户会话；邮件通道进 M4 |
| R8 | auth / auth_service 授权错误 | 密码哈希泄露或 `app_rw` 越权 | 显式 `GRANT`/`REVOKE` 矩阵；集成测试断言 `app_rw` 不能直接读 `auth.*`，认证连接固定 `role=auth_service` |
| R9 | `ltree` 路径长度上限 | 超深谱系无法表达 | 单代路径约 33 字节，理论上限约 1900 代；现实中不存在。文档记录上限即可 |
| R10 | 软删数据永不清理，长期膨胀 | 存储成本、查询变慢 | 十万级数据量下 2 年约 30MB；超过 500 万行再评估归档。**与隐私保留期冲突，见 R18** |
| R11 | Vercel 或 Neon 服务故障 / 函数冷启动 | 请求延迟或短时不可用 | 依赖托管状态页；关键操作重试；Vercel 即时回滚 |
| R12 | 无客户自助导出 | 数据主权争议 | 合同约定 + 手工 `pg_dump` 兜底。**自助导出是数据可携带权的常见要求，见 R18** |
| R13 | Serverless 多实例耗尽 Neon 连接数 | 新请求无法连接数据库 | 使用 pooled endpoint；每实例 pool = 1–5；生产用 `attachDatabasePool` 释放空闲连接；监控连接数 |
| R14 | Vercel 函数执行时长超限 | 长请求被中断 | M1 无长任务；批量写上限 500 行；超时前完成响应 |
| R15 | 登录限流只存在于进程内 | Vercel 多实例下失败计数不共享，暴力尝试可分散到不同实例 | 接受为 best-effort；配合强密码策略；需要严格锁定时再引入持久化计数或上游防护 |

### 14.2 本次评审新增的风险

以下 5 条在原文档中没有登记，但属于同一类「已知且需要决策」的风险。

| # | 风险 | 影响 | 建议 |
|---|---|---|---|
| R16 | **无 staging / preview 环境** | 生产形态的三个假设从未验证：`pg` + `attachDatabasePool` 的连接生命周期、非属主 `app` 角色下 `FORCE RLS` 的兜底、pooled/direct 双 URL 分离下的迁移执行。上线当天可能才发现地基不成立 | 每个 PR 一套 Vercel Preview + Neon 分支（`neonctl branches create`）。成本近零，收益是「第一次真的跑过」 |
| R17 | **谱系图全量加载** | 画布的按代加载只约束渲染，不约束传输与内存。数万人丁的谱系会把整棵图传到浏览器，帧率与内存随之崩塌；G2 与容量目标因此不可同时成立 | 读路径按 `depth` 取窗口（`idx_node_lineage_depth` 已存在），搜索改为「返回目标 + 祖先链」而非全图。口径见 [05-data §8.5](./05-data.md) |
| R18 | **数据生命周期与删除权缺口** | 软删永存意味着账号注销后个人信息仍永久保留。家谱含在世人口信息，数据主体（族人）与账号所有者（修谱人）不是同一人 | 定义数据分级与保留期；给出一条物理删除路径（需要打破「永不 DELETE」与「零后台任务」两个决策）。见 [05-data §8.6](./05-data.md) |
| R19 | **99.5% 可用性不可测量** | 无错误聚合、无外部探针、Vercel 日志不可聚合。指标存在而测量手段不存在，等于没有承诺；且所有写错误返回 HTTP 200，服务端错误率恒为 0% | 补错误聚合 + 一条 5 分钟探针 + 三条 SLO。成本约 1–2 天 |
| R20 | **`BETTER_AUTH_SECRET` 无平滑轮换路径** | 轮换会使现有 Cookie 失效，于是实际结果是不轮换。密钥泄露时最需要轮换的时刻最不敢按 | 数据库会话可在轮换后按用户撤销；轮换流程为「更新 secret → 观察旧会话 → 需要时批量删 `auth.session`」。若 Better Auth 后续支持密钥版本，再评估双密钥 |
