## 风险登记簿

「状态」只有三种：`已接受`（有意共存，不再投入）、`缓解中`（有兜底但没消除）、`需决策`（不能长期挂着，要拍板）。

| 编号 | 风险 | 影响 | 触发信号 | 现在的缓解 | 状态 |
|---|---|---|---|---|---|
| R1 | Neon 项目低于 PostgreSQL 18 | 建表与插入直接失败（没有 `uuidv7()`） | 部署前置自检 `SELECT uuidv7();` 失败 | 创建项目时选 18+；`verify:deploy` 断言版本 | 已接受 |
| R2 | 画布在 1000+ 节点时的帧率 | 核心体验，直接决定产品可用性 | 真实族谱压测掉帧 | 按代渲染窗口 + `onlyRenderVisibleElements` | 缓解中 |
| R3 | 无编辑锁导致并发覆盖（last-write-wins） | 两人同时编辑，后保存的覆盖先保存的 | 客户反馈覆盖问题 | UI 提示；[ADR 0002](../decisions/0002-no-edit-lock.md) | 已接受 |
| R4 | 无回收站，业务删除只能由运维在库里恢复 | 恢复依赖人工，有响应延迟 | 误删投诉 | 软删兜底 + [runbook](../guides/runbooks.md) RB-1 | 缓解中 |
| R5 | 注册触发器失败会连带注册失败 | 新用户无法注册 | 注册 500 | 触发器只做两条 INSERT；失败整体回滚不留半残账号；集成测试覆盖 | 已接受 |
| R6 | `BETTER_AUTH_SECRET` 泄露或轮换不当 | 会话可被伪造，或轮换导致全员登出 | 密钥出现在日志/仓库 | 只存服务端环境变量；轮换按 runbook RB-4 执行 | 已接受 |
| R7 | 无自助密码找回 | 忘记密码只能人工重置 | 用户求助 | runbook RB-2：验证身份后重置并撤销会话 | 已接受 |
| R8 | `app_rw` / `auth_service` 授权矩阵写错 | 密码哈希泄露，或业务角色越权读 `auth.*` | 集成测试出现意外放行 | 显式 `GRANT`/`REVOKE`；集成测试断言两个角色边界 | 缓解中 |
| R9 | `ltree` 路径长度上限 | 超深谱系无法表达 | 单条路径接近上限 | 单代约 33 字节，现实世代数远低于上限 | 已接受 |
| R10 | 软删数据永不清理，长期膨胀 | 存储成本与查询变慢；与保留期要求冲突（见 R18） | 表体积或查询耗时上升 | 超过阈值再评估归档；当前无清理任务 | 需决策 |
| R11 | Vercel / Neon 平台故障与函数冷启动 | 短时不可用或首请求变慢 | 平台状态页告警 | 依赖托管状态页；Vercel 即时回滚上一版本 | 已接受 |
| R12 | 无客户自助数据导出 | 数据主权争议 | 客户要求导出 | 合同约定 + 手工 `pg_dump` 兜底 | 需决策 |
| R13 | Serverless 多实例耗尽 Neon 连接数 | 新请求连不上库 | 日志出现 `too many connections` | pooled 端点 + 每实例池上限 5 + `attachDatabasePool`；runbook RB-5 | 缓解中 |
| R14 | 函数执行时长超限 | 长请求被中断 | 超时错误 | M1 没有长任务；批量写有行数上限 | 已接受 |
| R15 | 登录限流只存在于进程内 | 多实例下失败计数不共享，暴力尝试可分散到不同实例 | 异常登录量 | 接受为 best-effort；`x-forwarded-for` 可伪造这一点已记录 | 已接受 |
| R16 | 无 staging / preview 环境 | 生产形态的三个假设从未真实跑过：`pg` + `attachDatabasePool` 的连接生命周期、非属主 `app` 角色下 RLS 的兜底、pooled/direct 双 URL 下的迁移执行 | 首次真实部署 | `verify:deploy` 与 external E2E 已就绪但未执行 | 需决策 |
| R17 | 谱系图全量加载 | 画布的按代加载只约束渲染，不约束传输与内存；数万人丁的谱系会把整棵树传到浏览器 | 单谱系人丁数增长 | `getNodes` 无分页；`generationLimit` 只裁剪渲染 | 缓解中 |
| R18 | 数据生命周期与删除权缺口 | 软删永存意味着账号注销后个人信息仍在；家谱含在世人口信息，数据主体与账号所有者不是同一人 | 客户询问数据处置能力 | 无保留期、无物理删除路径（需要打破 ADR 0004 与 ADR 0005） | 需决策 |
| R19 | 可用性目标不可测量（无外部探针、无错误聚合） | 指标存在但测量手段不存在，等于没有承诺；页面写错误统一返回 200，服务端错误率恒为 0 | 需要对外承诺 SLA 时 | 只有 `/api/health` 可被手动探测，没有定时探针与告警 | 需决策 |
| R20 | `BETTER_AUTH_SECRET` 没有平滑轮换路径 | 轮换使现有 Cookie 全部失效，于是实际不轮换——最需要轮换时最不敢按 | 泄露事件 | 数据库会话可在轮换后按用户撤销；若认证库支持密钥版本再评估双密钥 | 已接受 |
| R21 | 事实层六表已落库但读写仍全部走 `node` | 存在两套数据形态，回填与对账要持续维护；切换前任何写入都不会进事实层 | 有人开始写事实层查询 | 回填 + 十项对账 CLI 可重复执行；切换计划未编写 | 缓解中 |
| R22 | 谱文 / 谱书表已落库但没有读写路径 | 表结构随需求变化要改迁移，而没人用；评审容易误以为功能已存在 | 开始做谱文/谱书功能 | 页面只渲染占位 `EmptyState`；[03-逻辑视图](./03-逻辑视图-模块设计.md) 明确标注所有权与入口缺口 | 缓解中 |
| R23 | `organization_member` 与 `invite` 是硬删除 | 误删成员/邀请不可恢复，只能从备份恢复 | 误删工单 | 移除成员前预检 + 最后 owner 触发器兜底；备份恢复见 runbook | 已接受 |
| R24 | 没有审计表，`activity_logs` 是可变的产品活动流 | 无法回答「谁改了哪条数据」；日志保留期外无法逐条追溯 | 合规或纠纷追溯需求 | 活动流 + 结构化日志；明确声明它不是审计日志 | 已接受 |
| R25 | 迁移与业务代码在同一 PR 里混提交 | 回滚代码时迁移已在库上，出现版本不匹配 | 需要紧急回滚 | 约定迁移与业务分开提交；CI 有迁移漂移检查；回滚策略要求迁移向后兼容一个版本 | 缓解中 |
| R26 | 单文件行数上限的豁免清单只增不减 | 400 行约束逐渐失效，大文件继续变大 | 豁免条目数增加 | 豁免只许缩小不许扩大（`scripts/check-file-size.mjs`）；评审盯住新增豁免 | 缓解中 |
| R27 | 公开 ID 冲突重试上限为 3 次 | 极端情况下创建失败 | 出现 `conflict` 失败 | 每次重试都生成新 ID（不复用冲突值）；20 位空间下冲突概率极低 | 已接受 |
| R28 | 活动日志与业务写不在同一事务 | 组织级写入的日志可能永久缺失；谱系写入的日志失败会回滚业务（语义不一致） | 日志与数据对不上 | 日志失败只告警不回滚（组织侧）；差异已登记 | 缓解中 |

## 技术债偿还顺序

顺序不是按工作量排，而是按**「不做会不会堵住后面的路」**排。

1. **先补读写路径（事实层切换）**——R21、R22。事实层与谱文/谱书是「表在、路径无」的状态，只要不切换，每加一个业务功能都要同时维护两套数据形态；这是唯一会持续放大利息的债。第一步：先给事实层写查询函数与 DTO，用 `node` 与事实层双跑对账，再切读、最后切写。
2. **再补回收站**——R4、R18。软删数据已经在库里，缺的只是界面与恢复流程；它不阻塞其它工作，但每多一天，误删就多一天只能靠运维。做它的同时必须回答保留期问题（R18），否则回收站会变成「永久保留」的入口。
3. **再补告警与探针**——R19。它不阻塞开发，但阻塞「敢对外承诺可用性」；成本低（一条探针 + 三条 SLO），收益是把 R11、R13 从「不知道」变成「知道」。
4. **最后补审计**——R24。它需要先有明确的合规诉求（谁要、保留多久、能否篡改），否则会做成一张没人查的表；在诉求出现前，活动流 + 结构化日志够用。

被刻意排在最后的：编辑锁（R3，等客户反馈）、缓存层与外部搜索索引（等 R17 的量级信号出现）、拆服务（等团队规模信号）。

## 演进方向

三条路线，每条只写触发条件、第一步和不做什么。**本文件不重新设计目标架构**——目标形态在 [PRD](../prd.md) 与 [decisions](../decisions/README.md) 里。

### 方向一：家谱业务 M1 收尾（谱文、谱书接入）

- **触发条件**：无外部信号，是既定下一步。
- **第一步**：给 `content` / `publishing` 两个域补查询函数与 Action（按 [guides/add-a-feature](../guides/add-a-feature.md) 的顺序），富文本先按 [ADR 0010](../decisions/0010-rich-text-editor-selection.md) 的格式边界落地，编辑器依赖单独 PR 引入。
- **不做什么**：不引入新存储、不加后台任务、不做实时协同；谱书预览与分享（`FR-PREV-*`）仍留在 M2。

### 方向二：多实例化（共享限流、后台任务）

- **触发条件**：单实例承载不住流量，或限流被证明需要真正生效（R15 升级为实际威胁）。
- **第一步**：把限流计数搬到共享存储（同一数据库的一张表即可），再评估是否需要队列。
- **不做什么**：不引入消息中间件、不拆微服务；[ADR 0005](../decisions/0005-zero-background-jobs.md) 的破例条件必须先被满足，且需要新 ADR。

### 方向三：生产化（真实 Vercel / Neon 部署与告警）

- **触发条件**：准备对外交付第一个真实组织。
- **第一步**：建 staging（Vercel Preview + Neon 分支），跑通 `verify:deploy` 与 external E2E，把 R16 的三个假设各验证一次；同时加一条 5 分钟探针与三条 SLO。
- **不做什么**：不为了「生产级」提前引入多 region、双活、APM 全家桶——先把一条链路真正跑通。

## 待决策项

待决策清单的唯一来源是 [decisions 索引](../decisions/README.md) 的「待决策」一节，本文件不复制问题描述。当前影响架构演进的四条：

| 编号 | 主题 | 为什么会改变架构 |
|---|---|---|
| D-4 | 关系模型 | 单 `parent_id` 表达不了过继/兼祧/入赘；一旦要支持，`node` 的树结构、移动语义与画布布局都要改 |
| D-6 | 数据生命周期 | 软删永存与删除权/保留期冲突；决定 R10 与 R18 的解法，可能需要打破「零后台任务」 |
| D-10 | 表单栈 | 扁平表单模型挡住人丁自定义字段与编目树；决定 `content` / `publishing` 域接入时的表单形态 |
| D-11 | 登录限流 | 进程内计数 vs 共享存储；决定方向二的第一步要不要提前 |
