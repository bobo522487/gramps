# 架构文档集重构设计（docs/architecture/ → 15 份 as-is 架构说明）

> **状态**：待批准
> **日期**：2026-10-30
> **决策依据**：用户选定「以代码现状为准（as-is）」+「重构 `docs/architecture/` 为这 15 份」+ 细节切分方案 C（结构级自包含、字段级外链）。

---

## 1. 意图与为什么

### 1.1 现在的问题

`docs/architecture/` 现有 9 份，定位是**目标架构**（`docs/README.md` §1：面向家谱编纂场景的 M1 设计）。它与代码有三处持续扩大的落差：

1. **读者要判断「现在长什么样」必须换文档**：架构文档不写现状，`implementation-status.md`（302 行）是状态表而不是架构叙述——它回答「实现了没有」，不回答「系统怎么搭的」。
2. **目标与现状已经分叉**：事实层六张表（`person`/`person_name`/`family`/`family_partner`/`family_child`/`event`）已落库、有 RLS 与回填对账，但**没有任何读写路径**，`node` 仍是唯一读写源；谱文/谱书表存在、无页面无 Action。目标文档描述的是切换后的形态。
3. **覆盖不全**：用户需要的 15 个视角里，接口与集成、安全、可观测性与运维、需求追溯矩阵、附录这 5 块在架构层没有独立文档，散在 `api.md`/`06-crosscutting.md`/`ops-target.md`/`implementation-status.md` 里。

### 1.2 目标形态

`docs/architecture/` 变成一套 **15 份 as-is 架构说明**，编号 00–14，一份文档回答一个问题，读者不需要在四份文档之间拼图就能读懂「这个系统怎么搭的」。字段级、契约级、运维级的真相**仍然只有一份**，在 `data-model.md` / `api.md` / `ops-target.md` / `setup.md`。

## 2. 目标 / 非目标 / 反目标

### 2.1 目标

| # | 目标 | 验收方式 |
|---|---|---|
| G1 | 15 份文件存在，编号与文件名与用户给定一致 | `ls docs/architecture/` |
| G2 | 每份回答一个独立问题，可单独读懂，不要求先读别的 | 人工评审：随机抽 3 份，只读它能否答出自己的问题 |
| G3 | 所有结构性事实与代码一致，且文中给出可验证的代码路径 | 抽查：表清单、Route Handler 数量、角色与权限字符串、事务边界、日志字段 |
| G4 | `pnpm docs:check --strict` 与 `pnpm test` 全绿 | 命令输出 |
| G5 | 单一事实来源不变：字段级/契约级/运维级细节仍只写在原文档 | 评审：15 份里不出现列定义、完整错误码表、逐条环境变量说明 |

### 2.2 非目标

- **不写 to-be 设计**。目标形态留在 `prd.md`、`decisions/`；13 章只写「触发条件 + 演进方向」，不重新设计目标架构。
- **不改 `data-model.md` / `api.md` / `ops-target.md` / `setup.md` 正文**。只在链接目标改名时改链接。
- **不写教程**。`setup.md`、`guides/` 已经承担「怎么跑、怎么加功能、怎么值班」。
- **不追求 C4-L3 逐组件图**。06 章的 L3 用「部署单元 + 运行时进程」表达，不逐模块画图。

### 2.3 反目标（做了就算失败）

| 反目标 | 为什么是失败 |
|---|---|
| 出现第二份表结构真相（列/索引/策略体抄进 04） | 下次改迁移时两处漂移，`docs:check` 报矛盾措辞；仓库已因手抄表清单翻车三次（D-24） |
| 在架构文档里写「已实现 / 未实现」状态 | 状态只允许在 `implementation-status.md`；目标文档写状态横幅会在下次更新时变成谎话（`docs/README` §5.2） |
| 抄命令清单、环境变量清单、错误码表 | 同上，且 `setup.md` / `api.md` 是唯一来源 |
| 保留旧 9 份与新 15 份并存 | 读者要在两套编号间跳，等于没重构 |

## 3. 约束

### 3.1 仓库强制的约束（`scripts/check-docs.mjs`）

- `docs/architecture/*.md` 前 15 行必须含 `回答什么问题`、`读者`、`长度上限`，以及 `目标 vs 现状` 或 `本文档为新增`。
- 禁用措辞清单（`forbiddenPhrases`，如 `1 个 Route Handler`、`目标 10 张业务表`、`ActionResult`、`revalidateTag`）不得出现在 `docs/` 下的受检文件里。
- 过期路径（`docs/adr/`、`src/modules/` 等）不得出现。
- 所有相对链接目标必须存在，`#锚点` 必须匹配目标文件标题（标题按 `slugify` 规则：小写、去反引号、空格转 `-`）。
- 裸 RLS 子查询写法（`organization_id IN (SELECT ... FROM organization_member)`）被禁止。

### 3.3 写作约束

- 简体中文，与仓库其余文档一致；品牌「云谱」。
- 每份文件头四字段 + 一行「本文描述当前实现」。
- 长度按「页」声明，正文建议 ≤ 400 行（`arch:check` 只管代码，但长文档没人读）。
- 图用 mermaid；只画结构/流程，不画装饰。

## 4. 方案：细节切分（已选 C）

三个候选已在对话中给出：A 完全自包含（违反单一事实来源）、B 纯归纳 + 深链（读不成一套）、**C 结构级自包含、字段级外链（选定）**。

### 4.1 边界规则（本设计最需要被守住的东西）

| 层级 | 判据 | 写在哪 |
|---|---|---|
| **结构级** | 表名与职责、实体关系、约束**类别**（唯一/部分唯一/复合外键/触发器）、模块与依赖方向、流程步骤、接口清单与状态码**类别**、部署单元与环境**类别**、日志字段名 | 架构文档正文 |
| **字段级** | 列定义、索引 DDL、RLS 策略体、触发器函数体、完整错误码表、逐条环境变量说明、命令 | 原文档，架构文档只放链接 |

**判定问句**：「这条事实变了，需要改几个文件？」——答案必须是 1。若为 2，说明写深了，往后退一层。

### 4.2 已知的边界灰区与本设计的裁决

| 灰区 | 裁决 | 理由 |
|---|---|---|
| 17 张表的清单 | 04 章写「表名 + 一句话职责 + 分组（认证/组织/内容/事实层/活动）」，列级链 `data-model.md` | 表清单是理解架构的必要结构，且变更频率低；列级是高频漂移区 |
| 4 个 Route Handler 的路径与 DTO 形状 | 05 章写路径 + 状态码类别（401/403/404/200），DTO 字段链 `api.md` | 数量与路径是结构，字段是契约细节 |
| 9 个权限字符串 | 09 章写角色 → 权限的**矩阵形状**与判定入口 `hasPermission()`，字符串全集链 `lib/auth/permissions.ts` | 矩阵是架构，字符串全集是代码 |
| 环境变量 | 06 章写「必需 / 可选」两组与用途一句话，逐条说明链 `ops-target.md` | 变量名清单漂移快，`lib/config.ts` 的 Zod schema 才是真相 |
| 迁移文件清单 | 一律链 `lib/db/migrations/meta/_journal.json`，不枚举 | 已有明确教训（D-24） |
| 测试文件数/用例数 | 不写数字，写分层与覆盖范围 | 同上 |
